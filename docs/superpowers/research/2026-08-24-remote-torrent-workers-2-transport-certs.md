================================================================================
AGENT: web:acme-for-workers
================================================================================
SUMMARY: The single most important finding is that the research premise ("use Let's Encrypt for a hostname") is now partly obsolete: since 15 January 2026 Let's Encrypt issues **publicly-trusted certificates for bare IP addresses** (GA), under the `shortlived` profile (160 h ≈ 6.7 days), validated with http-01 or tls-alpn-01 directly against the IP — no DNS, no domain, no zone API. Since ss workers are VPSes with public IPs, this collapses the whole certificate problem for self-hosters to "open port 80, run ACME." For the main instance's own fleet, a per-worker subdomain on a **dedicated registered domain** is still preferable for operational flexibility, and the right key-custody model is Tailscale's, not Plex's: the *worker* runs ACME and keeps the private key; the *server* only writes the DNS record. Never ship a shared wildcard key to workers — that is the one option to reject outright. On crates: `instant-acme` 0.8.5 is the only Rust ACME client covering everything you might need (dns-01, `Identifier::Ip`, ACME profiles, ARI/RFC 9773); `rustls-acme` 0.15.4 is more turnkey but has literally zero support for profiles, IP identifiers, or ARI (verified by grep of its source). Caddy-as-sidecar is disqualified for the IP path — it hardcodes a refusal to request public-IP certs (caddy#7399). ARI-based renewals are **exempt from all Let's Encrypt rate limits**, which removes the "50 certs per registered domain per week" ceiling for everything except first issuance of a new worker.

### Let's Encrypt IP-address certificates are GA (the game-changer for this design)
Announced GA 2026-01-15. IP certs (IPv4 and IPv6) are only available under the `shortlived` profile — LE's reasoning: "IP addresses are more transient than domain names, so validating more frequently is important." The profiles table confirms `shortlived` is the only profile whose Identifier Types column reads "DNS, IP"; `classic` (90 d) and `tlsserver` (45 d) are DNS-only. Validity = 160 hours. Max 25 names. dns-01 is structurally impossible for an IP identifier, so validation is http-01 (port 80) or tls-alpn-01 (port 443). Private/reserved ranges are refused. Practical consequence for ss: a worker VPS needs *nothing* but a public IP and an open port 80 to get a browser-valid cert — no domain, no DNS API, no server involvement at all.
sources: https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability; https://letsencrypt.org/docs/profiles/; https://aye.sh/blog/letsencrypt-ip-address-certificates

### Rate limits: ARI renewals are exempt from ALL limits — this kills the 50/week ceiling
Verbatim from letsencrypt.org/docs/rate-limits (last updated 2026-08-05): "Renewals coordinated by ARI offer the unique benefit of being exempt from all rate limits... If the new order includes at least one identifier matching the certificate it intends to replace and the certificate has not been previously replaced using ARI, the order will not be subject to any rate limits." Non-ARI renewals (exact same identifier set) are still exempt from *New Orders per Account* and *New Certificates per Registered Domain*, but remain subject to *New Certificates per Exact Set of Identifiers* (5 per 7 days) and auth-failure limits. Net effect: the 50-certs-per-registered-domain/week budget is consumed only by **first issuance for a brand-new worker** — i.e. you can onboard 50 new workers a week per registered domain, forever, with unlimited renewals.
sources: https://letsencrypt.org/docs/rate-limits/

### For IP certs, the rate-limit bucket is the IP itself
"If you're requesting a certificate for an IP address, we also try to treat the most common allocation... as the 'registered domain'. For IPv4 addresses, we treat the exact address as the registered domain. For IPv6 addresses, we treat the containing /64 range as the registered domain." So each worker gets its own private 50/week budget — fleet size is completely unbounded on the IP path. The binding constraint is the exact-set limit of 5 per 7 days: renewing a 160 h cert every 3 days = 2.33/week, safely under, and with ARI `replaces` it is exempt entirely.
sources: https://letsencrypt.org/docs/rate-limits/

### `workers.giuli.dev` is NOT a separate rate-limit bucket — this is a concrete trap
Let's Encrypt computes the "registered domain" via the Public Suffix List: for `w7.workers.giuli.dev` the registered domain is `giuli.dev`. The 50-certs/week bucket is therefore SHARED with ss.giuli.dev and every other subdomain, and it is a *global* limit ("all new order requests, regardless of which account submits them, count towards this limit"). If you go the subdomain route, buy a dedicated registered domain (e.g. `ssworkers.dev`) so a runaway worker-enrollment loop cannot lock you out of renewing the certificate for the main site.
sources: https://letsencrypt.org/docs/rate-limits/

### The Plex model (*.plex.direct) — mechanism and why you should NOT copy it wholesale
Plex runs a DNS zone where `1-2-3-4.<hash>.plex.direct` resolves to `1.2.3.4`, and issues each server a **wildcard cert for `*.<hash>.plex.direct`**, where hash is derived from the server identity. The wildcard is what buys IP mobility: the same cert stays valid as the server's IP changes, because the IP is just a label in the name. Filippo's analysis of why it is safe to hand the user the private key: "the user/server/whatever hash makes it so a certificate can only be used to authenticate a specific server (even if it can have any IP)." Note that per-server scoping is load-bearing — a single shared `*.plex.direct` key would be catastrophic. The famous pitfall is entirely a *private-IP* problem: routers/resolvers with DNS-rebinding protection (dnsmasq, pfSense/unbound, Pi-hole, NextDNS, Sophos) refuse to return private RFC1918 answers for public names, breaking `192-168-1-7.<hash>.plex.direct`; the fixes are per-resolver allowlists (`rebind-domain-ok=/plex.direct/`, `private-domain: "plex.direct"`). **ss workers are on public IPs, so the rebinding pitfall does not apply to you** — rebinding protection only triggers on private-range answers.
sources: https://words.filippo.io/how-plex-is-doing-https-for-all-its-users/; https://support.plex.tv/articles/206225077-how-to-use-secure-server-connections/; https://github.com/nextdns/metadata/issues/500; https://discourse.pi-hole.net/t/plex-secure-connections-issues-with-dns-rebinding-possible-fix/15240

### tlsmy.net — an open reimplementation of the Plex model, with the identity-proof detail worth stealing
tlsmy.net issues `*.<accountid>.tlsmy.net` where accountid is "a base36 fingerprint of your Let's Encrypt account public key", and its DNS resolves `A-B-C-D.<accountid>.tlsmy.net` → `A.B.C.D`. The client generates its own key, and proves entitlement to its subdomain by signing the TXT-publication request **with its Let's Encrypt account private key** — the service verifies the signature matches the fingerprint in the requested name. Author's own caveat: "designed to be a proof-of-concept and NOT a production service", scaling blocked by the 50-certs/week limit (written before ARI exemptions existed). For ss you get this property for free: the worker is already authenticated on the control channel, so the control channel *is* the entitlement proof.
sources: https://github.com/supersat/tlsmy.net

### Tailscale's ts.net model — the correct key-custody pattern for option (a)
`tailscale cert` has the *node* run ACME against Let's Encrypt; the node generates both the certificate private key and the LE account private key locally, and calls the Tailscale control plane over the already-authenticated channel to publish the `_acme-challenge` TXT record in the `*.ts.net` zone. Tailscale's own statement: "The certificate's private key and the Let's Encrypt account's private key are generated and stored locally on the machine and Tailscale never sees them." This is exactly the shape ss should use if it goes the subdomain route: the Go server never handles a private key, it only writes DNS on request from an authenticated worker.
sources: https://tailscale.com/docs/how-to/set-up-https-certificates; https://tailscale.com/blog/tls-certs; https://github.com/tailscale/tailscale/issues/1235

### instant-acme 0.8.5 — the correct crate choice; verified against the source
Published 2026-06-24, Apache-2.0, by djc (also rustls maintainer), used in production at Instant Domain Search. Verified directly in the .crate tarball: `pub enum Identifier { Dns(String), Ip(IpAddr), PermanentIdentifier(String), HardwareModule(String) }` with the Ip variant documented as "An IP address (IPv4 or IPv6) identifier"; `NewOrder::profile(&str)` for ACME profiles (draft-aaron-acme-profiles); `NewOrder::replaces(CertificateIdentifier)` for ARI with the exact rate-limit caveat spelled out in the doc comment; `RenewalInfo`/`SuggestedWindow` behind the `time` feature; `ChallengeType` covers Http01/Dns01/TlsAlpn01/DeviceAttest01. Crucially, `Order::finalize()` (rcgen feature) builds the CSR from `identifier.to_string()` via `rcgen::CertificateParams::new`, and rcgen 0.14 does `match IpAddr::from_str(&s) { Ok(ip) => SanType::IpAddress(ip), Err(_) => SanType::DnsName(...) }` — so **IP identifiers automatically become correct iPAddress SANs with no extra work**. Limitation: P-256 ECDSA account keys only.
sources: https://github.com/djc/instant-acme; https://docs.rs/instant-acme/latest/instant_acme/enum.Identifier.html; https://docs.rs/instant-acme/latest/instant_acme/

### rustls-acme 0.15.4 — turnkey but disqualified for anything IP/profile/ARI
0.15.4 published 2026-08-11, ~651k downloads, very ergonomic (`AcmeConfig::new(["example.com"]).cache(DirCache::new(...)).incoming(tcp_listener.incoming(), vec![])` yields a stream of accepted TLS connections, with tls-alpn-01 served inline on the *same* port 443 — no port 80 needed). But I grepped src/ of the published crate: **zero occurrences of `profile`, `IpAddr`, `renewal-info`, `ari`, or `replaces`**. So it cannot request the `shortlived` profile (→ cannot do IP certs) and cannot do ARI. It also does not support dns-01 at all (docs: "The validation mechanism used is TLS-ALPN-01 OR HTTP-01"). Also only 3.6% documented per docs.rs. Fine if you commit permanently to DNS-name-only certs on the 90-day `classic` profile.
sources: https://docs.rs/rustls-acme/latest/rustls_acme/; https://lib.rs/crates/rustls-acme

### Caddy-as-sidecar is currently broken for IP certs
caddy#7399: requesting an IP cert with the shortlived profile fails with `subject '167.150.90.148' cannot have public IP certificate from https://acme-v02.api.letsencrypt.org/directory (if CA's policy has changed, please notify the developers in an issue)` — a hardcoded client-side policy check in Caddy/CertMagic that predates LE's GA and has not been lifted. Profiles themselves *are* supported since Caddy 2.10 (ACMEz/CertMagic added them ahead of the LE rollout), so the DNS-name path works; the IP path does not. Workaround people use is acme.sh issuing the cert and Caddy loading static cert paths. Independently, putting Caddy in front of the worker adds a proxy hop on a path that is pushing video bytes at the browser — not worth it.
sources: https://github.com/caddyserver/caddy/issues/7399; https://caddy.community/t/using-setting-acme-profiles-as-of-2-10/31006/2; https://caddyserver.com/docs/automatic-https

### Caddy's on-demand TLS is the wrong shape for this problem anyway
On-demand TLS obtains a cert during the TLS handshake for whatever SNI arrives, gated by an `ask` HTTP endpoint that you implement to authorize the hostname. Notably: when an `ask` endpoint is configured, Caddy does not apply its own internal rate limiting — "your endpoint is expected to make wise decisions instead." That model is designed for multi-tenant SaaS custom domains (unbounded, user-supplied hostnames). ss has a *known, enrolled, small* set of workers whose identity the control plane already establishes, so handshake-time issuance buys nothing and adds a first-connection latency spike plus a DoS surface.
sources: https://caddyserver.com/docs/automatic-https; https://caddy.community/t/on-demand-tls-if-ask-endpoint-takes-long-it-does-nothing/14672

### sslip.io / nip.io / traefik.me / localhost.direct — reject for production
These are shared registered domains: every user's certs come out of one Let's Encrypt bucket. sslip.io's maintainer had the limit raised from 50 to 250,000 but a request for 500,000 was refused ("This is too large for us to support"), and users who get rate-limited are told to open a GitHub issue. nip.io/sslip.io explicitly do not support wildcard certs. localtls / dummytls / traefik.me / localhost.direct exist to solve the *private-IP* secure-context problem — irrelevant here, since ss workers have public IPs and can get real certs. Fine for dev/staging convenience, never for the product.
sources: https://github.com/cunnie/sslip.io/issues/6; https://nip.io/; https://github.com/Corollarium/localtls; https://github.com/paullouisageneau/dummytls/blob/master/README.md

### SNI is the hidden gotcha on the IP path
RFC 6066 forbids IP literals in the SNI HostName field, so a browser opening `https://203.0.113.5/...` sends **no SNI at all**. The worker's rustls `ResolvesServerCert` must therefore return the IP cert as the default/no-SNI certificate rather than failing the handshake — this is the same issue reported in the wild as "SNI must be disabled in web servers like Caddy" when serving IP certs. Related trap: tls-alpn-01 for an IP identifier does not use the IP in SNI either (the IP-identifier drafts use the reverse-DNS name, e.g. `5.113.0.203.in-addr.arpa`), which is fiddly to get right — **use http-01 on port 80 for IP certs** and avoid the whole question.
sources: https://aye.sh/blog/letsencrypt-ip-address-certificates; https://letsencrypt.org/docs/challenge-types/

### One certificate can cover both the hostname and the IP
The `shortlived` profile permits mixed identifier sets (up to 25 names), and the rate-limit docs use `[192.168.1.1, www.example.com, example.com]` as their worked example of an "exact set of identifiers", confirming mixed DNS+IP orders are a supported shape. So a worker can hold a single cert for `[w7.ssworkers.dev, 203.0.113.5, 2001:db8::5]`, served with or without SNI — belt and braces, one renewal loop, at the cost of accepting the 6-day lifetime for everything.
sources: https://letsencrypt.org/docs/rate-limits/; https://www.ai.moda/en/blog/ip-and-domain-one-cert-lets-encrypt

### Certificate Transparency publishes your worker fleet
Every publicly-trusted cert is logged to CT and is searchable on crt.sh/Censys — Let's Encrypt's own rate-limit docs point you there to audit your issuance. Concretely: with per-worker subdomains, a `crt.sh?q=%25.ssworkers.dev` query enumerates the entire fleet's hostnames (and DNS then gives the IPs); with IP certs, the IPs are directly in the logs. Given that these workers exist to fetch torrents, that is a real disclosure to reason about deliberately rather than discover later. It is not avoidable while using a public CA — the mitigations are (i) a dedicated throwaway registered domain that isn't linkable to giuli.dev, or (ii) accepting it on the grounds that a torrenting node's IP is publicly visible in the swarm anyway.
sources: https://letsencrypt.org/docs/rate-limits/

### DNS-PERSIST-01 will simplify the dns-01 path — but not yet
New challenge type (Feb 2026): a single standing TXT at `_validation-persist.<domain>` naming the CA and the ACME account URI, reusable indefinitely, with optional `policy=wildcard` and `persistUntil`. It removes DNS writes from the issuance path entirely — the server would write one record at worker enrollment and never touch DNS again. Status per Let's Encrypt: Pebble support done, lego implementation in progress, staging late Q1 2026, **production targeted Q2 2026**. Design for it, don't depend on it: keep the DNS-write RPC on the control channel abstract enough that you can swap in a one-time persist record later.
sources: https://letsencrypt.org/2026/02/18/dns-persist-01

### acme-dns / CNAME delegation as the alternative to giving anyone zone credentials
If a self-hoster balks at handing their instance a Cloudflare token with Zone:DNS:Edit over their real zone, the standard answer is CNAME delegation: `_acme-challenge.w7.example.com` CNAMEs to a delegated zone (acme-dns, acmedns.org, or Certify DNS), so "your primary DNS zone never changes after initial CNAME setup, and the ACME client only needs credentials for the delegated zone" and "when acme-dns API keys are exposed, the effects are limited to the subdomain TXT record in question." Worth documenting as the self-hoster escape hatch, but it is strictly more setup than just using an IP cert.
sources: https://cert-manager.io/docs/configuration/acme/dns01/acme-dns/; https://acmedns.org/; https://github.com/joohoi/acme-dns

### Fallback CA if you ever need one
Google Trust Services offers free ACME issuance with External Account Binding and, unlike LE, **configurable** validity down to 1 day (3+ recommended for clock skew), with per-customer rate limits negotiated through your Google Cloud account. Useful as a second issuer if LE ever rate-limits or has an incident — worth keeping the issuer URL and EAB creds configurable rather than hardcoding LE.
sources: https://cloud.google.com/certificate-manager/docs/public-ca-tutorial; https://scotthelme.co.uk/blink-and-youll-miss-them-6-day-certificates-are-here/

### Short-lived certs change the failure mode you must engineer for
160 h is short enough that a worker which was powered off for a week comes back with an expired cert. The worker must therefore (i) attempt issuance/renewal *before* announcing readiness on the control channel, and (ii) never advertise itself as job-eligible while holding an expired or absent cert — otherwise the browser gets a hard TLS error mid-playback with no recoverable signal. LE's `tlsserver` profile (45 days, DNS-only, max 25 names) is the middle ground if you want more slack on the DNS-name path; LE is separately walking the default down from 90 to 45 days over the coming years, so build the renewal loop as if lifetimes will keep shrinking.
sources: https://letsencrypt.org/docs/profiles/; https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability

RECOMMENDATIONS:
- RANK 1 — for a random self-hoster's instance (and as the universal fallback for your own fleet): **Let's Encrypt IP-address certificate, obtained by the worker itself, http-01 on port 80, `shortlived` profile.** Zero DNS, zero domain, zero server involvement, per-IP rate-limit bucket so it scales without bound, and the private key never exists anywhere but the worker. This is the only option that preserves the 'zero install, it just works' promise for someone who owns a VPS but no domain. Exact call shape with instant-acme 0.8.5: `NewOrder::new(&[Identifier::Ip(public_ip)]).profile("shortlived")`, take `ChallengeType::Http01`, serve `challenge.key_authorization().as_str()` at `/.well-known/acme-challenge/{token}` on :80, `challenge.set_ready()`, then `order.finalize()` — rcgen turns the IP identifier into an `iPAddress` SAN for you.
- RANK 2 — for the main instance's own fleet: **per-worker subdomain `w<id>.ssworkers.dev` on a DEDICATED registered domain, A/AAAA record written once by the Go server at enrollment, ACME run entirely by the worker.** Buy a separate registered domain — `workers.giuli.dev` shares the 50-certs/week bucket with ss.giuli.dev because the PSL registered domain is `giuli.dev`. Gives you a stable name independent of VPS IP changes, nicer logs/debugging, and the ability to repoint DNS at a relay if a worker dies mid-session.
- For RANK 2's validation, prefer **http-01 on port 80** over tls-alpn-01, even though tls-alpn-01 is tidier. Reason: it is the same code path you already need for the IP-cert case, so one worker binary handles named and unnamed deployments with one ACME implementation. If you later want the worker to also be reachable by IP, put both identifiers in ONE order — `[Identifier::Dns("w7.ssworkers.dev"), Identifier::Ip(v4), Identifier::Ip(v6)]` with `profile("shortlived")` — and serve that single cert regardless of SNI.
- Use **instant-acme 0.8.5**, not rustls-acme. rustls-acme is more ergonomic but has no profiles, no IP identifiers and no ARI (verified by source grep), which permanently forecloses the IP path and the rate-limit exemption. Enable the `rcgen`, `x509-parser` and `time` features. Budget ~150 lines for the order state machine plus a ~30-line hyper service on :80 for the http-01 responder. Keep the issuer directory URL and optional EAB credentials configurable so Google Trust Services can be swapped in.
- Implement **ARI-based renewal from day one**, not a naive 'renew at 2/3 lifetime' timer. Persist the issued cert, extract its `CertificateIdentifier` (x509-parser feature), poll `renewal_info`, renew inside `SuggestedWindow`, and always pass `NewOrder::replaces(cert_id)`. This makes every renewal exempt from *all* Let's Encrypt rate limits, so your only budget consumption is first-issuance for a newly enrolled worker. Do not call `replaces` twice against the same predecessor cert — LE only exempts the first replacement of a given certificate.
- Only fall back to **dns-01 relayed over the existing control channel (Tailscale's model)** if http-01 turns out to be blocked — e.g. a provider that filters :80, an IPv6-only worker, or a future need for a wildcard. Shape: worker generates account key + cert key locally, gets the dns-01 token, sends `{op:"acme_txt", name:"_acme-challenge.w7.ssworkers.dev", value: challenge.key_authorization().dns_value()}` over the authenticated WSS; the Go server writes it via a Cloudflare API token scoped to Zone:DNS:Edit **on the workers zone only**; worker polls and finalizes. The server never sees a private key. Watch DNS-PERSIST-01 (LE production target Q2 2026) — it would reduce this to a single TXT written once at enrollment.
- REJECT the shared wildcard `*.workers.giuli.dev` distributed to all workers. It requires shipping a private key over the wire, puts the key in the server's custody, and makes any single worker compromise a full-namespace impersonation of every other worker — including the ability to MITM host browsers. If you specifically want IP mobility, the safe variant is the Plex/tlsmy.net shape: a **per-worker** wildcard `*.<random>.ssworkers.dev` issued via dns-01, one scope per worker. Note that ss doesn't actually need IP mobility, because the control channel already reports each worker's current IP and the server can rewrite an A record in seconds.
- REJECT sslip.io/nip.io-style third-party DNS for production (shared LE bucket at another maintainer's discretion, no wildcards, extra party in the trust path) and reject Caddy-as-sidecar (hardcoded refusal to request public-IP certs per caddy#7399, plus an unwanted proxy hop on a video-bytes path). Both are fine for local dev only.
- Plumb three things into the worker's TLS/HTTP layer that are easy to miss: (1) a rustls cert resolver that returns the cert when **SNI is absent**, because browsers send no SNI for IP-literal URLs (RFC 6066); (2) CORS for the mediabunny CustomSource range reads — `Access-Control-Allow-Origin: https://ss.giuli.dev`, `Access-Control-Allow-Headers: Range`, `Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length`, and a real preflight handler, since `Range` is not CORS-safelisted; (3) a readiness gate so a worker never advertises itself as job-eligible while its cert is expired or missing — with 160-hour certs, a worker offline for a week comes back broken and would otherwise hand the browser an unrecoverable TLS error mid-playback.
- Decide the Certificate Transparency question deliberately, now. Every worker cert lands in public CT logs: with subdomains, `crt.sh?q=%25.ssworkers.dev` enumerates the whole fleet; with IP certs, the IPs are logged directly. Given the fleet's purpose, either accept it (a torrent peer's IP is public in the swarm anyway) or register the workers' domain so it is not trivially linkable to giuli.dev — but do not assume the fleet is private.
- Test everything against `https://acme-staging-v02.api.letsencrypt.org/directory` first (LE's *Authorization Failures per Identifier* limit is only 5/hour and consecutive failures eventually pause the account for that identifier), and cache both the ACME account credentials and the issued cert in the worker's state dir — a worker that re-registers an account on every restart will burn the 10-accounts-per-IP-per-3h limit.

OPEN_QUESTIONS:
- Do the two existing VPSes have stable IPs and unfiltered inbound port 80? Some providers (notably OVH/Hetzner under DDoS mitigation, and some abuse-flagged ranges) filter :80 — that determines whether http-01 is viable or you need the dns-01-over-control-channel path from the start.
- Are the workers IPv4-only, or dual-stack? If a host browser is on IPv6-only mobile, an IPv4-only worker is unreachable regardless of certificates. This should probably drive a requirement that workers have a routable AAAA and that the cert covers both.
- What is the intended behaviour when a worker VPS's IP changes (provider migration, floating IP failover)? With IP certs the cert is instantly dead; with subdomain certs only an A-record update is needed. If IP churn is expected, that argues for ranking the subdomain path first even for self-hosters who have a domain.
- Does the self-hoster story assume they run the Go server and the worker on the SAME box? If so, the worker can just share the instance's existing certificate and hostname (e.g. a path prefix on ss.example.com), and no per-worker certificate machinery is needed at all for the simplest deployment — worth confirming before building enrollment for a case that may be the majority.
- Is a server-relayed data-plane fallback in scope? It would cover workers behind NAT/CGNAT, workers whose cert issuance failed, and browsers on networks that block IP-literal HTTPS — but it puts the video bytes back through the instance, which is exactly the bandwidth cost the worker design avoids. Worth deciding whether it exists as a degraded mode.
- Confirm empirically that Chrome, Firefox and Safari all accept a Let's Encrypt IP-SAN certificate for a cross-origin `fetch()` with a `Range` header, on a non-443 port if you plan to use one. The feature is only ~7 months old at GA; the search results on IP-SAN browser handling were dominated by pre-2020 material and none of it tested the modern LE IP certs. This is a 30-minute experiment against a staging-issued cert and should be run before committing.

AGENT: web:browser-to-worker-http
================================================================================
SUMMARY: Reading torrent bytes from a remote HTTPS worker is cheaper than expected on the CORS axis and more expensive than expected on the abort axis. `Range` has been a CORS-safelisted request header in all three engines since Firefox 117 (Aug 2023), so a plain cross-origin `GET` carrying a single `bytes=N-M` range triggers **no preflight at all** — provided nothing else on the request is unsafe. That makes a URL-embedded capability ticket strictly better than an `Authorization` header, which would put a preflight (and a WAN RTT) in front of reads and is explicitly not covered by `Access-Control-Allow-Headers: *`. The hard problem is cancellation: mediabunny only aborts an in-flight read on `Input.dispose()`, and ss keeps one `Input` alive across every region restart (`clientMedia.ts:82` built once, reused at `:486`; a seek only calls `conversion.cancel()` at `:433`), so **a seek cannot cancel the outstanding torrent read** — the worker will keep serving and prioritizing bytes for a region the room already left. The data-plane contract therefore needs an out-of-band playhead/retract endpoint, streaming (never buffered) 206 responses with server-side length caps and stall deadlines, and h2 so that mediabunny's constant self-aborts cost an RST_STREAM instead of a TCP+TLS handshake. Viewers are confirmed never to touch the worker: the Go server serves only `.m3u8` (`internal/httpapi/media.go:27`), rewritten to `cfg.MediaPublicURL` so segments come straight from R2.

### Range IS CORS-safelisted — zero preflights for the data plane
Fetch's CORS-safelisted request-header algorithm lists `range` alongside accept/accept-language/content-language/content-type. The `range` case runs "parse a single range header value given value and false", returns false on failure or when rangeValue[0] is null — i.e. only `bytes=[0-9]+-[0-9]*` qualifies (a suffix range `bytes=-500` and multi-ranges do NOT). Two extra gates: step 1 rejects any header value longer than 128 bytes, and the "CORS-unsafe request-header names" algorithm dumps everything into the unsafe list if the combined safelisted value size exceeds 1024 bytes — neither is reachable with a byte-range value. Shipped: Chromium first, WebKit next, Firefox in 117 (bug 1733981 RESOLVED FIXED, Aug 2023: "Allow single range header values without preflight"). Both shapes ss produces are safelisted: the hand-rolled `bytes=${start}-${clamped-1}` (web/src/pipeline/remuxJob.ts:99) and mediabunny UrlSource's open-ended `bytes=${worker.currentPos}-` (node_modules/mediabunny/src/source.ts:915). Consequence: if the only non-default thing on the request is Range, the worker never sees an OPTIONS.
sources: https://fetch.spec.whatwg.org/#cors-safelisted-request-header; https://developer.mozilla.org/en-US/docs/Glossary/CORS-safelisted_request_header; https://bugzilla.mozilla.org/show_bug.cgi?id=1733981

### Authorization header: works in a Web Worker, but costs a preflight per request-ish
A `fetch()` inside a dedicated Web Worker is the same Fetch machinery with the owner document's origin, so a cross-origin `Authorization` header works fine *if* CORS allows it — there is no worker-specific restriction. The cost is the problem. `Authorization` is not safelisted, so every read becomes preflighted; `Access-Control-Allow-Headers: *` does NOT cover it (MDN: "The Authorization header doesn't accept wildcard and always needs to be listed explicitly"); and whatwg/fetch#1278 documents Chrome and Firefox re-preflighting on every request when Authorization is set programmatically unless the server explicitly names it in ACAH. Even with it named, the preflight cache is capped hard: Firefox 86400s, Chromium 7200s (600s pre-v76), Safari ~600s — values above the cap are clamped. Over a 150ms WAN RTT that is a needless extra round trip in front of the very first read of every cache window. Verdict: do not use a header for read auth.
sources: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Allow-Headers; https://github.com/whatwg/fetch/issues/1278; https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Max-Age

### Which response headers must be exposed
Fetch's CORS-safelisted response-header names are Cache-Control, Content-Language, Content-Length, Content-Type, Expires, Last-Modified, Pragma — so `Content-Length` is already visible cross-origin and needs no exposing. `Content-Range` and `Accept-Ranges` are NOT in that list and need `Access-Control-Expose-Headers`. mediabunny reads `Content-Range` at source.ts:937-941 to derive file size (regex `/\/(\d+)/`), falling back to `Content-Length` at :944-952 with `basePos = status===206 ? worker.currentPos : 0`. If Content-Range is hidden the fallback still computes the right total ONLY while the worker answers open-ended ranges without capping the length — the moment you cap responses server-side (recommended, see contract) the fallback computes a wrong file size. So: exposing Content-Range is mandatory, not cosmetic. `Accept-Ranges` is never read by mediabunny (grepped: zero hits in node_modules/mediabunny/src) — expose it for humans/curl only. `Access-Control-Expose-Headers: *` is honoured for non-credentialed requests, which ours are.
sources: https://fetch.spec.whatwg.org/; web/node_modules/mediabunny/src/source.ts:937-952

### THE abort problem: mediabunny cannot cancel a read, and ss never disposes the Input
`CustomSourceOptions.read` has signature `(start, end) => MaybePromise<Uint8Array | ReadableStream>` — no AbortSignal (source.ts:1416). `_runWorker` awaits the read and only *then* checks `worker.aborted` and discards the bytes (source.ts:1483-1495). Grepping every assignment of `.aborted =` shows it is set in exactly three places: `ReadOrchestrator.dispose()` (source.ts:2598), worker creation while already disposed (:2279), and UrlSource's non-206 sequential fallback (:1185). There is no per-read cancellation path. Now the ss side: `plan.input` is constructed once (web/src/pipeline/clientMedia.ts:82) and reused by every region's `Conversion.init({ input: plan.input, ... })` (clientMedia.ts:485-490). A seek runs `restartAt()` which aborts *upload* controllers only (`inflightAborts`, clientMedia.ts:280,432 — those wrap the R2 PUT batches at :295-306) and calls `conversion?.cancel()` (:433). `Input.dispose()` is never called. Net effect over WAN: after a seek, the abandoned region's outstanding Range read stays open against the torrent worker, holding piece priority for bytes nobody will use, competing with the new region's reads — the exact failure the recent perf commits (e2f4b43, 77272aa) fought on the local-bridge side. And because CustomSource is capped at `maxWorkerCount: 2` (source.ts:1439) and LRU eviction refuses to reclaim a worker with pending slices (:2261), one stuck read can starve the new region entirely.
sources: web/src/pipeline/clientMedia.ts:82,280,432,433,485; web/node_modules/mediabunny/src/source.ts:1416,1439,1483,2261,2598

### The current stream path buffers whole ranges and cannot resume — UrlSource can
`streamInput()` (web/src/pipeline/remuxJob.ts:95-119, the path taken for torrents via upload.ts:281-283) does `fetch(url, {headers:{Range}})` with no signal, then `await response.arrayBuffer()` (remuxJob.ts:101) — the whole range is buffered before mediabunny sees a byte — and throws on a short read (`helper short read`, :103). The same shape exists in localHelper.ts:215-225. That contract is fine on loopback and wrong over WAN: no incremental delivery, no abort, and any truncated response is fatal. mediabunny's UrlSource, by contrast: streams the body chunk-by-chunk into the cache (source.ts:1053), aborts the fetch the instant `currentPos >= targetPos` (:1005-1009), and on a body that ends early re-issues a new Range request from `currentPos` (:1041-1049, "the server decides to cap range requests arbitrarily... let's fetch the rest using a new request"), and on a mid-stream reader error waits `getRetryDelay(1, ...)` and resumes (:1015-1030). It also carries a 64 MiB default cache vs CustomSource's 8 MiB, and a `parallelism` option (default 2). Recommendation: build the torrent source as a UrlSource, not a hand-rolled CustomSource.
sources: web/src/pipeline/remuxJob.ts:95-119; web/src/localHelper.ts:215-225; web/node_modules/mediabunny/src/source.ts:1005-1053,700-704

### UrlSource's CORS heuristic is disabled inside a Web Worker → infinite retry on a CORS misconfig
DEFAULT_RETRY_DELAY (source.ts:632-670) only decides a failure is unrecoverable-CORS when `typeof window !== 'undefined'`. The remux runs in a dedicated Web Worker (web/src/pipeline/remuxWorker.ts), where `window` is undefined — so the heuristic never fires and the default backoff `Math.min(2**(attempts-2), 16)` retries forever, capped at 16s. A misconfigured `Access-Control-Allow-Origin` on the torrent worker would therefore present as a room that silently never prepares, with no error surfaced through remuxWorker.ts's `classify()` (:64-72). Note the flip side is fine: `!response.ok` throws immediately without retrying (source.ts:922-925), so a 401/403/410 from the worker fails fast and cleanly. Mitigation: always pass a custom `getRetryDelay` that gives up after N attempts.
sources: web/node_modules/mediabunny/src/source.ts:632-670,922-925; web/src/pipeline/remuxWorker.ts:1-10,64-72; web/node_modules/mediabunny/src/misc.ts:572-611

### Read pattern the worker will actually see
With `prefetchProfile: 'network'` (already chosen at remuxJob.ts:116 and mediaInput.ts:50) the profile pads the start back to a 64 KiB boundary, enforces a 512 KiB minimum load (`URL_SOURCE_MIN_LOAD_AMOUNT`, source.ts:632), and on detected sequential access grows the read region exponentially up to 8 MiB extensions (source.ts:1864-1909). So the worker sees: a ~512 KiB head read (format sniffing / `canRead()`), a tail read (MKV Cues / MP4 moov — mediaInput.ts:2-7 documents exactly this), then increasingly long sequential reads capped at 8 MiB growth steps, at most 2 concurrent (CustomSource fixed `maxWorkerCount: 2`; UrlSource `parallelism` default 2, configurable). Separately, the MKV subtitle pass reads the ENTIRE file sequentially in 8 MiB slices through `input.read` (remuxJob.ts:184-190, SUBTITLE_SLICE_BYTES at :26), bypassing mediabunny's cache — a second full-file reader running concurrently with the remux, for every .mkv (isMatroska, subtitles.ts:93-95). Over WAN that forces the whole torrent down even if the room watches ten minutes, and it competes with the playhead for piece priority.
sources: web/node_modules/mediabunny/src/source.ts:1864-1909; web/src/pipeline/remuxJob.ts:26,116,184-190; web/src/pipeline/mediaInput.ts:2-7,50; web/src/subtitles.ts:93-95

### Why HTTP/2 on the worker matters (it is not about the 6-connection limit)
mediabunny caps itself at 2 concurrent reads, so HTTP/1.1's per-origin 6-connection limit is never the binding constraint and h2 multiplexing buys nothing there. The real argument is abort economics. UrlSource aborts its own response the moment it has enough bytes (source.ts:1005-1009) and that happens constantly under the exponential prefetch. On HTTP/1.1, a cancelled response leaves unread body on the socket; Chromium's HttpResponseBodyDrainer will only drain it to reuse the socket with `kDrainBodyBufferSize = 16384` and `kTimeoutInSeconds = 5` — beyond that "we may as well just create a new socket", i.e. a fresh TCP+TLS handshake (2-3 RTT ≈ 300-450ms at 150ms RTT) on every overshoot and every seek. On h2 (RFC 9113 §5.4.2/§6.4) the same cancel is one RST_STREAM on a connection that stays warm. Second-order: Chrome advertises a ~6 MiB initial stream window while Firefox advertises 128 KiB — at 150ms RTT that is roughly a 7 Mbit/s per-stream ceiling in Firefox, so for WAN reads bump UrlSource `parallelism` above the default 2 and measure. Serve ALPN h2 with http/1.1 fallback.
sources: https://chromium.googlesource.com/chromium/src/+/HEAD/net/http/http_response_body_drainer.h; https://chromium.googlesource.com/chromium/src/+/HEAD/net/docs/life-of-a-url-request.md; https://datatracker.ietf.org/doc/html/rfc9113; web/node_modules/mediabunny/src/source.ts:1005-1009

### Abort/disconnect semantics the Rust worker must implement (the bridge never had to)
On the wire: browser `AbortController.abort()` or tab close → h2 RST_STREAM(CANCEL) (or TCP FIN/RST on h1). In axum/hyper this surfaces as the response body future being dropped — hyper stops polling the body and drops it; there is no callback, so the retraction must live in a `Drop` guard on the reader session (or a `tokio::select!` on a cancellation token). The contract must state: dropping the response body means "this reader is gone — release its piece window and its bandwidth reservation immediately", and it is a normal event, not an error to log at warn. The ss-bridge contract specified none of this because it never happened: localHelper.ts:215-225 and remuxJob.ts:99-104 issue fetches with no `signal` and consume them with `arrayBuffer()`, so the Rust side literally never saw a client cancel, and the only teardown signal was the explicit `POST /close` on session destroy (localHelper.ts:283-288, `keepalive: true`).
sources: https://github.com/tokio-rs/axum/discussions/1094; web/src/localHelper.ts:215-225,283-288; web/src/pipeline/remuxJob.ts:99-104

### Credential rotation collides with UrlSource's immutable URL — use fetchFn
A UrlSource holds one URL for the life of the Input, and ss holds one Input for the life of the room (clientMedia.ts:82 → :485 across every region). A short-TTL token baked into that URL therefore expires mid-remux with no way to rotate it short of tearing down the pipeline — and a 3-hour movie remux over a slow swarm can outlive any sane TTL. The clean escape hatch already exists: `UrlSourceOptions.fetchFn` (source.ts:706-710), a WHATWG-compatible fetch the caller supplies. Wrap it to rewrite the ticket into the URL per request from a live variable the page refreshes over the existing room WebSocket. That keeps UrlSource's streaming + resume + self-abort behaviour while making the credential rotatable, and it is also where the `prio=` hint and a custom `getRetryDelay` belong.
sources: web/node_modules/mediabunny/src/source.ts:706-710; web/src/pipeline/clientMedia.ts:82,485

### Viewers never touch the worker — confirmed in the repo
`Player.tsx:203` builds exactly one media source for host and viewer alike: `/media/${room.id}/hls/master.m3u8?g=…&v=…`. That route is served by the Go API (`internal/httpapi/media.go:27`), whose doc comment states it outright: "Only playlists come from here. Segments, init files and subtitles are delivered straight from the bucket, so the bytes a viewer downloads never cross this machine." The playlists are rewritten against `cfg.MediaPublicURL` before being stored (`internal/httpapi/clientmedia.go:418`, `media.RenderClientPlaylist`), so every segment URI a viewer resolves points at R2. Nothing in web/src outside the host upload path (upload.ts:281-283 → remuxJob streamInput) ever constructs a torrent stream URL — `streamUrl` appears only in torrent.ts:16,26, localHelper.ts:235,250 and upload.ts:281-289. The worker's CORS policy can therefore be pinned to "host session only"; there is no viewer case to accommodate.
sources: web/src/player/Player.tsx:203; internal/httpapi/media.go:17-27; internal/httpapi/clientmedia.go:397-420; web/src/upload.ts:281-289

### TLS is now mandatory and IP-only certs are possible
The loopback exemption ss relies on today disappears with the worker. A page on https://ss.giuli.dev may fetch `http://127.0.0.1:32227` because loopback is "potentially trustworthy", but `http://<public-ip>` is plain mixed content and is blocked. So the worker must terminate TLS. Two options: (a) a DNS name per worker under a wildcard the instance owner controls (`*.w.ss.giuli.dev`, DNS-01) — recommended, since it survives IP changes and keeps the certificate lifecycle off the worker's critical path; (b) a Let's Encrypt IP-address certificate, generally available since 2026-01-15, IPv4 and IPv6, but only under the `shortlived` profile (160-hour / ~6-day lifetime), which means renewal roughly every 2-3 days and a hard dependency on the worker's ACME loop staying healthy. A side benefit of leaving loopback: the entire Local Network Access permission dance in localHelper.ts:101-189 (the `local-network-access` permission query, the 90s prompt timeout, the gated `helperAvailable`) is deleted outright.
sources: https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability; https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content; web/src/localHelper.ts:101-189

### CONTRACT SKETCH — worker data plane v1
ORIGIN: https://{worker-id}.w.{instance-domain}, ALPN h2 then http/1.1.

(1) GET /v1/f/{ticket} — the only byte endpoint. `ticket` = base64url(payload)'.'base64url(sig), payload = {v, roomID, infohash, fileIndex, size, aud (instance origin), iat, exp, epoch}, signed with the same Ed25519 key that signs job envelopes (worker already verifies it). Path-embedded, never a header. Optional query `?prio=head|playhead|scan` and `?gen=N` (query, not header, to stay preflight-free).
  Request: only `Range: bytes=N-` or `bytes=N-M` (safelisted). credentials omitted; no cookies, no custom headers.
  200 — only when no Range was sent (mediabunny treats this as "no range support" and degrades to a sequential, evict-as-you-go mode, source.ts:966-999). Avoid.
  206 — Content-Range: bytes N-M/size; Content-Length: exact bytes in THIS response; Content-Type: application/octet-stream; Accept-Ranges: bytes; Cache-Control: no-store. Headers MUST be sent as soon as the first byte is obtainable, body streamed as pieces land — never buffer the range.
  416 — start >= size, with `Content-Range: bytes */{size}` (RFC 9110 §14.4, §15.5.17).
  401 bad signature / 403 wrong audience or revoked epoch / 404 unknown infohash or fileIndex / 410 job retired / 429 too many readers / 503 + Retry-After while draining. All of these are terminal for mediabunny (`!response.ok` throws without retry), which is the desired behaviour.
  504 — first byte not obtainable within T_first (~30s). Body-side stall: if no byte for T_stall (~20s), END the body early rather than hanging; UrlSource re-requests from currentPos.
  Server-side length cap: answer an open-ended `bytes=N-` with at most 16 MiB and an honest Content-Length + Content-Range; UrlSource issues a follow-up request for the rest (source.ts:1041-1049). This is what stops one response from pinning a piece window for the whole file.
  CORS on EVERY response including 4xx/416: `Access-Control-Allow-Origin: {aud from ticket}` (exact origin, not *), `Vary: Origin`, `Access-Control-Expose-Headers: Content-Range, Accept-Ranges, X-SS-Piece-Ready-To`, no Access-Control-Allow-Credentials.

(2) HEAD /v1/f/{ticket} — size probe, same CORS. Not used by mediabunny (size comes from the signed job) — keep for ops.

(3) OPTIONS /v1/f/{ticket} — defensive preflight answer for anything that ever does preflight: `Access-Control-Allow-Methods: GET, HEAD, OPTIONS`, `Access-Control-Allow-Headers: Range`, `Access-Control-Max-Age: 600` (larger is clamped by Safari anyway).

(4) POST /v1/hint/{ticket} — the seek/retract channel, and the load-bearing part of this design, because the browser CANNOT cancel an in-flight mediabunny read. Body `{"playheadByte":N,"gen":G,"dropBefore":M}` sent with `Content-Type: text/plain;charset=UTF-8` (a JSON content-type would trigger a preflight) and `keepalive: true`, fire-and-forget from clientMedia.ts's restartAt(). The worker moves the piece window to N, cancels priority for the abandoned region, and stops feeding any still-open response whose gen < G (end its body early; the client discards it anyway).

(5) Priority classes: `prio=head` (format sniff / tail read — tiny, highest urgency, must not disturb the playhead window), `prio=playhead` (the remux), `prio=scan` (the MKV subtitle sweep, remuxJob.ts:184-190) — scan reads must be served strictly behind playhead reads and ideally only from pieces already on disk.

(6) Lifecycle: reader session keyed by (ticket, infohash, fileIndex), NOT by connection. On body drop / RST_STREAM, retract priority but hold the window for a ~30s grace period so a reconnect after a network change resumes warm. h2 PING every 20-30s; idle timeout >= 5 min. Ticket lifetime must exceed the whole remux (hours) or be rotated via UrlSourceOptions.fetchFn; revoke through the control-plane epoch, not through short TTLs.

(7) Concurrency budget: expect <= 2 concurrent reads per file from the remux plus 1 from the subtitle sweep. Cap at ~4 and answer 429 above that.
sources: https://www.rfc-editor.org/rfc/rfc9110.html; https://datatracker.ietf.org/doc/html/rfc9113; web/node_modules/mediabunny/src/source.ts:966-1053; web/src/pipeline/clientMedia.ts:424-441

RECOMMENDATIONS:
- Auth: capability ticket embedded in the URL PATH (`/v1/f/{ticket}`), Ed25519/HMAC-signed by the instance, scoped to (roomID, infohash, fileIndex, audience origin, epoch). Not an Authorization header (preflight per request, not covered by ACAH `*`, poorly cached — whatwg/fetch#1278), not a query string (path keeps it out of naive access-log query redaction gaps and makes the URL a stable single string). Pin `Access-Control-Allow-Origin` to the ticket's audience rather than `*`, so a leaked ticket is not usable from an arbitrary page.
- Replace the hand-rolled `streamInput` CustomSource (web/src/pipeline/remuxJob.ts:95-119) with mediabunny `UrlSource` for the torrent path, configured `{ fetchFn, getRetryDelay, parallelism: 4, maxCacheSize: 64-128 MiB }`. That buys incremental body delivery, automatic resume of truncated 206s, self-aborting requests, and ticket rotation via fetchFn — all of which the current `await response.arrayBuffer()` path cannot do.
- MUST supply a custom `getRetryDelay` that gives up after ~6 attempts: mediabunny's default CORS bail-out is gated on `typeof window !== 'undefined'` and the remux runs in a Web Worker, so a CORS misconfiguration currently retries forever at a 16s cap instead of failing the room.
- Add the out-of-band `POST /v1/hint` playhead/retract call and wire it into `restartAt()` in web/src/pipeline/clientMedia.ts:424-441, right where the upload aborts already fire. This is not an optimization — it is the only mechanism by which a seek can retract piece priority, because mediabunny exposes no per-read cancellation and ss never disposes the shared Input.
- Alternatively/additionally, consider calling `Input.dispose()` and rebuilding the Input on region restart. It is the only supported way to abort mediabunny's in-flight reads (source.ts:2590-2600) — the cost is losing the read cache and re-sniffing the container on every seek, so measure before choosing it over the hint endpoint.
- Serve h2 (rustls ALPN h2 + http/1.1 fallback). The motivation is that UrlSource self-aborts constantly and an HTTP/1.1 cancel with >16 KiB of body left forces Chrome to drop the socket (kDrainBodyBufferSize=16384, 5s), paying a full TCP+TLS handshake per seek/overshoot.
- Stream 206 bodies and cap each response at ~16 MiB with an honest Content-Range; add a first-byte deadline (~30s → 504) and a mid-stream stall deadline (~20s → end body early). Never let a range read block indefinitely: with maxWorkerCount 2 and LRU eviction refusing workers with pending slices, one stuck read starves the whole pipeline.
- Expose `Content-Range` (mandatory once responses are length-capped) and `Accept-Ranges` (cosmetic) via Access-Control-Expose-Headers; do not bother exposing Content-Length (already safelisted). Emit CORS headers on 4xx and 416 too, or the browser reports a generic CORS failure instead of the real status.
- Add a `prio=` query parameter and treat the MKV subtitle sweep (remuxJob.ts:184-190, a full sequential read of the entire file, concurrent with the remux) as a distinct low-priority class — otherwise every .mkv room forces a complete torrent download and steals swarm bandwidth from the playhead.
- Prefer a DNS name per worker under a wildcard (`*.w.<instance-domain>`, DNS-01) over a Let's Encrypt IP certificate. IP certs are GA since 2026-01-15 but are locked to the `shortlived` profile (160h), which makes every worker's ACME loop a availability dependency on a ~2-day cadence.
- Delete the entire Local Network Access path in web/src/localHelper.ts:101-189 with the bridge — the permission query, the 90s prompt timeout, and the availability gate all exist purely because the helper sat on loopback.

OPEN_QUESTIONS:
- Should the seek path dispose and rebuild the mediabunny Input (true cancellation, cold cache, re-sniff cost) or keep one Input and rely on the out-of-band hint endpoint (warm cache, but the abandoned read runs to completion)? Needs a measurement of how long a stale 8 MiB read actually takes to drain over WAN before choosing.
- How long can a ticket live? The remux of a long film over a slow swarm can run for hours and UrlSource cannot rotate its URL by itself. The fetchFn wrapper solves it mechanically, but the epoch/revocation semantics on the worker (how fast a revoked room stops being readable) still need a number.
- Firefox's 128 KiB h2 stream window may cap a single read stream around 7 Mbit/s at 150ms RTT. Does raising UrlSource `parallelism` to 4-6 actually recover throughput, or does it just fragment the piece window and hurt the swarm? Needs a real test against a VPS.
- The MKV subtitle sweep's whole-file read is a product question as much as a protocol one: is it acceptable to force a full torrent download for subtitles, or should it be bounded (first N minutes / only pieces already downloaded) once the bytes cross a WAN?
- Does the worker need HEAD at all, or is the file size always authoritative from the signed job? If a torrent's metadata disagrees with the ticket's `size`, which one wins, and what status does the mismatch produce?
- Nothing was verified about how many rooms one worker serves concurrently, so the 429 threshold and the per-reader bandwidth reservation in the contract are placeholders.

SUMMARY: The debrid industry (Real-Debrid, TorBox, AllDebrid, Premiumize, Offcloud) has already standardised the exact API shape this product needs — add magnet by infohash, select files (which gates the download), poll status, mint an HTTPS link — and the entire ecosystem downstream of it (Stremio addons, zurg/rclone mounts) is built on plain ranged GETs against those links, which is precisely the access pattern mediabunny's CustomSource wants. What none of them do is stream a torrent that is still downloading: TorBox streams only at "Download Ready", Real-Debrid's product IS the completed-file cache, Premiumize deprecated its stream link, and the seedbox stack can't do it at all because nginx has no piece priority. Only self-hosted/niche tools cross that line — TorrServer, webtor.io's torrent-web-seeder, Tiramisu, Seedr — and webtor.io in particular is the closest existing product (browser + magnet + server-side swarm + HTTPS, open source, k8s job per infohash, JWT-scoped URLs), differing mainly in that it burns CPU on server-side FFmpeg-to-HLS where ss.giuli.dev copy-remuxes in the host's browser for free. The certificate question has a known good answer in Plex's plex.direct: a controlled DNS zone plus a per-server-scoped certificate, so a leaked key can impersonate only one node — adapt it as per-worker Let's Encrypt via DNS-01, watching the 50-certs-per-registered-domain-per-week cap. The real implementation hazard is CORS, not TLS: the worker must expose Content-Range/Accept-Ranges/Content-Length and keep auth in the signed URL so single-range GETs stay preflight-free, which is exactly where Stremio Web fails today. Infohash-level dedup is the debrid category's whole economic engine (TorBox keeps every torrent 30 days shared across all users; DMM crowdsources RD's cache index), and it transfers cleanly to a worker fleet — but Real-Debrid's history under FNEF pressure, from the Nov 2024 API shutdown to the 2026 keyword filters that cost users 50–70% of their libraries, is the argument for building blocklist-at-intake abuse handling now and for making self-hosting a first-class escape hatch.

### Debrid API shape is a 4-call state machine you should copy verbatim

API is rate-limited to 250 req/min, 429 on excess. TorBox is the same shape with better naming: POST /v1/api/torrents/createtorrent (magnet or .torrent), GET /v1/api/torrents/checkcached?hash=a,b,c&format=object&list_files=true (~100 hashes/request), GET /v1/api/torrents/requestdl?token=&torrent_id=&file_id=&user_ip=&redirect=true. Premiumize: POST /api/cache/check, /api/transfer/create, /api/transfer/directdl (returns content[] of {path, size, link}, no cloud storage). AllDebrid: uploadMagnet / statusMagnet / unlockLink / streamingLink. Offcloud: POST /api/remote?key=, /api/remote/status, GET /api/cloud/explore/{requestId}. Every one of them separates "register the torrent (by infohash/magnet)" from "pick the file" from "mint a byte-serving URL" — which is exactly the split your signed-job envelope + worker Range endpoint needs.

### The link model: short-lived mintable URL + long-lived permalink that redirects
TorBox is the cleanest published design and is directly copyable for worker URLs: the CDN link itself is NOT permanent (3 hours to *start* the download; once started you have "nearly unlimited time" to finish), and instead of re-requesting, clients build a *permalink* — the requestdl endpoint with redirect=true, which 302s to the current CDN link. Invalidation is coarse: rotate the API token or delete the item. Real-Debrid links are valid 30 days with no uptime guarantee; the account (not the link) is the IP-scoped thing — RD permits use from any public IP but not two public IPs simultaneously. TorBox's requestdl takes a user_ip parameter, i.e. the client's IP is an explicit input to link minting (geo/CDN routing and/or lock). Design lesson: give the browser a stable, signed worker URL that 302s to a short-TTL byte-serving URL, rather than embedding a long-lived credential in a <video src>.
sources: https://github.com/TorBox-App/torbox-sdk-py/blob/main/documentation/services/TorrentsService.md; https://github.com/debridmediamanager/awesome-debrid/discussions/7

### Range support is universal and load-bearing — the whole debrid ecosystem is built on it
Debrid download links are plain HTTPS with byte-range support, which is what makes zurg+rclone work: zurg exposes the RD library as WebDAV, rclone mounts it, and "every read becomes a ranged HTTP GET against the provider's CDN at the moment a player asks for those bytes" — a 60 GB remux costs zero local disk. Stremio relies on the same: "HTTP Range Requests provide full seeking support for all streams." This is precisely the access pattern mediabunny's CustomSource needs, so a worker that speaks correct 206/Content-Range is API-compatible with an entire existing tooling ecosystem (rclone, Infuse, Plex, Jellyfin, VLC) for free — worth preserving even though your primary consumer is the browser.
sources: https://github.com/debridmediamanager/zurg-public; https://guides.viren070.me/stremio/technical-details; https://deepwiki.com/debridmediamanager/zurg-testing/2.1-webdav-configuration

### CONFIRMED GAP: no commercial debrid streams a still-downloading torrent. They all wait for completion
TorBox explicitly streams only once a file reaches "Download Ready" status — streaming during the active downloading phase is not offered. Real-Debrid's entire value proposition is the *cache*: if the infohash isn't already on their storage servers you wait for the full download before you get a link (uncached torrents changed the API response shape and broke clients). Premiumize deprecated stream_link entirely and now just returns the same completed-file link. The seedbox world has the same gap for mundane reasons: qBittorrent's "append .!qB to incomplete files" hides them from Jellyfin, hardlinked still-seeding files fail to play, and nginx has no concept of piece priority — it can only serve bytes that already exist on disk. So the free-seek-during-download capability is a genuine differentiator, not a commodity.
sources: https://support.torbox.app/en/articles/9928977-download-statuses; https://github.com/rogerfar/rdt-client/issues/545; https://www.premiumize.me/api; https://github.com/jellyfin/jellyfin/issues/11552; https://github.com/qbittorrent/qBittorrent/issues/24239

### The exceptions that DO stream mid-download — TorrServer, webtor.io, Seedr, Tiramisu/GoStream
TorrServer (Go, anacrolix/torrent) serves /stream/{fname} and /play/{hash}/{id} over HTTP(S) with Range, using http.ServeContent so the reader's Seek() drives piece prioritisation; it sets reader.SetResponsive() and adjusts readahead by piece length, and preloads with dual readers — head up to PreloadSize plus a minimum 8 MB tail reserve so the MP4 moov atom / MKV cues are present before playback. It tracks an activeStreams atomic counter for concurrency. This is your piece-scheduling playbook already shipped in production, and the 8 MB tail pin is a concrete number to copy. Webtor's torrent-web-seeder does the same with mmap-backed piece storage, per-torrent LRU eviction (--per-torrent-cache-budget default 50 GB) and --max-readahead default 20 MB, serving /<infohash>/<path> with Range while still downloading. Tiramisu (ex-GoStream) does it via FUSE rather than HTTP — every byte served live from the swarm on demand, no temp files — and markets itself literally as "Forget Real-Debrid". Seedr markets stream-while-downloading to consumers. None of these are debrid services; all are self-hosted or niche.
sources: https://deepwiki.com/YouROK/TorrServer/3.8-streaming-and-playback; https://github.com/YouROK/TorrServer; https://github.com/webtor-io/torrent-web-seeder; https://github.com/MrRobotoGit/tiramisu

### webtor.io is the closest existing product to ss.giuli.dev — and it is open source
Same shape: paste a magnet in a browser, servers join the swarm, bytes come back over HTTPS, video plays with zero install and the user's home IP never enters the swarm. Architecture (Go, ~10 microservices on Kubernetes, 100+ concurrent download/transcode jobs): rest-api (POST /resource stores a magnet/torrent → resource_id; GET /resource/{id}/list; GET /resource/{id}/export/{content_id} → export variants with URLs), torrent-store (gRPC metadata), magnet2torrent, torrent-web-seeder (per-infohash HTTP Range server), content-transcoder (HTTP stream → HLS), and torrent-http-proxy. The proxy is the interesting part for you: it routes /{infohash}/{path} to a Kubernetes Job spawned on demand with the infohash injected as an env var, waits for readiness, then proxies; it supports "matryoshka" service chaining via tilde syntax (/{hash}/Sintel.mp4~hls/index.m3u8 spawns transcoder → seeder) and JWT token auth (--jwt-secret). The JS SDK takes apiKey OR tokenUrl + tokenRenewInterval + a getToken() callback — i.e. short-lived browser tokens renewed on a timer, not a long-lived key in the page. There is also an all-in-one self-hosted Docker image (port 8080, embedded Postgres, /data + /pgdata volumes, autocleaner for old data, DISABLE_VIDEO_TRANSCODING, DOMAIN=https://...). Crucial difference to exploit: webtor transcodes to HLS server-side with FFmpeg (CPU-expensive, per-viewer), whereas your host's browser copy-remuxes for free.

### The certificate problem is already solved by Plex, and the pattern maps onto your worker fleet exactly
Plex's plex.direct: a dynamic-DNS zone where any IP is encodable as a hostname — 1-2-3-4.<hash>.plex.direct resolves to 1.2.3.4 — combined with a per-server wildcard certificate for *.<hash>.plex.direct, where <hash> is derived from the server identity. Because the cert only covers that one server's hash-labelled subtree, handing the private key to the server operator is safe: a leaked key can impersonate only that server, on any IP. The client connects to https://1-2-3-4.<hash>.plex.direct:32400. For your workers (public IPs, unlike Plex's LAN case, so no DNS-rebinding-protection problem) this becomes: worker-<id>.workers.ss.giuli.dev, an A record you control, and either (a) per-worker Let's Encrypt certs the worker obtains itself via DNS-01 against your zone (worker never needs port 80/443 pre-provisioned, and DNS-01 is the only option for wildcards), or (b) one wildcard *.workers.ss.giuli.dev issued centrally and pushed to workers — simpler but a single leaked key impersonates the whole fleet, which is the tradeoff Plex deliberately avoided. Watch the Let's Encrypt cap: 50 new certs per registered domain per 7 days (token-bucket, global across ACME accounts), renewals exempt but capped at 5 duplicate certs/week. A fleet of two VPSes is nowhere near it; a self-hoster fleet per-instance-domain is also fine, but a shared ss.giuli.dev issuing per-worker certs for many self-hosters would hit it — another argument for self-hosters using their own domain.
sources: https://words.filippo.io/how-plex-is-doing-https-for-all-its-users/; https://notes.billmill.org/programming/DNS/How_plex_is_doing_HTTPS_for_all_its_users.html; https://letsencrypt.org/docs/rate-limits/; https://letsencrypt.org/2025/01/30/scaling-rate-limits.html

### CORS is the thing that will actually break the browser→worker data plane
Debrid links work in Stremio's *desktop* player, which is not a browser origin. Stremio Web is a different story: it cannot run the P2P streaming server, relies on HTTP/debrid links, and users repeatedly hit CORS and mixed-content failures ("Video is not supported") when pointing it at a self-hosted streaming server; localhost is the only origin browsers exempt from mixed-content, so LAN servers need real TLS, and the standard fix is "Let's Encrypt + nginx in front of the server." Your worker must therefore serve: Access-Control-Allow-Origin for the instance origin, and Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length — otherwise mediabunny's CustomSource can read the body but cannot see the range/length metadata it needs. A single-range Range: bytes=500-999 is CORS-safelisted and does NOT preflight; multi-range requests and any custom auth header DO preflight, so keep auth in the URL (signed path/query) rather than an Authorization header if you want to avoid an OPTIONS round-trip per seek.
sources: https://github.com/Stremio/stremio-web/issues/588; https://github.com/tsaridas/stremio-docker/issues/54; https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Range; https://github.com/bilibili/flv.js/blob/master/docs/cors.md

### Infohash-level dedup is the entire economic engine of debrid — and it is a cache, not storage
TorBox: a torrent downloaded to any account is kept at least 30 days, and if anyone else adds the same torrent in that window their download is instant; all download types (torrent/web/usenet) are cached. Real-Debrid's cache is described by the community as synonymous with their storage servers — "every content that users download is stored so that when another user requests it, it's not redownloaded again." The whole Stremio-addon ecosystem is built on querying that shared cache before offering a stream. The dedup is one-directional value: the marginal cost of the Nth user of a popular infohash is egress only, not swarm bandwidth or wall-clock. Debrid Media Manager went so far as to crowdsource a cache-availability index from users' own "instantly turned 100%" observations, and to deliberately re-touch hashes to keep them from being evicted — evidence that cache retention policy is the most user-visible knob in the whole product.
sources: https://support.torbox.app/en/articles/9923071-how-does-the-torbox-cache-work; https://deepwiki.com/debridmediamanager/debrid-media-manager/1.1-features-and-capabilities; https://www.patreon.com/posts/faq-116666686

### Pricing and egress economics: debrid sells slots, not bytes; and VPS egress is ~90x cheaper than hyperscaler
TorBox: Free / Essential $3 / Standard $5 / Pro $10 per month, with NO storage or bandwidth caps — segmentation is by concurrent slots (1/3/5/10 active transfers), per-torrent size (10 GB / 200 GB / 200 GB / 1 TB), seeding time (none / none / 2 weeks / 30 days) and add-frequency (free tier: 1 download per 24h, 10/month). That is why this product shape is viable on two owner-operated VPSes and would be ruinous on a hyperscaler, and why the pricing lever to copy is concurrency slots + per-job size caps rather than metered GB.

### Legal posture: the API is the first thing to die, and it dies by infohash/keyword filter
Nov 2024: after a formal notice from the FNEF (French Federation of Film Distributors), which had already litigated file-hosts in the Paris Judicial Court, Real-Debrid deployed hash filtering against torrent hashes named in Paris lawsuits, keyword filters (admitted false positives), blocking of cyberlockers on the USTR Notorious Markets and EU Piracy Watchlist, purging of all matching cached files, and deactivation of api.real-debrid.com — which killed /torrents/instantAvailability and with it every Stremio/Kodi/Plex debrid addon overnight. Webtor's posture is the lighter-weight template for a small operator: screen incoming torrents against a continuously-updated abuse blocklist at intake (rejected torrents are never stored, indexed or served), block already-known illegal infohashes at playback, and on a confirmed report permanently block the infohash with cascading removal across the service.

### What the zero-install crowd already accepts (Stremio + Torrentio), and what it doesn't
The Stremio stream object is minimal: {url} for a direct http(s) link, or {infoHash, fileIdx} for a torrent, plus behaviorHints — notWebReady ("does not support https or is not an MP4 file", forces a different playback path), proxyHeaders (request/response headers the player must inject; requires notWebReady: true), bingeGroup (auto-select the same source for the next episode), videoSize and filename (fed to subtitle matching and buffering). Debrid addons simply return a plain HTTPS {url}; the player does a direct ranged GET. Users demonstrably accept: paying a third party ~$3–5/month, an account that can only be used from one public IP at a time, links that expire, and a service that can and does delete their library for legal reasons. What they do NOT accept is installing a local daemon — that is exactly the friction Stremio Web tries to remove and fails at, because in a real browser origin CORS and mixed content bite. Your product's wedge is the intersection: browser origin + no daemon + streams while downloading.

### Self-hosted torrent-streamers exposed on public VPSes are secured with, at best, HTTP basic auth
TorrServer's guidance is -a/--httpauth (TS_HTTPAUTH in Docker, accounts in accs.db). cloud-torrent offers optional basic auth via --auth user:password / AUTH env var — optional, so instances routinely sit on a public IP:port with no auth at all. This is the state of the art you are replacing, and it is weak in the ways that matter for your threat model: a shared static credential, no per-job scoping, no way to bound what an authenticated client may fetch, and no revocation short of restarting with a new password. Your signed-job envelope (Ed25519, jobs carry infohash never URL) plus per-room short-TTL URL signing is a real improvement over every deployed alternative, and worth saying so in the product's security page.

RECOMMENDATIONS:
- Copy the debrid API state machine verbatim for the worker control plane: register-by-infohash → list files → select file → mint URL. The selectFiles-gates-the-download rule from Real-Debrid is worth keeping: don't start pulling pieces until the room has actually chosen a file, and use that same gate to enforce video-torrents-only (reject at intake, like webtor's blocklist, not at playback).
- Adopt TorBox's two-tier link model rather than a single long-lived URL: a stable signed permalink on the instance (or the worker) that 302s to a short-TTL byte-serving URL, with invalidation by rotating the room/worker key. It survives token expiry mid-playback without the browser holding a credential, and it keeps the redirect target swappable if the job migrates to another worker.
- Solve certs with the Plex plex.direct pattern, adapted: give each worker a hostname in a zone you control (worker-<id>.workers.<instance-domain>) and have the worker obtain its OWN Let's Encrypt cert via DNS-01 with a narrowly-scoped credential, so no private key ever leaves the box. Prefer this over a fleet-wide wildcard; the whole reason Plex hashed the subtree was so handing out the key stayed safe. Budget against the 50-certs-per-registered-domain-per-7-days cap and note renewals are exempt.
- Make CORS a first-class part of the worker's HTTP contract, not an afterthought: Access-Control-Allow-Origin for the instance origin plus Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length, and keep authentication in the signed URL path/query so single-range GETs stay CORS-safelisted and never preflight. Every seek that triggers an OPTIONS round-trip is latency you don't need.
- Steal TorrServer's concrete buffering constants as your starting point rather than deriving them: responsive reader mode with readahead scaled to piece length, head preload, and a minimum 8 MB tail pin so the MP4 moov / MKV cues are resident before the first read. Webtor's numbers are a second data point (20 MB max readahead, 50 GB per-torrent cache budget with LRU piece eviction).
- Lead the product on the capability nobody sells: TorBox, Real-Debrid and Premiumize all require a completed download before they hand you a link, and the seedbox stack physically cannot do better because nginx has no piece priority. "Seek anywhere while it's still downloading" is a defensible differentiator against the entire debrid category, and against Stremio+Torrentio's dependence on someone else's cache.
- Do NOT copy webtor's server-side FFmpeg-to-HLS transcode. That is their biggest per-viewer cost (100+ concurrent transcode jobs on a k8s cluster) and your architecture already avoids it by copy-remuxing in the host's browser. Keep the worker dumb: pieces in, bytes out over Range, nothing else. It keeps the worker cheap enough to run two of them on VPS-class hardware and makes the self-hosted worker a small, auditable binary.
- Design the fleet cache as an explicit, short, documented retention policy modelled on TorBox's 30 days, with LRU eviction under a disk budget and a re-download fallback. Publish it — DMM's existence proves users will build tooling against cache retention behaviour whether or not you document it, and a documented policy is cheaper than an undocumented one being reverse-engineered.
- Build the abuse posture in from day one along webtor's lines rather than Real-Debrid's: blocklist screening at intake so rejected infohashes are never stored, playback-time blocking of known-bad hashes, and permanent cascading infohash removal on a confirmed report. Real-Debrid's history is the cautionary tale — under FNEF pressure they killed the public API first, and the 2026 keyword filters (targeting [rarbg], WEB-DL, AMZN) cost users 50–70% of their libraries. A self-hostable product whose users own their own workers is structurally less exposed to that outcome, and that should be stated as a feature.
- Price on concurrency slots and per-job size caps, not on metered GB — that is what TorBox does and it maps directly to what a worker fleet actually runs out of (active torrent slots, disk, wall-clock), not to what egress costs on a Hetzner-class box where 20 TB is included and overage is ~€1/TB.

OPEN_QUESTIONS:
- Does the worker keep completed files as a cache, and for how long? TorBox's answer is 30 days shared across all users; for a two-VPS fleet the binding constraint is disk, not policy. Unresolved: whether cache entries are per-instance or shared across self-hosted instances (sharing infohash availability across instances is the debrid superpower, but it also makes the owner's fleet an index of what everyone is watching — a liability given the RD/FNEF precedent).
- Should the browser talk to a worker directly (Plex-style per-worker cert) or through the instance as a reverse proxy? Direct is the whole point (egress off the API box), but it leaks worker IPs to every viewer's browser devtools and makes the workers individually addressable for abuse complaints and blocklisting. TorrServer's answer is to block the read; whether that is acceptable inside mediabunny's CustomSource (which may not tolerate a multi-second read) is untested.
- Whether to expose the worker's Range endpoint as a WebDAV/plain-HTTP surface as well. It would make the fleet instantly compatible with rclone/Infuse/Plex (the zurg ecosystem) at zero cost, but it also turns the product into a debrid service in the eyes of a rightsholder, which is precisely the framing that got RD's API killed.
- No source found confirming whether Real-Debrid or TorBox links are hard-locked to the requesting IP. RD's documented restriction is on the account, and TorBox's requestdl takes user_ip as an input, but neither documents rejecting a mismatched IP on the byte-serving request.

### Two rooms, one torrent, two read heads: TorrentStreams is built for this
librqbit supports arbitrarily many concurrent FileStreams on one ManagedTorrent. `ManagedTorrent::stream(self: Arc<Self>, file_id) -> anyhow::Result<FileStream>` (torrent_state/streaming.rs:337) registers a StreamState in a DashMap<StreamId, StreamState> keyed by a monotonic id; `TorrentStreams::iter_next_pieces` (streaming.rs:72-102) builds one 32MB-ahead queue per live stream, SHUFFLES the queues (`all.shuffle(&mut rand::rng())` — explicit fairness/anti-determinism), then round-robin interleaves them. Two rooms at different playheads therefore get fair alternating piece priority, not last-writer-wins.

Mechanics that matter for the Range server:
- FileStream implements AsyncRead + AsyncSeek. `start_seek` is pure bookkeeping (streaming.rs:247-270) — it just sets position and updates the StreamState, so the priority window follows the playhead on the very next poll. This is your free-seek primitive.
- `poll_read` checks the have-bit for the current piece and, if missing, registers the task waker and returns Pending (streaming.rs:186-201). `wake_streams_on_piece_completed` (streaming.rs:104-119) only wakes streams whose CURRENT piece is the one that landed. A read blocks precisely until its own piece arrives.
- `Drop for FileStream` removes the stream from the map (streaming.rs:278-282). Cancel-on-seek == drop the FileStream. Keeping a FileStream parked at the last read offset keeps its window pinned — this is exactly the StreamSlot trick already in ss-bridge (engine.rs:23-31, MAX_SLOTS_PER_FILE = 2).
- HARD CAP: every FileStream holds an OwnedSemaphorePermit from BlockingSpawner's semaphore (`self.shared().spawner.semaphore().acquire_owned().await`, streaming.rs:346), sized by SessionOptions::runtime_worker_threads (spawn_utils.rs:15-28, `Semaphore::new(max_blocking_threads.max(1))`). Session::add_torrent takes a permit from the SAME semaphore (session.rs:1319). So the number of simultaneously-open FileStreams across the whole worker is bounded by that number, and exhausting it will deadlock new torrent adds. ### THE load-bearing constraint: the streaming window is advisory, so every served torrent trends to full size on disk
PieceTracker::acquire_piece (piece_tracker.rs:123-160) is a 3-step ladder: (1) steal from a peer 10x slower; (2) try the stream priority_pieces — but ONLY those the requesting peer actually has; then unconditionally fall through to `self.chunks.iter_queued_pieces(req.file_priorities, req.file_infos)` and reserve the first piece the peer has, anywhere in the selected files; (3) steal at 3x. There is no 'if the window is unavailable, idle' branch. A peer that lacks the window pieces will happily pull the far end of the file. Over a 2-hour room the worker downloads the whole selected file, and often finishes it long before the room ends.

This is precisely what rqbit PR #574 (`get_piece_bitfield()` + `update_streaming_window()`) asks for, and it is still OPEN and unmerged — the maintainer's position is that the existing streaming prioritization should suffice; the PR author and a second contributor argue the ability to 'restrict downloads to a window around the current playback position' is unavailable through existing endpoints. I agree with the PR author, and the source above is why.

What you CAN do without a fork:
- AddTorrentOptions.only_files / Session::update_only_files(&handle, &HashSet<usize>) (session.rs:1617) shrinks the ceiling to one video file (+ sidecar subs), which ss-bridge already does (engine.rs:268-306). This caps a season pack at one episode.
- AddTorrentOptions.ratelimits.download_bps (LimitsConfig, governor-backed) caps the rate at which the ceiling is approached.
What you CANNOT do without a fork: bound disk per torrent. librqbit exposes no public way to mark a piece not-have — ChunkTracker::mark_piece_broken_if_not_have is `pub` but ManagedTorrent::with_chunk_tracker is `pub(crate)` (torrent_state/mod.rs:265). The TorrentStorage trait (storage/mod.rs:120-170) lets you back pieces with anything you like, but the have-bitfield lives in ChunkTracker/BitV above it, so a storage that silently drops pieces would make the engine believe it has data it does not. TorrentServer gets ring-buffer eviction only because anacrolix/torrent's storage.TorrentImpl owns piece completion state.

CONSEQUENCE FOR THE DESIGN: plan disk as `worst case = sum of selected-file sizes of all live torrents`, enforced by admission control at job-accept time, not as a per-torrent cache. If you want a true ring buffer, the fork patch is the same shape as the existing ss-bridge patches (see the co-download finding).

### Leech mode: disable_upload is a cargo feature, and its swarm implications are real
`disable-upload = []` is an opt-in feature in librqbit's Cargo.toml:43; SessionOptions.disable_upload only EXISTS under `#[cfg(feature = "disable-upload")]` (session.rs:470-471). Enabling it changes four behaviors:

### Job re-dispatch / failover: what actually transfers, and the one accelerator that exists
Baseline reality: a re-dispatched job on a fresh worker is a COLD START. Zero pieces, new DHT lookup, new swarm ramp. For a 1080p release that is typically 10-60s to first playable bytes on a healthy public swarm, and the ramp is peer-count-bound (ss-bridge's engine.rs comment: 'librqbit fetches a piece from one peer at a time, so throughput is peers times what each uploads').

What can transfer, ranked by cost/benefit:
1. NOTHING (accept the cold start). Correct default. The server re-dispatches by infohash + file index + last known playhead; the new worker opens a FileStream and seeks straight to the playhead, so head+tail+window priority is immediately correct. Simple, no new protocol.
2. THE OLD WORKER AS A PEER — this is the real win and it is free. `AddTorrentOptions.initial_peers: Option<Vec<SocketAddr>>` (session.rs:508) injects peers directly. If the old worker is draining rather than dead (deploy, rolling restart, quota eviction), hand the new worker `initial_peers = [old_worker_bt_addr]`. The old worker has the exact pieces the new one needs, on a fat VPS uplink, with no DHT latency. This REQUIRES the old worker to have upload enabled at least toward siblings — which conflicts with the global disable-upload feature flag, since it is compile-time and session-wide. Resolution: either run workers with upload enabled and rely on `is_finished_and_no_active_streams` + peer_limit to bound seeding, or run two Sessions in one process (a leech session for public swarms and… no, same process, same feature flag — so realistically: don't compile disable-upload, and instead enforce leech behavior with `ratelimits.upload_bps` set to a small nonzero value, which is per-torrent and runtime-adjustable). That is a genuine fork-vs-config decision worth making explicitly.
3. BITFIELD TRANSFER ONLY — near-worthless. Knowing which pieces the old worker had does not give you the bytes; the new worker still downloads them.
4. WORKER-TO-WORKER FILE COPY (rsync/HTTP of the sparse file + the .bitv). Technically sound — fastresume validates the copied bitv with ~65 hash checks, so a corrupted transfer is caught — but you are moving gigabytes between VPSes to save a swarm ramp, and you must copy the sparse file sparsely (`rsync -S` / `--sparse`) or you'll transfer the zeros. Only worth it for planned drains of very large torrents, and option 2 dominates it in almost every case.

What the browser experiences: mediabunny's CustomSource read() against the worker returns bytes or it doesn't. On worker death, in-flight Range requests fail (connection reset / TLS close). The browser must (a) hold the read, (b) ask the server for a new worker endpoint, (c) retry the SAME byte range against the new endpoint. Because the data plane is stateless Range-over-HTTP against a content-addressed file, retry-with-new-host is genuinely transparent to the demuxer as long as the read layer retries rather than propagating the error. Build that retry/rebind into the CustomSource from day one — it is a ~30-line wrapper and it is the difference between 'the room hiccups' and 'the room dies'. Segments already uploaded to R2 keep playing for viewers throughout, so only the HOST's remux stalls; viewers see the sparse HLS timeline stop growing. That asymmetry is a real advantage of this architecture and is worth surfacing in the UI ('re-acquiring source…') rather than hiding.

Prior art check: TorrServer does not do engine failover at all — it is single-node; on restart it re-adds torrents from its DB and re-downloads its cache, since its cache is explicitly ephemeral (RemoveCacheOnDrop). No BitTorrent streaming server I found does cross-node piece handoff; the universal answer is cold restart. Don't over-engineer this.

### TorrServer as prior art for GC: bounded ring cache, LRU by piece access, idle disconnect timeout
TorrServer implements anacrolix/torrent's `storage.TorrentImpl` as a fixed-capacity Cache (server/torr/storage/torrstor/cache.go). `getRemPieces()` collects the piece ranges of all ACTIVE readers, merges them, and marks every piece outside those ranges (except file begin/end, `isIdInFileBE`) for removal, sorted oldest-`Accessed`-first. `priorityWatchdog()` re-arms piece priorities every 5s with an excellent comment explaining the deadlock it prevents: if priorities get cleared while a reader still needs data, nothing downloads, so no piece I/O happens, so cleanup never runs, so priorities are never restored — the torrent stalls forever with peers connected. That failure mode is worth remembering for ANY playhead-driven priority scheme.

Its settings (server/settings/btsets.go) are a good checklist for the worker's config surface: CacheSize (default 64MB, and `if c.capacity == 0 { c.capacity = info.PieceLength * 4 }`), ReaderReadAHead (percent), PreloadCache (percent), UseDisk, TorrentsSavePath, RemoveCacheOnDrop, TorrentDisconnectTimeout (seconds — the idle-TTL knob), ConnectionsLimit, DownloadRateLimit/UploadRateLimit (kb), DisableUpload, DisableDHT/PEX/UTP/TCP, ResponsiveMode ('don't wait pieceComplete').

The structural difference you cannot paper over: TorrServer can evict pieces because anacrolix's storage layer owns completion state. librqbit's ChunkTracker owns it above the storage trait. So the honest options are (a) worker-level LRU over whole torrents, not pieces — which is what I recommend — or (b) a fork patch that exposes piece invalidation. ss-bridge has already shown you're willing to carry fork patches, so (b) is open, but (a) is enough for a first deployment.

### The worker's HTTP server: certificates, CORS, HTTP/2, and the Range handler
CERTIFICATES — three viable shapes, and I'd pick the third:
(a) rustls-acme / tokio-rustls-acme with TLS-ALPN-01. Solves cert acquisition and serving in one crate, no persistent background task (renewal folds into the polled stream), DirCache for account+cert caching (mandatory against LE prod rate limits). BUT: TLS-ALPN-01 must run on port 443 of the worker's own hostname, and rustls-acme supports only TLS-ALPN-01 and HTTP-01 — no DNS-01, therefore no wildcards. Each worker needs its own A record and its own cert.
(b) HTTP-01 — needs port 80 as well; strictly worse than (a) here.
(c) CENTRAL DNS-01 WILDCARD, pushed over the control channel. The server instance owns the domain, uses instant-acme (0.8.5, ChallengeType::Dns01 is a real variant, wildcard-aware AuthorizedIdentifier) to issue ONE `*.w.ss.giuli.dev` cert via DNS-01, and ships cert+key to each enrolled worker over the already-authenticated outbound WSS control channel on renewal. Workers then need NO inbound port 80/443 ACME path, no per-worker DNS bookkeeping of their own, and no ACME credentials. This composes perfectly with the enrollment-token + Ed25519 design you already have: the cert becomes just another signed control-plane payload. Rate limits favor it too — LE allows 50 certs per registered domain per 7 days and 5 duplicate certs per identical identifier set per 7 days, so per-worker certs (option a) would start to pinch at ~50 worker rotations/week, whereas one wildcard renewed every 60 days uses ~1. Self-hosters do the same thing on their own domain. Downside: a wildcard private key now lives on every worker, so a compromised worker compromises the wildcard — mitigate by scoping the wildcard to a dedicated subdomain (`*.w.` only, never the apex) and by rotating on any worker decommission. Also watch LE's new DNS-PERSIST-01 (announced Feb 2026), which removes the per-issuance TXT dance and would make (c) cheaper still.

CORS — non-negotiable details for mediabunny CustomSource cross-origin Range reads: `Access-Control-Allow-Origin` (echo the instance origin, don't use `*` if you ever add credentials), `Access-Control-Allow-Headers: range`, and critically `Access-Control-Expose-Headers: content-range, content-length, accept-ranges` — without Expose-Headers the JS cannot read Content-Range and cannot learn the file size. A `Range` header makes the request non-simple, so every read is preflighted: cache the preflight aggressively with `Access-Control-Max-Age` (600s+) or you double your request count. rqbit's own CorsLayer is origin-predicate based (http_api/mod.rs:125-170); ss-bridge's is `Any` + `allow_private_network(true)` (server.rs:21-28) — the private-network bit becomes unnecessary once the worker is public, and `Any` should tighten to the instance origin(s).

HTTP/2 — enable ALPN h2 in the rustls config. On HTTP/1.1 the browser caps at ~6 connections per origin, which throttles the remux's read parallelism (and it shares that budget with everything else on the page). HTTP/2 lifts it to ~100-200 concurrent streams on one connection. For a workload that is 'many small ranged reads at scattered offsets', that is a large, cheap win.

RANGE HANDLER — rqbit's h_torrent_stream_file (http_api/handlers/streaming.rs) is the reference: parse `bytes=start-end`, `stream.seek(SeekFrom::Start(start))`, `.take(end-start)`, set Content-Range/Content-Length/Accept-Ranges, wrap in `tokio_util::io::ReaderStream::with_capacity(stream, 65536)`, return 206. Note it STREAMS the body (backpressured, constant memory) whereas ss-bridge BUFFERS the whole range into a Vec and caps it at MAX_RANGE=64MB (server.rs:120-124). For a multi-tenant worker, stream it — buffering N concurrent 64MB ranges is an OOM waiting to happen. Keep a range-size cap anyway, as a request-validation guard.

GRACEFUL SHUTDOWN — `with_graceful_shutdown` was removed in hyper 1.0 and axum::serve's story here is still rough (axum#2323, #2352, #3003: tasks spawned inside handlers are not connected to the shutdown future). Long-lived streaming responses are exactly the case that breaks. Practical shape: (1) control plane sends 'draining' → server stops accepting new job leases and reports itself unschedulable; (2) HTTP layer keeps serving in-flight ranges but returns 503 + `Connection: close` on new ones; (3) track in-flight stream count yourself in an Arc<AtomicUsize>/watch channel and wait on it with a hard deadline (30-60s); (4) `Session::stop()` (session.rs:1059-1075) pauses every torrent, cancels the session CancellationToken, and sleeps 1s — note that 1s sleep is the library's own admitted 'this sucks, but hopefully will be enough', so give it more room than that before SIGKILL; (5) then exit. Because reads are idempotent Ranges, a 503 on a new range is safe for a client that retries — which is the same retry path failover needs, so build it once.

### ARCHITECTURE SKETCH — per-torrent state machine, and how it maps onto librqbit's own states
Worker phase (what the control plane sees) → librqbit ManagedTorrentState (torrent_state/mod.rs:67-84: Initializing | Paused | Live | Error):

Requested — lease accepted, admission passed. No librqbit object yet.
  → Resolving: add_torrent(list_only=true). Timeout 90s → Failed. Yields ListOnlyResponse{info, torrent_bytes, seen_peers}.
  → Screening: apply video-only policy to info.iter_file_details(). Reject → Rejected (report reason upstream; the server should remember the infohash so no worker retries it).
  → Validating: real add_torrent(TorrentFileBytes(torrent_bytes), { paused: true, overwrite: true, sub_folder: Some(hex), only_files: Some([video, ...sidecar_subs]), initial_peers: seen_peers, peer_limit, ratelimits }). librqbit is Initializing; fastresume spot-check (~65 hashes) or full rehash. wait_until_initialized with a timeout. → librqbit Paused.
  → Ready: paused, bytes validated, file list known. Reported to the server; the browser can be handed the endpoint. Enters Serving on first Range read, or immediately via session.unpause.
  → Serving: librqbit Live, ≥1 lease, ≥1 StreamSlot. This is the only phase that consumes bandwidth. Reads block on poll_read/waker; seeks are start_seek + slot repoint.
  → Idle: librqbit Live but 0 leases (or last_active > idle_grace). session.pause(&handle) → librqbit Paused. Bytes retained. A new lease here CANCELS pending_reap and unpauses — the cheapest possible re-open, and the case that matters most (host reloads the tab, room restarts, viewer rejoins).
  → Reaped: after reap_ttl, session.delete(id, delete_files=true). Disk accountant credited. Entry removed. Also reachable directly from Idle by LRU pressure when disk > high_water.
  → Failed: librqbit Error, or resolve timeout, or storage error. Report upstream with reason so the server can re-dispatch elsewhere (the same infohash may succeed on a worker with a different network path). librqbit itself can restart an errored torrent (mod.rs:430-441 puts Error back to Initializing on start), so ONE in-place retry before giving up is worth doing.

Invariants to assert in code: (1) a torrent with ≥1 lease is never reaped; (2) pending_reap and a live lease are mutually exclusive; (3) every phase transition writes last_active; (4) DiskAccountant is credited/debited only in Validating (reserve worst case = selected_total) and Reaped (release actual), never incrementally — reserving the worst case up front is what makes admission control honest, given that the streaming window does not clamp downloads.

Why `delete_files=true` here but `false` in ss-bridge: ss-bridge runs on the user's own machine where keeping bytes in ~/Downloads is a feature. A shared multi-tenant worker with a fixed VPS disk must reclaim, and retaining another room's content is also the wrong legal posture. Keep the .bitv? No — session.delete removes the persistence entry too, and a bitv without its file is useless.

RECOMMENDATIONS:
- Fork ss-bridge's engine.rs into the worker rather than starting clean — its refcount + pending_delete-cancellation + idle-sweep + StreamSlot pool is exactly the model the worker needs, already debugged against librqbit 9.0.1. Change three things: leases replace refs, delete_files goes true, and add the DiskAccountant. Carry all four vendored fork patches forward (64MB window, co-download with MAX_CODOWNLOADERS=4, missing_chunks, and the InflightPiece.peers change).
- Set SessionOptions.runtime_worker_threads explicitly and generously. It sizes a semaphore that gates BOTH concurrent FileStreams and Session::add_torrent; exhausting it stalls new job acceptance in a way that will look like a mysterious hang. Budget (max_leases × slots_per_lease) + concurrent_init_limit + headroom, and add a metric for permits in use.
- Enforce disk as worst-case reservation at admission time (reserve the full selected-file size when a torrent enters Validating), not as observed usage. The streaming window does not clamp downloads, so observed usage is a lagging indicator that will let you over-commit and then hit ENOSPC mid-room — the worst possible failure, since it corrupts the room for everyone rather than just refusing one job.
- Use the list_only pre-flight for video-only enforcement, and re-add with the returned torrent_bytes and seen_peers rather than the magnet. This is free, it skips a second DHT resolve, and it makes librqbit's own AlreadyManaged dedup actually work on the fast path.
- Serve the have-bitfield in rqbit's exact wire format (raw bytes + x-bitfield-len, gated on Accept: application/octet-stream) and add x-piece-length. It is compact, it is already proven, and it lets the web UI's buffered-ranges bar be a single fetch on a timer instead of a stats-polling scheme.
- Alert on average_piece_download_time and on a new ssw_range_stall_seconds histogram, not on peer count. Peer count is a vanity metric that stays healthy while a room stalls; time-blocked-in-poll_read is the actual user experience, and it is trivially instrumentable by timing the read in the Range handler.
- Build the browser-side CustomSource retry/rebind wrapper before building worker failover. Because the data plane is idempotent Range-over-HTTP against content-addressed files, a read layer that retries the same range against a newly-issued endpoint makes worker death, worker drain, and 503-during-shutdown all the same code path — and it is the cheapest resilience in the entire design.
- Prefer the central DNS-01 wildcard (instant-acme on the server, cert pushed over the existing signed control channel) over per-worker ACME, but scope it to a dedicated subdomain (*.w.ss.giuli.dev, never the apex) and rotate on worker decommission. It removes inbound port-80/443 ACME requirements from workers entirely, keeps LE rate limits irrelevant, and reuses the enrollment trust you have already designed. Implement cert hot-reload via an ArcSwap in the rustls cert resolver so renewal never drops a live stream.
- Enable ALPN h2 on the worker's TLS config. The workload is many concurrent ranged reads to one origin; HTTP/1.1's ~6-connection browser cap is a real ceiling and h2 removes it for one config line.
- Do not build worker-to-worker piece transfer. Ship cold restart, add initial_peers=[draining worker] for planned drains, and measure. No comparable system does cross-node handoff, and the complexity would buy you seconds on an event that should be rare.

OPEN_QUESTIONS:
- disable-upload vs worker-to-worker seeding: the feature is compile-time and session-wide, so you cannot be a strict leecher toward public swarms AND a seed toward sibling workers in one process. Decide: (a) don't enable the feature, enforce leech behavior with a low per-torrent upload_bps and rely on is_finished_and_no_active_streams to shed peers — keeps sibling seeding and failover option 2 alive; or (b) enable it and accept cold restarts plus a measurable throughput penalty from non-reciprocating peers. I lean (a); it is also reversible per-torrent at runtime, which (b) is not.
- Wildcard key distribution: option (c) puts a *.w.ss.giuli.dev private key on every worker. Is that acceptable given workers are the most exposed component (public IP, public swarm traffic, attacker-supplied infohashes)? If not, per-worker TLS-ALPN-01 certs are the safer default and the LE 50-certs/domain/week limit only binds at high worker churn. Worth deciding before the enrollment protocol is frozen, since the cert path shapes it.
- Does the browser's mediabunny CustomSource issue reads that are small and scattered (favoring HTTP/2 multiplexing and cheap preflights) or large and sequential (favoring fewer, bigger ranges)? This determines whether to cap max range size aggressively, how long to set Access-Control-Max-Age, and whether the 2-slot-per-file pool is enough or should be raised. Instrument the existing ss-bridge before designing around a guess — the data is one log line away.
- How does the server pick a worker? Nothing in this research covers scheduling. Candidates: least-disk-used, least-leases, infohash-affinity (dispatch a second room on the same infohash to the worker that already has it — this is the highest-value one, since it converts a cold start into a zero-cost AlreadyManaged and halves disk), or geographic proximity to the host. Infohash-affinity plus disk headroom is probably the whole algorithm.
- Is a strict streaming-window fork patch worth carrying? It would make disk-per-torrent bounded and turn admission control from 'reserve the worst case' into 'reserve a constant', roughly tripling the rooms one VPS can host. The patch shape is known (rqbit PR #574's update_streaming_window, or a narrower 'if priority pieces exist and are all in flight, return NoneAvailable rather than falling through'), but it changes swarm behavior and needs measurement against real releases before trusting it.
- Legal/abuse surface not covered here: what stops a worker from being pointed at an infohash the instance owner does not want to touch? The signed-job envelope authenticates the SERVER, not the CONTENT. A worker-side denylist and an operator kill-switch over the control channel are probably needed, and self-hosters will want the denylist to be theirs, not yours.

### Capability token goes in the URL PATH, not an Authorization header — a header forces a CORS preflight on every range read
`Range` is a CORS-safelisted request header for simple single-byte-range values (`bytes=0-127`), shipped in Chromium and WebKit, so a cross-origin ranged GET is one request with no preflight. `Authorization` is never safelisted and would add an OPTIONS round trip to every single read — fatal for a pipeline doing thousands of ranged reads over a 50 GB file. Put the token in the path: `https://<worker>/r/<token>/<infohash>/<fileIndex>`. The worker must still implement OPTIONS (Firefox has lagged on the Range safelisting) and must send `Access-Control-Allow-Origin: <instance origin>` plus `Access-Control-Expose-Headers: Content-Range, Content-Length, Accept-Ranges`. Token-in-URL is acceptable given a ~15 min expiry over HTTPS; the app already sets `Referrer-Policy: no-referrer` (internal/httpapi/server.go:91). There is no CSP on app pages today (server.go:107-109 scopes the only CSP to `/assets/plugin-worker/`), so no `connect-src` change is needed — but if a CSP is ever added, worker hosts must be listed.
sources: https://developer.mozilla.org/en-US/docs/Glossary/CORS-safelisted_request_header; https://github.com/whatwg/fetch/issues/1310; internal/httpapi/server.go:89-115

### Token format: Ed25519-signed opaque envelope, verified offline by the worker, revoked over the control plane
Mint server-side only. `v1.<b64url(payload)>.<b64url(sig)>` with a FIXED binary payload layout rather than JSON (no canonicalization ambiguity), carrying: `kid` (server signing key id, for rotation), `jti` (16 bytes, the revocation handle), `wid` (worker binding — a token stolen from one worker is useless on another), `ih` (20-byte infohash), `fi` (file index; -1 = metadata only), `rid` (room id, empty while the job is still pre-room), `sid` (anonymous session id), `nbf`/`exp` (~15 min). The worker validates signature against the server pubkey pinned at enrollment, then `wid == self`, `exp`, and that `ih`/`fi` match the path — no DB, no callback, which is the whole point. Do NOT use JWT: the algorithm field is a footgun the worker has no use for. Revocation in three layers: (a) short exp does the heavy lifting; (b) a `revoke` control-plane message keyed by `jti`/`rid`/`jobId`, held in a small in-memory set on the worker until each entry's exp; (c) lifecycle triggers — room delete (internal/room/store.go:740, driven by internal/room/sweeper.go:52-81), source swap (store.go:525), and stale-claim reclaim (store.go:392-431).
sources: internal/room/store.go:525; internal/room/store.go:740; internal/room/sweeper.go:52-81; internal/room/store.go:392-431

### The claim model and the job token are orthogonal and must stay separate
The claim (internal/httpapi/clientmedia.go:85-117, backed by `ReserveUpload` at internal/room/store.go:133-163) answers 'who is the room's one media producer'. The job token answers 'who may read these torrent bytes'. Merging them would break the pre-room phase (the job exists before any room) and the failover path (the token rotates, the claim must not). Keep both, and piggyback the job lease on the claim heartbeat: `publishClientMedia` already calls `TouchClientClaim` on every non-final publish (clientmedia.go:371-373, store.go:383-390), and `ReclaimStaleClientClaims` (store.go:392-431) already runs on the sweeper tick with `UPLOAD_IDLE_MINUTES` (default 10, internal/config/config.go:61; wired at cmd/server/main.go:61-62). A job whose room's claim went stale should be stopped on the same sweep — otherwise a dead host tab leaves a worker seeding a 50 GB torrent for ten minutes and then forever.

### Worker registry: liveness in memory, durable facts in Redis, affinity derived purely from heartbeats
Mirror the existing split — `Hub` keeps live connections in in-process maps (internal/sync/hub.go:43-66, 249-283) while `room.Store` keeps durable state in Redis. Redis keys following the store's naming (internal/room/store.go:38-50): `worker:{id}` hash (pubkey, name, state, capacity, last_seen_ms), `workers:by_seen` ZSET (the same trick as `rooms:by_expiry`, store.go:50, giving cheap reaping), `job:{id}` hash, `worker:{id}:jobs` set. CRITICAL design choice for the affinity table: do NOT maintain `infohash → worker` as an event-sourced table that must be invalidated when a worker evicts torrent data from disk — instead DERIVE it from each heartbeat, which lists what the worker currently holds `[{infohash, fileIndex, haveBytes, wantBytes, peers, downSpeed}]` capped at the 64 most recent. A derived table cannot go stale, so there is nothing to invalidate and no way for the server to send a job to a worker that quietly deleted the data. Health states: enrolling → healthy → degraded (disk low or job cap) → draining (admin, serves existing jobs, accepts none) → down (3 missed 5s heartbeats = suspect, 6 = down, re-dispatch). Draining is what lets a worker be redeployed without killing live rooms.
sources: internal/sync/hub.go:43-66; internal/sync/hub.go:249-283; internal/room/store.go:38-50

### Placement: infohash affinity first, then least-loaded — never round robin
Round robin is wrong for this workload because jobs are wildly uneven (a 700 MB episode vs a 60 GB remux) and long-lived (hours), so a 2-worker fleet lands both heavy jobs on one node roughly half the time. Order: (1) hard filters — state==healthy, freeDisk > fileSize*1.2, activeJobs < maxJobs; (2) infohash affinity — any surviving worker that already holds pieces of this infohash wins, tie-broken by `haveBytes` for the requested fileIndex; this is the single biggest win, making a rewatch or the next episode of a season pack start instantly; (3) composite least-loaded score over (activeJobs/maxJobs, 1 − freeDisk/totalDisk, recent downlink saturation). Zero-worker behaviour must distinguish two cases with different user actions: no healthy worker at all → 503 `no_workers` ('torrents are unavailable on this instance right now'), versus all healthy workers at capacity → 503 `workers_busy` ('all download nodes are busy, try again in a few minutes'). No queueing — a magnet that resolves ten minutes later is worse than an honest failure — and no fallback, matching the existing absolutism of `HelperRequiredError` (web/src/torrent.ts:49-60).
sources: web/src/torrent.ts:49-71

### Failover should re-seed the new worker with the playhead — the server already knows it
On re-dispatch, the new worker starts with zero pieces and the room stalls while it refetches from byte 0, which is the wrong offset: the room is mid-film. The server already holds `PlayState.PositionMs` (`store.GetState`, internal/room/store.go:648-669) and the room's `DurationMs` (internal/room/types.go:79). ### There is no identity and no rate limiting anywhere, and SetTrustedProxies(nil) makes per-IP limiting impossible today
Confirmed by exhaustive grep: no cookies, no sessions, no accounts, no limiter. Authorization is 'possession of the room id plus being first' (documented at internal/httpapi/clientmedia.go:28-31); the only credential is the in-memory `capability` minted per WebSocket join (internal/sync/hub.go:352-357, checked by `AuthorizeMember` at hub.go:131-137) which dies with the connection. Hang quotas on it: dispatches/hour (~10), concurrent active jobs (~2), and — the one that actually protects the bandwidth bill — bytes/day accounted from worker heartbeats. Add a coarse per-IP outer limit (sessions minted per hour) since a cookie is trivially reset. Mount the middleware ONLY on the new `/api/torrents` group; touching the existing room routes would change claim semantics for no benefit. Turnstile is the escalation if that proves insufficient (the deployment is already behind Cloudflare) — do not build it now. Shape the session record so an optional account is later just 'a session with a user_id'.

### Topology: proxy-through-origin for single box, direct HTTPS for the VPS fleet — same client code, server hands out a base URL
The abstraction that makes this a non-choice is that the browser only ever receives a `readBase` string. SINGLE BOX (self-host default): the API server reverse-proxies `/api/worker/{id}/r/*` to the worker on the Compose network. Zero certificates, zero DNS, zero CORS, no mixed-content problem, and the worker's HTTP port is never exposed to the internet at all — only the enrolled server can reach it, which is a genuine security improvement over the direct path. Cost is O(source size) once per room through the Go process, not per viewer; acceptable. MULTI-VPS (ss.giuli.dev): direct, because proxying would double the API VPS's bandwidth (in from worker, out to browser) and make it the throughput ceiling for every concurrent room — the exact property internal/httpapi/media.go:19-21 is built to preserve. Ship the proxy path FIRST: it is the fallback when a cert expires, when a worker hostname does not resolve, or when a viewer's network blocks the worker port, so a cert failure degrades to slow instead of to an outage. Two implementation notes: use `httputil.ReverseProxy` with `FlushInterval: -1` for unbuffered streaming, and exclude the proxy route from the metrics middleware's duration histogram the same way WebSockets are excluded (internal/httpapi/metrics.go:43-45) — an hours-long range stream would drag every quantile, and `gin.Default()`'s logger (server.go:55) would emit thousands of lines per room.
sources: internal/httpapi/media.go:17-28; internal/httpapi/metrics.go:40-52; internal/httpapi/server.go:55

### Certificates: per-worker Let's Encrypt via TLS-ALPN-01 on the data port; the private CA idea does not work for browsers
The rcgen private CA from the prior research is correct for the control plane and USELESS for the data plane — a browser will not trust it, and the page is HTTPS so a plain-http worker is blocked as mixed content regardless. Recommended: give each worker a hostname `w1.w.ss.giuli.dev` (A record created by the server, which already holds zone credentials) and let the worker obtain its own cert with rustls-acme using TLS-ALPN-01 on port 443 — the same port and listener it serves data from, which is precisely what rustls-acme is designed for, and it means no private key ever crosses the control plane. Escape hatch for a worker without a reachable 443: the server obtains one wildcard `*.w.ss.giuli.dev` via DNS-01 (the only challenge type that yields wildcards) and pushes the key over the enrolled control-plane connection; one cert covers an unbounded fleet and sidesteps Let's Encrypt per-domain rate limits. HARD CONSTRAINT: the worker's DNS record must be grey-cloud / DNS-only. Cloudflare's CDN terms restrict proxying video hosted outside Cloudflare, and orange-clouding would also terminate TLS and break TLS-ALPN-01. Note that the entire Local Network Access permission apparatus in web/src/localHelper.ts:108-161 (and the 'Já baixei e abri' prompt-raising dance at localHelper.ts:163-189) simply disappears — that gate only exists for loopback, not for public IPs.
sources: https://docs.rs/rustls-acme/latest/rustls_acme/; https://blog.cloudflare.com/updated-tos; web/src/localHelper.ts:100-189

RECOMMENDATIONS:
- Ship the proxy-through-origin data path FIRST, before any certificate work. It makes the single-box self-host story complete with zero TLS work, and it is the permanent fallback that turns a cert failure into 'slow' instead of 'down'. The direct path is then a pure optimization behind a per-worker `directHost` field that, when empty, yields a proxy URL.
- Make `readBase` a server-issued string from day one and never let the client construct a worker URL. Every other property in this design — failover, token refresh, proxy-vs-direct, draining — falls out of that single indirection for free.
- Derive the infohash→worker affinity table entirely from heartbeat contents rather than maintaining it as mutable state. A derived table cannot lie about what a worker holds, which removes the entire class of 'dispatched to a worker that already deleted the data' bugs.
- Add the AbortController/timeout and single retry to `streamInput`'s read (remuxJob.ts:96-103) as a standalone change BEFORE the worker migration. It is a latent bug today (a hung bridge stalls the pipeline for the OS TCP timeout) and it is the exact hook failover needs, so it can be written and tested against the existing bridge.
- Wire `SourceHooks.CancelMedia` in cmd/server/main.go:73 — it is currently nil and therefore dead. Doing it as part of this work gives source-swap cleanup for workers at essentially no cost, and the seam is already called in the right place (source.go:90-92).
- Do not merge the worker job token with the room claim. They have different lifetimes (the job predates the room and the token rotates on failover while the claim must not) and different subjects. Piggyback the job lease on the existing claim heartbeat instead (clientmedia.go:371-373).
- Put the capability token in the URL path, never in an Authorization header. This is not a style preference — a header adds a CORS preflight to every one of thousands of ranged reads.
- Publish the worker's BitTorrent port TCP+UDP in the compose file and call it out in the README. It is the single most likely thing a self-hoster will miss, and the symptom (slow torrents) does not point at the cause.
- Surface worker swarm stats through `room.Preparation` so every viewer sees peers and speed, not just the host tab. This is a user-visible improvement that the migration hands over for free (upload.ts:70-75 currently makes it host-only), and it is what makes a failover stall legible instead of looking like a dead transfer.
- Build the anonymous session cookie now, even with generous limits. Retrofitting an identity anchor after the torrent endpoint is public is much harder than shipping it alongside, and the current authorization model ('possession of the room id plus being first', clientmedia.go:28-31) does not extend to an endpoint that spends someone else's disk and bandwidth.

OPEN_QUESTIONS:
- Where does the worker job live before a room exists? The picker resolves a magnet before room creation (Home.tsx:354-370), so a job is born bound only to an anonymous session and is bound to a room later. Decide whether an unbound job is reaped on a short timer (e.g. 5 min) or whether room creation is moved BEFORE the magnet resolve — the latter simplifies token scoping and revocation considerably but changes the Home page flow.
- Does a worker keep seeding after the room dies? Seeding back to the swarm is good citizenship and costs upload bandwidth on the instance owner's VPS, and it has a different legal profile from leeching. Needs an explicit policy knob with a documented default.
- Worker disk eviction policy: LRU by last read, with what floor? This interacts directly with the value of infohash affinity — evict too eagerly and the affinity table is always empty; too lazily and a 2-worker fleet fills up. Needs a number tied to the room TTL (5h, config.go:58).
- Does the browser verify what it reads? Today the pipeline trusts the bytes the bridge serves because the bridge is on the user's own machine. A remote worker is a different trust position, and BitTorrent piece hashes are verified on the WORKER, not in the browser. Probably acceptable (the worker is the instance owner's), but it should be a stated decision, not an accident.
- Multi-server-process future: the control-plane WSS terminates on one Go process, so with two API replicas a worker is reachable from only one of them. The current deployment is single-process so this is not urgent, but the dispatch path should go through Redis pub/sub from the start if horizontal scaling is ever intended.
- Token expiry vs a very long read stall: a 15-min token can expire while a single ranged read is blocked waiting on a slow swarm. Decide whether the worker validates the token only at request start (simplest, correct) or continuously.
- Is `MAX_UPLOAD_MB` (default 51200, config.go:57) still the right cap when the source is a remote torrent the server never stores? The budget is charged against remuxed OUTPUT bytes (clientmedia.go:166-174, maxClientBytes at clientmedia.go:557-559), which is unchanged — but the worker now needs its own per-job disk cap, and the two limits should be reconciled so a job cannot be admitted that the budget will later refuse.

SUMMARY: Bandwidth is not the cost problem for this architecture — legality is. With a 2h 1080p WEB-DL baseline (8 GB, ~8.9 Mbit/s), each room moves ~8.7 GB swarm→worker (free ingress everywhere), ~8.5 GB worker→browser (the only metered leg), ~8.1 GB browser→R2 (the host's own uplink), and 8.1 GB × viewers out of R2 (free egress). At 50 rooms/day that is 12.8 TB/month of worker egress, which fits inside Hetzner's 20 TB EU allowance with room to spare; overage is €1/TB so even 200 rooms/day costs single-digit euros. All-in the fleet lands at roughly $42/mo (10 rooms/day), $61/mo (50/day), $185/mo (200/day), and at the larger scales R2 Class-A operations and R2 storage retention cost MORE than all VPS bandwidth combined — segment duration and delete-after-room policy are the real cost levers. Relaying through the main instance (option A) is free-ish on Hetzner but costs $255–$1,020/mo on Fly-class pricing and $1,148–$4,592/mo on AWS-class egress, so direct worker→browser is worth 1–2 orders of magnitude the moment the instance is not on a cheap-transit host. The binding constraints are: (1) OVH explicitly bans P2P in its VPS and Public Cloud terms, disqualifying it outright; Hetzner has no explicit P2P clause but runs a 24h-notice abuse process and has a community reputation for proactive torrent emails; (2) per-worker uplink (Hetzner Cloud is unguaranteed ~300–500 Mbit/s shared, Contabo's cheap tier is a hard 200 Mbit/s) caps concurrent rooms at ~20–35 per worker, not bandwidth quota; (3) the host's residential UPLOAD (8.9 Mbit/s realtime, 13–28 Mbit/s to buffer ahead or for bigger releases) is the single most likely failure point in the whole design.

### Per-room byte ledger (2h 1080p, 8 GB source, S = source size)
Six legs, per room, with framing overhead included (TCP/IP+TLS on the wire ≈ 3.2%, since providers meter interface bytes not payload):

| Leg | Formula | GB @ S=8 | Who pays | Metered? |
|---|---|---|---|---|
| swarm → worker (ingress) | S × 1.05 × 1.032 | 8.67 | instance owner | NO — inbound unmetered at Hetzner, Contabo, OVH, Vultr, Oracle |
| worker → swarm (seeding) | S × ratio × 1.032 | 0 / 4.13 / 8.26 | instance owner | YES — pure added egress |
| worker → host browser | S × 1.03 × 1.032 | 8.50 | instance owner | YES — the only structurally unavoidable metered leg |
| host browser → R2 (PUT) | S × 1.01 | 8.08 | the HOST's home connection | YES against their ISP cap |
| R2 storage | S × 1.01 × retention | — | instance owner | $0.015/GB-mo |
| R2 → viewers | S × 1.01 × V | 8.08 × V | instance owner | NO — R2 egress is $0 |

The 1.05 on the swarm leg is protocol + endgame/head-pinning duplicate requests (2–8% depending on how aggressively the head is requested from N peers). The 1.03 on the worker→browser leg is moov/cues parsing plus per-seek re-reads from the nearest keyframe (~1 GOP + container cluster, a few MB per seek; 10 seeks on an 8 GB file ≈ 1%). Note that seek waste on the SWARM leg is near-zero for a full watch: BitTorrent reorders rather than duplicates, and with an 8 GB torrent on an 80–400 GB disk there is no intra-room eviction, so rewind never re-downloads. Abandoned prefetch REDUCES the swarm leg (user quits at 60% → ~62% of S downloaded), it does not inflate it.
sources: https://developers.cloudflare.com/r2/pricing/

### Seeding: leech-only is cheap and, on public swarms, socially tolerated but not free of consequence
Ratio math: seeding at 1.0 exactly doubles the worker's metered egress (8.26 GB/room added at S=8 GB), taking 50 rooms/day from 12.76 to 25.14 TB — the first configuration in this whole analysis that actually exceeds Hetzner's 20 TB and starts costing money (€5.14/mo, still trivial). At Vultr/DO pricing the same choice costs $124–$248/mo.

Mandated ratios exist only on PRIVATE trackers: minimums are typically 0.5–1.0, with per-torrent expectations of hitting 1.0 (or a minimum seed time, commonly 24–72h) to avoid a hit-and-run strike, enforced by account suspension or download restriction. Freeleech torrents and seeding bonus points are the sanctioned escape hatches. None of this applies to the worker if the product is magnet-links-from-public-sources: public trackers and DHT have no enforcement, and the free-rider problem there is precisely why private trackers exist. So a leech-only worker is technically viable on public swarms.

But: (a) leech-only on public swarms degrades the commons the product depends on, and if ss.giuli.dev ever becomes a meaningful share of a swarm's leechers, it measurably slows everyone including its own users; (b) a peer that advertises complete pieces but never unchokes is trivially detectable and gets choked back by tit-for-tat clients, so pure leeching actively hurts the worker's own DOWNLOAD speed and therefore time-to-first-frame; (c) private trackers are off the table entirely for a worker fleet (announce credentials in a hosted binary, ratio accounting across shared IPs, and passkey leakage all violate typical tracker rules). Recommended posture: seed at a small capped ratio (0.25–0.5) or a fixed upload rate cap (e.g. 2–5 Mbit/s per torrent) while the torrent is in the hot cache, then stop on eviction. That buys tit-for-tat standing and healthy download rates for a few euros a month, and it is the cheapest line item in the entire budget.
sources: https://wiki.pulsedmedia.com/wiki/Private_tracker; https://www.rapidseedbox.com/blog/torrent-ratio-tips; https://bytesized-hosting.com/guides/private-tracker-seedbox-guide-ratio-building-racing-and-best-practices

### Disk sizing and the real value of dedup (latency, not money)
Usable capacity at 85% (leave headroom for partial pieces and fs overhead):

| Disk | @4 GB torrents | @8 GB | @25 GB remux |
|---|---|---|---|
| 80 GB (Hetzner CX33) | 17 | 8.5 | 2.7 |
| 160 GB (CX43) | 34 | 17 | 5.4 |
| 320 GB (CX53) | 68 | 34 | 10.9 |
| 400 GB (Contabo VPS 12) | 85 | 42.5 | 13.6 |
| 1 TB (BuyVM + 4 block slabs, $5/mo) | 212 | 106 | 34 |

160 GB holds ~17 concurrent 8 GB torrents — comfortably above the 15–20 peak-concurrent estimate for 50 rooms/day, so no intra-room eviction and therefore no re-download on rewind. 400 GB gives a genuine retention cache.

Dedup benefit, LRU cache hit rate under Zipf-distributed title popularity (simulated, 200k requests):
| Zipf α | catalog 500 | cache 20 | cache 40 | cache 100 |
|---|---|---|---|---|
| 0.7 (flat/long tail) | — | 13.7% | 23.2% | 42.1% |
| 1.0 (typical web) | — | 36.8% | 49.2% | 66.6% |
| 1.3 (very concentrated) | — | 65.0% | 75.5% | 86.1% |
Against a 5,000-title catalog at α=1.0 the same caches give 23.1% / 31.8% / 43.5%.

Realistic expectation for a small social watch-party app (α likely 1.0–1.3, small effective catalog because friends watch what is trending): a 40-title cache (~320 GB) should hit 50–75%. But note WHAT that saves: the swarm ingress it avoids was free anyway, and the R2 output would be re-uploaded regardless unless you also key the R2 object by infohash. The genuine wins are (1) time-to-first-frame drops from swarm-warmup seconds to instant, (2) no dependence on swarm health for a re-watch, (3) disk, which is the metered resource. Bigger win available: dedup the R2 side too — key HLS output by (infohash, remux params) and a second room on the same title uploads zero bytes and issues zero Class A ops, which at 200 rooms/day with 50% repeat would halve the $60/mo Class A line and the storage line.
sources: https://contabo.com/en/vps/; https://buyvm.net/

### The host's residential uplink is the architecture's real bottleneck
The plan moves the DOWNLOAD to a VPS but leaves the UPLOAD on the host's home connection. Per room the host's own line carries 8.50 GB down (worker→browser) + 8.08 GB up (browser→R2) = 16.58 GB — about 72 rooms before a 1.2 TB ISP cap (Comcast-style) is exhausted. Required sustained UPSTREAM:

| Release | realtime (1×) | 1.5× buffer-ahead |
|---|---|---|
| 4 GB x265 | 4.4 Mbit/s | 6.7 Mbit/s |
| 8 GB WEB-DL | 8.9 Mbit/s | 13.3 Mbit/s |
| 15 GB 1080p BD | 16.7 Mbit/s | 25.0 Mbit/s |
| 25 GB remux | 27.8 Mbit/s | 41.7 Mbit/s |

US median fixed upload is ~55.8 Mbit/s (Ookla, Feb 2026) rising to 58+ by June 2026, so the median host is fine for WEB-DL and marginal for remuxes. The tail is not: cable and DSL customers on 5–10 Mbit/s upstream cannot sustain even the 8 GB baseline while also holding a video call, and 'zero install, it just works' fails for exactly the users who most need a watch-party. This is the strongest argument for eventually offering worker-side remux as a fallback — but that flips the worker from a byte-range file server into a transcoder and origin, which is a materially different legal posture and should be a deliberate, separately-reasoned decision, not a perf patch.
sources: https://www.allconnect.com/blog/us-internet-speeds-globally; https://ezeefiber.com/blog/internet-speeds-usa-vs-the-world/

- Provider shortlist, in order: (1) BuyVM/Frantech Luxembourg — jurisdiction-scoped AUP with no P2P clause, unmetered 1 Gbps, $1.25/256 GB block storage for the piece cache, $2–$30/mo; (2) Contabo VPS 12 (12c/48 GB/400 GB/800 Mbit/$30) — best storage-per-dollar, unlimited traffic, only German law as a constraint; (3) Hetzner CX43 EU (€15.99, 20 TB, 160 GB NVMe) — cheapest compute but notice-and-takedown risk; (4) FlokiNET Romania/Iceland if legal exposure is the dominant concern. Strike OVH entirely — its VPS and Public Cloud terms name P2P as prohibited.
- Never put the main instance and the workers in the same hosting account or the same provider project. The whole point of the direct worker→browser data plane is that the instance's traffic profile is a plain JSON API; a shared account re-couples them at the abuse-desk level, which is where the actual risk lives.
- Do NOT put workers in Hetzner's US locations without re-running the numbers: US includes 1 TB, not 20 TB. It is still cheap at €1/TB, but the '20 TB is free' mental model is wrong there and wildly wrong in Singapore (0.5 TB, €7.40/TB).
- Spend the engineering effort on R2, not on bandwidth. Use 6s or 10s segments (not 2s — that is a 4–8× Class A multiplier for marginal seek granularity), write the playlist once as a complete VOD manifest when the room ends rather than rewriting per segment, and set a lifecycle rule deleting objects a few hours after the room ends. Those three choices are worth more than every VPS decision combined at 200 rooms/day.
- Key R2 output objects by (infohash, remux parameters) so a second room on the same title uploads zero bytes and issues zero Class A operations. At 50% repeat rate this halves both the dominant cost lines and gives instant playback — a better user-visible win than anything on the torrent side.
- Seed at a capped ratio (0.25–0.5) or a per-torrent upload rate cap of 2–5 Mbit/s while the torrent is hot, then stop on cache eviction. Pure leeching costs you download speed via tit-for-tat choking, and the egress it saves is ~€5/month at 50 rooms/day. Do not attempt private trackers with a hosted worker fleet — passkey handling and ratio accounting across shared IPs violate typical tracker rules.
- Size workers by peak concurrent rooms against a ~300–500 Mbit/s realistic per-instance ceiling, not by monthly TB. Rule of thumb at 8.9 Mbit/s/room: ~20–34 rooms per Hetzner instance at 60% utilisation. Two workers cover 50 rooms/day with headroom; plan a fourth before evening peaks reach ~50 concurrent.
- Instrument the host's measured upload throughput in the browser before starting the remux, and refuse or degrade gracefully below ~1.2× the source bitrate rather than letting the room stall. This is the most likely real-world failure mode and it is invisible in every cost table above.
- Treat worker-side remux as a designed fallback for low-uplink hosts, not as an optimisation. It rescues the tail of users the product's 'zero install' promise is aimed at, but it converts the worker from a byte-range file server into an origin — decide that on legal grounds, deliberately, not as a performance patch.
- Presign HLS segment URLs in batches (e.g. 100 per call) rather than one per segment. It cuts the residual main-instance traffic by an order of magnitude and, more usefully, removes a per-segment round-trip from the upload hot path.

- What fraction of rooms will use large releases (15–25 GB remuxes)? Every concurrency and host-uplink number in this analysis scales inversely with source bitrate, and a 3× shift in the mix is the difference between two workers and six.

- How many rooms re-watch the same infohash? This drives both the worker cache hit rate and, more importantly, whether R2-side dedup (keying HLS output by infohash) is worth building — it is the single largest available cost reduction at 200 rooms/day.

- What is the actual sustained MB/s of the real remux over a 100 ms RTT link with the tuned h2 window and 2 CustomSource workers? Every capacity, cost and product claim downstream assumes it clears realtime, and nothing in either research sweep measured it.
- Does a deliberate throw from the read closure (epoch abort on seek) leave the shared mediabunny Input usable, or does it poison it? ss builds one Input at clientMedia.ts:82 and reuses it at :486 across every region restart, so if an aborted read fails the Input permanently, the epoch-abort mechanism is unusable and Input.dispose()+rebuild is forced — with the cost of losing the read cache and re-sniffing the container on every seek.
- Which component enforces video-torrents-only when a video torrent legitimately contains non-video sidecars (subtitles ride the same range reads, with no separate /read-file endpoint)? The list_only intake gate must admit them without becoming a general file-serving proxy.
- When a worker is taken down by an abuse notice mid-room, what is the user-visible behaviour and how fast? Failover is described as a cold restart on a new worker seeded with initial_peers pointing at the draining old worker — but a seized or suspended VPS is not draining, it is gone, and the placement table, the DNS record and the ticket audience all point at it.
- For the single-box self-host, does the worker bind to 127.0.0.1 (proxy-only) or 0.0.0.0 (direct), and who decides — the operator via config, or the server based on whether a cert was obtained? The readBase indirection covers the URL but not the bind address or the auth-model switch between same-origin cookies and cross-origin tickets.
- Is there any intent to front workers with a CDN later? Ticket-in-path makes every URL unique per room and epoch, which is correct for security and fatal for cache reuse — worth deciding now, because it constrains the URL layout, not just the auth.
