SUMMARY: Server-side torrenting in this repo was never anacrolix/torrent — it was a Node.js `webtorrent` sidecar (`bridge/server.mjs`, `Dockerfile.bridge`, compose service `torrent-bridge` on an isolated network) fronted by three small Go files: `internal/torrent/bridge.go` (private HTTP client), `internal/torrent/ingest.go` (the `Ingestor`), and `internal/httpapi/torrent.go` (`POST /api/rooms/:id/torrent`). It was introduced in 1a39bb1 (2026-08-19) and lasted four days. Bytes flowed bridge → one forward-only `/stream` response → Go `PATCH` into this same server's tus endpoint over loopback → growing file on VPS disk → `ffmpeg -i pipe:0` fed by `streamGrowingFile` → HLS fMP4 `event` playlist published to R2. Streaming-while-downloading genuinely worked (`STREAM_START_MB=1`, 4-second preview segments, an e2e test asserting the room is playable before the last byte), but seeking was strictly bounded by how far the remux had got: the playlist grew forward only, and piece priority was one `file.select(0)` plus a critical window trailing a single sequential read pointer. Everything was deleted in one commit, 8abe402 (2026-08-23, −17036 lines), along with the tus path, the ffmpeg queue and the URL ingest. The commit messages of that era record the real pain: a browser round trip capped at 0.49 MB/s up vs 2 MB/s down, a swarm that went to 0 B/s with 35 peers connected between range reads, the idle sweeper deleting rooms out from under live ffmpeg, sibling subtitles overwritten on completion, and a hard ceiling of ~2–4 concurrent rooms.

### The server never used anacrolix/torrent — it used Node webtorrent in a sidecar container
There is no anacrolix reference anywhere in history (`git log --all -S'anacrolix'` returns nothing). Server-side torrenting was a Node.js process: `bridge/server.mjs` (319 lines at removal), built by `Dockerfile.bridge` (node:24-bookworm, `npm ci` against `web/package.json`, so `webtorrent` was a *web* dependency), run as compose service `torrent-bridge` (read_only, cap_drop ALL, no-new-privileges, pids_limit 128, mem_limit 1g, volume `ss-torrent-cache:/cache`, on an isolated docker network `torrent-edge`, `expose: 8090`, never published). Client constructed as `new WebTorrent({ dht: true })` with a hardcoded tracker whitelist (nyaa.tracker.wf, opentrackr, open.stealth.si, exodus.desync, tracker.torrent.eu.org + 3 wss trackers). Caps: MAX_TORRENTS=4, MAX_FILE_BYTES=10 GiB, MAX_READ_BYTES=8 MiB, MAX_SIDE_FILE_BYTES=8 MiB, IDLE_MS=10 min idle sweeper, 30 s metadata timeout, magnet sanitized to xt+dn+whitelisted trackers only (`safeMagnet`).

### How bytes actually flowed: bridge → Go → its own tus endpoint over loopback → growing file → ffmpeg stdin
The ingest deliberately did NOT write the file itself. `Ingestor.pump` opens `POST /api/torrent-bridge/stream` on the bridge and pipes that body straight into an HTTP `PATCH` on `http://127.0.0.1:{PORT}/api/upload/{id}` with `Tus-Resumable: 1.0.0`, `Content-Type: application/offset+octet-stream`, `Upload-Offset`, and an explicit `request.ContentLength = job.Size - offset` ("declaring the length keeps the request out of chunked encoding and lets the store detect a truncated stream"). Comment in ingest.go: "Going back out through tus rather than writing the file directly is what keeps this small: the upload reservation, the progress ticks that start the preview, the completion hand-off to the media queue and the sweeper that reclaims abandoned transfers are all the ones that already exist." tusd wrote a growing file under `{DATA_DIR}/rooms/{id}/`; `media.Progressive` (internal/media/progressive.go, 800 lines) then ran `streamGrowingFile()` into `exec.Command("ffmpeg", BuildProgressiveRemuxArgs("pipe:0", hlsDir, probe)...)` — a blocking stdin feeder that treats temporary EOF as "wait 100 ms and read more" instead of end-of-input. On error the ingest re-reads the authoritative offset with a tus `HEAD` (`uploadOffset`) using `context.WithoutCancel`, so a broken stream resumes from what the store confirmed, not what the bridge had handed over.
sources: git show 8abe402^:internal/torrent/ingest.go; git show 8abe402^:internal/media/progressive.go; git show 8abe402 -- cmd/server/main.go

### Piece priority: whole-file low-priority select + a critical window that follows a single sequential read stream
`selectFile()` in bridge/server.mjs deselects every file then calls `file.select(0)` — whole file, priority 0 — and `streamSelectedFile()` returns `file.createReadStream({ start })`. The comment added in 1a39bb1 states the mechanism precisely: "one iterator selects every remaining piece at once and keeps `critical` on the few just past the read pointer. Byte-range reads can only ever select the range they were asked for, so between two of them the swarm has nothing selected and stops downloading entirely." Only ONE read pointer existed per session, always moving forward. There was no play-head-driven prioritization and no way to move the critical window backwards or to a seek target — the design assumption was strictly sequential ingest.
sources: git show 1a39bb1 -- bridge/server.mjs; git show 8abe402^:bridge/server.mjs

### Stable-era streaming: yes it played while downloading, and there was an integration test asserting exactly that
`STREAM_START_MB=1` (config.go, removed in 8abe402): after 1 MiB landed, tus callback `OnStreamStart: progressive.Submit` fired. Progressive probed the growing file (`probeGrowingFile`, 500 ms retry), stored chapters from that first probe, published 4-second fMP4 preview segments (`previewSegmentSeconds = "4"`, files `preview_stream_%v_%06d.m4s` / `preview_init_%v.mp4`, master `master.m3u8`), and flipped the room to `ready` as soon as the *video* variant playlist confirmed by the bucket contained an `#EXTINF`. When the upload completed, `progressive.Complete()` let the preview drain to true EOF, then `media.SubmitAfterPreview` ran the authoritative VOD pass (6 s segments, full `RenditionLadder`, `final_master.m3u8`). The e2e test `TestTorrentPlaysBeforeItFinishesDownloading` in internal/e2e/torrent_integration_test.go asserts `readyAt < info.Size()` and `bridge.streams.Load() == 1` ("the bytes were pulled once, sequentially, by the server").
sources: git show 8abe402^:internal/e2e/torrent_integration_test.go; git show 8abe402^:internal/media/remux.go; git show 8abe402 -- internal/config/config.go

### Seeking in the stable era was NOT free — the timeline only reached as far as the remux had
Both passes emitted `-hls_playlist_type event` (remux.go: "Both passes grow their playlist as they encode. A vod playlist is only written once ffmpeg finishes"). The player's `seekMax = Math.max(duration, 1)` came from the growing playlist, so the scrubber literally could not address bytes that had not been downloaded and remuxed yet. Commit a01b0c4 records the side effect: "A growing playlist also carries no ENDLIST, so hls.js reads it as live and recovers a stall by seeking to the newest segment — throwing the viewer to the end of what was just published." Free seeking only arrived later, on the client pipeline, in bc6fb36 "the room's timeline is whole from the start, and seeks lead the remux": "The pipeline used to convert the source strictly start to end, so the scrubber only reached as far as the remux had, and pulling it forward was impossible: the room could not do what any local player does."

### Recorded pain point #1: the browser round trip (why the server took over in the first place)
Commit 1a39bb1 (2026-08-19) message, with production numbers: "A torrent used to reach a room the long way round: the bridge sent 8 MB ranges down to the browser, which sent the same bytes back up over tus. Measured against production, the return leg ran at 0.49 MB/s against 2 MB/s coming down, so a viewer's upstream capped the whole transfer even though the bridge and the API share a host. Worse, a byte-range read can only select the range it was asked for, so between two of them nothing was selected and the swarm stopped entirely: 35 connected peers, 0 B/s, for as long as each PATCH took." (Old browser path: `TORRENT_CHUNK_BYTES = 8 * 1024 * 1024` in web/src/upload.ts; 98cf012 had already added one slot of read lookahead to overlap swarm reads with the in-flight PATCH.)

### Recorded pain point #2: lifecycle collisions — the sweeper killing live downloads
e8706fe (2026-08-20) "fix: stop reclaiming a room out from under the work still running in it" quotes real logs: `23:22:23 idle room reclaimed room_id=3VnEhODJ idle_for=1m30s` / `23:23:56 ERROR upload: move completed upload room=3VnEhODJ err="get room: room not found"` and an ffmpeg that died renaming its own output. ### Sources that could never be previewed, and the guard that detected them
`internal/media/container.go` provided `NeedsWholeFile()` / `ErrContainerUnknown`: an MP4 with a trailing `moov` atom has no decodable prefix, so instead of running an ffprobe every 500 ms for the whole download the pipeline read the first few kilobytes, recognized the layout and set `Preparation.PreviewPhase = room.PreviewUnavailable`. `CheckVideoSupported(probe)` reached the refusal verdict early and called `killRoom` (cmd/server/main.go), "often minutes before the download would have finished paying for a file that can never play". Any revived server-side path needs the equivalent — but note the modern client pipeline already answers this in the browser before a room opens.
sources: git show 8abe402^:internal/media/progressive.go; git show 8abe402 -- cmd/server/main.go

### The exposure surface: a reverse proxy that deliberately withheld the streaming endpoint
`registerTorrentBridge` in internal/httpapi/server.go proxied `/api/torrent-bridge/*path` to `cfg.TorrentBridgeURL` with `httputil.NewSingleHostReverseProxy`, but 404'd `/stream`: "The whole-file stream exists for the server-side ingest, which reaches the bridge directly. Proxying it would hand anyone an unmetered pipe for a 10 GB file over a single request." There was no authentication on the proxied endpoints (`/open`, `/select`, `/stats`, `/files`, `/read`, `/read-file`, `/close`) — any visitor could open a magnet on the VPS's swarm. That is exactly the hole the new signed-job design should close.
sources: git show 8abe402^:internal/httpapi/server.go

### What the current client already needs from a byte source — the contract a Rust worker must satisfy
The live ss-bridge contract (web/src/localHelper.ts, HELPER_ORIGIN `http://127.0.0.1:32227`) is: `GET /health` → `{name:"ss-bridge",version}`; `POST /add {magnet}` → `{id,name,files:[{index,name,path,size}]}`; `POST /select {id,fileIndex}` ("Focus the swarm on this one file, in order"); `GET /stream/{id}/{fileIndex}` with a `Range: bytes=a-b` header, which BLOCKS until those bytes have downloaded and must return exactly `b-a+1` bytes or the client throws `helper short read`; `GET /stats/{id}` → `{peers,downloadSpeed,downloaded,progress}`; `POST /close {id}`. The client-side pipeline (`web/src/pipeline/mediaInput.ts`, added in 8abe402) reads every source through one ranged `MediaInput`, and since bc6fb36 the remux is region-based and seek-led — so random-access ranged reads at arbitrary offsets are ALREADY the access pattern. Free seeking is therefore a property of the byte server's piece prioritization, not of the browser side.
sources: web/src/localHelper.ts; git log -1 bc6fb36

RECOMMENDATIONS:
- Do NOT revive internal/torrent as-is. Its whole shape — one forward-only `Stream(start)` piped into a tus PATCH so a growing file on VPS disk could feed `ffmpeg -i pipe:0` — is structurally incompatible with goal 3 (free seeking) and goal 1 (server never touches media). What is worth reviving is the surrounding discipline, not the pipe: `internal/torrent/bridge.go`'s session model (open/select/stats/files/close with refcounting), the ingest's resume accounting (only a zero-byte run spends an attempt), and the swarm metrics.
- Make the worker a ranged byte server, not a stream server. The current browser already does random-access ranged reads (web/src/pipeline/mediaInput.ts) and seek-led region remux (bc6fb36); it will 'just work' against a worker that implements the existing ss-bridge contract in web/src/localHelper.ts (`/add`, `/select`, `/stream/{id}/{index}` with Range, `/stats`, `/close`, `/health`). Building to that exact contract means the browser side needs almost no change — only the origin becomes remote instead of 127.0.0.1:32227.
- For free seeking, pick an engine whose priority window follows a read cursor rather than one that only selects what was asked for. webtorrent's `arrayBuffer({start,end})` is exactly the anti-pattern documented in 1a39bb1 (35 peers, 0 B/s between reads). In Rust, `rqbit` or `cratetorrent`-style engines, or a custom picker over `librqbit`, should expose: set a play-head offset, keep N MiB critical ahead of it, keep the file selected at low priority everywhere else, and re-point the critical window on seek instead of restarting. Serve a Range request by parking on those pieces.
- Keep the file-size / file-identity check on the server side of trust. 295d98c exists because a browser-supplied size created an upload that could never complete; the equivalent in the new design is: the signed job names the info hash and file index, and the worker refuses to serve any other file of that torrent.
- Sign the job payload, not just the request: `{infoHash, fileIndex, roomID, workerID, notBefore, notAfter, nonce}` with Ed25519, and have the worker verify against a server public key pinned at enrollment. Note that the old `/api/torrent-bridge/*` reverse proxy (internal/httpapi/server.go) had no auth at all — anyone could open a magnet on the VPS swarm. That is the exact regression to avoid.
- Reuse the removed metric names so the Grafana work is not lost: `ss_torrent_bytes_downloaded_total`, `ss_torrent_ingests_active`, `ss_torrent_ingests_total{outcome}`, `ss_torrent_peers` (internal/metrics/metrics.go at 8abe402^, all with PromQL in the doc comments). Add per-worker labels but keep peers summed — the old comment explains why room IDs are unbounded cardinality.
- Read `internal/e2e/torrent_integration_test.go` at 8abe402^ before writing new tests. `TestTorrentPlaysBeforeItFinishesDownloading` (throttled fake bridge at size/8 bytes per tick, asserts ready before the last byte and exactly one stream) is directly portable to 'room plays before the torrent finishes, and a seek to 20:00 is served without downloading 0:00–20:00'.
- Carry over the lifecycle lesson from e8706fe: a room must be held while its source is still arriving, and the worker's session must outlive neither the room nor a host reload. The old 10-minute IDLE_MS sweeper in bridge/server.mjs plus the refcounted `sessions`/`torrents` maps are a reasonable starting shape, but the hold must be driven by the room's live state, not by wall-clock idleness alone.

OPEN_QUESTIONS:
- Does the direction want the worker to serve raw torrent bytes over ranged HTTP to the HOST'S BROWSER (worker as a remote ss-bridge, browser still remuxes — matches goal 1 and the existing MediaInput contract), or to serve them to the SERVER which then proxies? The first keeps the VPS out of the byte path entirely; the second reintroduces the 2026-08 bandwidth bill. Nothing in history answers this because the old design always terminated bytes on the VPS.
- If the worker serves the browser directly, it needs a public TLS endpoint and CORS — the whole ss-bridge design leans on loopback + Local Network Access to avoid that. What is the intended transport (worker-initiated tunnel through the server? per-worker hostname? WebSocket relay?), and does the browser's mixed-content rule force TLS on every worker?
- 'Workers must ONLY download video torrents, nothing else' — how is that enforced? The old bridge enforced only shape (`safeMagnet` regex, MAX_FILE_BYTES 10 GiB, `VIDEO_EXTENSION` filter in the browser). A worker cannot know a magnet is a video before metadata arrives; enforcement can realistically only be 'after metadata, refuse if no file matches the video extension whitelist, and only ever serve those file indices'.
- What signs the job — the server with one key, or the room host? If the server signs, a worker cannot tell an abusive user from an abusive server operator; if the host signs, the server must publish host public keys. Also unresolved: replay protection (nonce/expiry in the signed payload) and revocation.
- Does the R2 bucket's egress/CORS policy still hold if workers, rather than the host browser, ever need to PUT? Currently the CORS policy (client-pipeline plan, 2026-08-22) allows PUT only from ss.giuli.dev / ss-beta.giuli.dev / localhost:5173.
- What is the intended failure mode when the host's tab closes mid-preparo? 675a0b5 made a reloaded host resume the preparo; with a worker holding the swarm, the worker becomes a resource that must be reclaimed on room death (the old bridge used a 10-minute idle sweeper, which is what e8706fe showed is not enough on its own).

AGENT: current:seek-pipeline
================================================================================
SUMMARY: Today a seek is a room-wide WebSocket command that the host's remux worker treats as a request to throw away its current conversion and restart it at the target keyframe: player -> `seek` WS frame -> hub -> `sync.state` -> Room.tsx `follow()` -> worker postMessage -> `ClientRemuxHandle.follow` -> `uncovered()` -> `restartAt()` -> cancel + abort uploads + `getKeyPacket` snap -> a new `Conversion` with `trim.start` -> a new `r{N}_`-prefixed HLS region -> publish -> `SetMediaOffset` bumps media_version -> every player rebuilds hls.js at the new offset. Crucially, mediabunny does NOT read the source sequentially: `MediaInput`/`CustomSource` is a random-access `read(start,end)` contract, the demuxer seeks by Matroska cues, and a local patch-package patch already makes trimmed regions start at an arbitrary keyframe by copy instead of re-encode (96s -> 2.4s to a served master). The sequential assumptions live elsewhere: ss-bridge's `/select` sets in-order whole-file priority and the web side has no way to hint a playhead; reads are unabortable, strict-full-length blocking fetches; the embedded-subtitle pass walks the entire file front-to-back in 8 MiB slices beside the remux; and the pipeline/server/player triple only ever represents ONE contiguous playable region (playlists.clear(), a single scalar mediaOffsetMs, and a server renderer that truncates a playlist at its first unconfirmed segment). So the demux/remux half of free seeking already works; what blocks it is the byte-priority contract with the bridge and the one-region-at-a-time publishing model — with the encouraging detail that dead regions' segments already persist in R2 and the server already allows the HLS tags (DISCONTINUITY, MAP, GAP) a stitched sparse timeline would need.

### Seek flow, end to end (today)

### The region restart itself
clientMedia.ts:418-423 `uncovered()` decides: a position < regionStart - 1s (COLD_BEHIND_MS, line 142) or > max(producedEnd, regionAim) + 30s (COLD_AHEAD_MS, line 139) triggers `restartAt()` (lines 424-440). restartAt: clears `pending`, aborts every in-flight PUT AbortController, `await conversion.cancel()`, then `snapToKeyframe()` (lines 391-398, `EncodedPacketSink.getKeyPacket(seconds, {verifyKeyPackets:true})`) — the ordering is commit e2f4b43 ("the dying region yields before the seek's keyframe snap"). RECOMMENDATIONS:
- Treat the byte layer and the region layer as two separate problems. The byte layer (bridge/worker) needs a playhead-priority API; the region layer (clientMedia.ts + publisher.go + Player.tsx) needs to stop collapsing the timeline to one contiguous region. Fixing only one gives nothing.
- For the new server-side worker, define the fetch contract as: (1) ranged reads with an explicit deadline/priority class, (2) an out-of-band `POST /priority {fileId, byteOffset, windowBytes}` that moves the piece-picker window without issuing a read, and (3) cancellable reads (the client passes a request id it can abort). All three are missing today and each maps to a concrete pain point above (localHelper.ts:276, remuxJob.ts:99, conversion.ts:1283).
- Have the pipeline call that priority hint from `restartAt` (clientMedia.ts:424) BEFORE `snapToKeyframe`: translate the seek target's timestamp to an approximate byte offset (duration/size ratio is good enough as a first hint, cues give the exact one) so the swarm starts fetching while the keyframe probe is still resolving.
- Pass an AbortSignal down MediaInput.read and wire it to the region restart, so the dead region's blocked bridge fetch dies with it instead of pinning one of the two CustomSource workers (remuxJob.ts:95-119, mediaInput.ts:34-53). This likely needs either a mediabunny option or an extension of the existing patch-package patch.
- Kill or restructure the full-file subtitle pass (remuxJob.ts:180-190) before attempting free seeking: either extract embedded subtitles only from the bytes the remux is already pulling, or defer it until the file is fully downloaded, or move it to the server-side worker which has the whole file on disk anyway.
- For the playlist model, prototype a sparse/stitched master: keep every region's variant playlist, and have the host publish one media playlist per rendition that concatenates the regions it owns with #EXT-X-DISCONTINUITY + per-region #EXT-X-MAP. The tags are already allowed (internal/media/clientmedia.go:66-81); the blocker is renderPlaylistWithBase's cut-at-first-hole rule (internal/media/publisher.go:182-225), which would need to emit #EXT-X-GAP or skip a hole instead of truncating.
- That change also retires mediaOffsetMs as a scalar (Player.tsx:125, useSync.ts:74, store.go:452): with a stitched playlist the element clock is the room clock again, and the hls.js rebuild on every region change (Player.tsx:386-393) disappears along with the cold-seek parking hack (Player.tsx:456/508-529).
- Keep the mediabunny patch in view when evaluating alternatives: the whole cold-seek cost model in this repo was set by whether trimmed conversions copy or re-encode. Any replacement remuxer must be benchmarked on 'time to first segment when starting at minute 40 of a 3-hour file', not on throughput.
- For the signed-job design, note the existing shape to imitate: the client-media claim/presign/publish trio already treats the browser as untrusted and validates every name against a regex grammar before signing anything (internal/media/clientmedia.go:37-58, 'The name grammar is the authorization'). The worker protocol should follow the same rule — the signature authorizes a narrowly-shaped job (one infohash, one file index, one byte window), not an arbitrary command.

SUMMARY: All three families solve "watch while downloading with free seeking" the same way at the HTTP layer — a plain `206 Partial Content` byte-range server in front of a torrent engine, with the player's `<video>`/ffmpeg doing normal range seeking — but they differ sharply in how a range request is translated into piece priority. Stremio (enginefs + a private fork of mafintosh/torrent-stream) uses a *priority-sorted selection list plus a "critical" flag on the 1–4 pieces at the play head*, and in its RAM-only mode adds a true sliding window (`selection.selectTo = piece + buffer/pieceLength`) over a circular memory buffer, plus "virtual pieces" (512 KiB sub-pieces of the real piece) so the play head advances in finer steps. TorrServer wraps anacrolix/torrent and instead runs a *multi-reader model*: one HTTP request = one `torrstor.Reader`, each reader owns a window `[pos − cap/N·(1−p), pos + cap/N·p]` (p = `ReaderReadAHead`, default 95 %), and a cache janitor re-stamps anacrolix's `PiecePriorityNow/Next/Readahead/High/Normal` ladder across all live readers while evicting everything outside the merged windows except a pinned head/tail. WebTorrent/peerflix are the minimal version of the Stremio scheme (sequential strategy + `critical()` over ≤2 pieces, no window cap, no cache eviction). The hard-won lessons are all in the seams: bounded caches that lie to the engine about piece completeness (anacrolix #471), priority sets that get cleared and never re-armed (TorrServer's `priorityWatchdog`), slow peers that squat on the highest-priority chunks and are never preempted (anacrolix #698), and MP4s whose `moov` atom lives at EOF so the tail must be fetched and pinned before playback can start.

### Stremio: HTTP layer is dumb byte-range serving, one FileStream per request
enginefs.js `handleTorrent` parses `Range` with `range-parser`, sets `Accept-Ranges: bytes`, `Content-Type` from `mime.lookup`, `206` + `Content-Range`, and pumps `handle.createReadStream({start,end})` into the response (enginefs.js:494-524). There is no remux and no HLS in enginefs itself — it is raw file bytes. Each range request creates a *new* FileStream with its own selection; `file.createReadStream` wraps it in `eos(stream, () => engine.deselect(stream.selection))`, so an abandoned seek's selection is dropped when the socket closes. A seek is therefore literally: new HTTP request → new selection at the new piece → old selection removed on close. Routes: `GET /:infoHash/:idx`, `GET /:infoHash/:idx/*`, `ALL /:infoHash/create`, `ALL /create`, `GET /:infoHash/stats.json`, `GET /:infoHash/:idx/stats.json`, `GET /stats.json`, `GET /:infoHash/remove`, `GET /removeAll` (enginefs.js:346-530). A per-request priority can be forced with the `enginefs-prio` request header (`opts.priority = parseInt(req.headers['enginefs-prio'])`, enginefs.js:511).
sources: https://github.com/Stremio/enginefs/blob/master/enginefs.js

### Stremio: open-ended Range ("bytes=N-") triggers a whole-file low-priority prewarm
`if (range && range.endsWith('-')) { if (!defaults.circularBuffer) prewarmStream(...) }` (enginefs.js:494-498). `prewarmStream` calls `engine.files[idx].select()` which does `engine.select(offsetPiece, endPiece, false)` — a *non-priority* selection over the whole file, so the disk-cache build keeps filling the file in the background behind the play-head selection. It is deliberately skipped in circular-buffer (RAM) mode because there is nowhere to put the data.
sources: https://github.com/Stremio/enginefs/blob/master/enginefs.js

### torrent-stream (upstream) piece prioritization: selection list + critical flag, no deadlines
`engine.select(from,to,priority,notify)` pushes `{from,to,offset,priority,notify}` and re-sorts descending by priority (index.js:639-654). The requester `select(wire, hotswap)` walks selections in priority order and, within each, pieces from `next.from + next.offset` upward — i.e. strictly sequential inside a selection (index.js:390-411). `gc()` advances `s.offset` past completed pieces and splices exhausted selections (index.js:201-219). `engine.critical(piece, width)` sets `critical[i]=true` (index.js:635-637); the only consumer is `onrequest(wire, j, critical[j] || hotswap)` — critical pieces are allowed to *preempt* (hotswap) blocks already reserved by a slower peer. Constants: `MAX_REQUESTS = 5`, `SPEED_THRESHOLD = 3 * BLOCK_LENGTH` (≈48 KiB/s), `CHOKE_TIMEOUT = 5000`. There is no per-piece deadline anywhere; the closest analogue is `speedRanker(wire)`, which makes a slow peer skip a piece if a faster peer that has it could finish the remaining bytes sooner (index.js:352-378), and `onhotswap`, which cancels a slow peer's outstanding blocks for a piece so a fast peer can take them (index.js:237-270).
sources: https://github.com/mafintosh/torrent-stream/blob/master/index.js

### torrent-stream: the play head marks pieces critical on every read attempt
lib/file-stream.js: `this._critical = Math.min(1024*1024 / pieceLength, 2) | 0`; `notify()` does `if (!engine.bitfield.get(this._piece)) return engine.critical(this._piece, this._critical)` and otherwise reads piece `this._piece++`. So the critical window is re-armed at the *current* play head each time the reader stalls, and slides forward one piece per read. Piece mapping from the range: `startPiece = (opts.start + file.offset)/pieceLength | 0`, `endPiece = (opts.end + file.offset)/pieceLength | 0`.
sources: https://github.com/mafintosh/torrent-stream/blob/master/lib/file-stream.js

### Stremio's private torrent-stream fork adds a real sliding window (selectTo/readFrom)
From the de-webpacked server.js bundle (module 792 = file-stream fork, module 760 = engine fork): `this.bufferPieces = engine.buffer ? engine.buffer / pieceLength | 0 : null`, and on construction and on *every* `_read()` it mutates the live selection: `selection.selectTo = Math.min(endPiece, this._piece + this.bufferPieces); selection.readFrom = this._piece; engine.refresh()`. The engine's request loop honours the cap: `for (j = next.from + next.offset; j <= (next.selectTo || next.to); j++)`. So with `buffer` set, the engine only ever requests within `[playhead, playhead + buffer]`; without it (`selectTo` undefined) the selection runs to the end of the requested range, exactly like upstream. Critical width is widened to `Math.min(1048576/pieceLength, 4)|0`, reads are serialized through `new bagpipe(2)`, and pieces currently being read are pushed onto `engine.lockedPieces` so the cache cannot evict them mid-read. If the play-head piece has fallen outside every selection (post-GC), the stream re-selects `[piece, selection.to]` at priority true before waiting.
sources: https://github.com/goofw/sw/blob/main/server/0792.js; https://github.com/goofw/sw/blob/main/server/0760.js

### Stremio: "virtual pieces" — internally re-piece the torrent at 512 KiB for finer scheduling
Engine fork, with `opts.virtual: true` (Stremio's default): `pieceLength = torrent.pieceLength > 524288 && torrent.pieceLength % 524288 == 0 ? 524288 : torrent.pieceLength`; `verificationLen` keeps the real piece length; `mapPiece(index) = Math.floor(index * torrent.pieceLength / verificationLen)`. Wire requests are translated back (`pos = index*pieceLength + offset; index = pos/verificationLen | 0; offset = pos % verificationLen`), peer bitfields are consulted via `mapPiece(j)`, and SHA-1 verification still happens on the real piece, emitting `verify` for every virtual sub-piece. Net effect: on a torrent with 4 MiB pieces the scheduler, the critical window, the sliding window and the `have` bookkeeping all operate at 512 KiB granularity, which shortens time-to-first-byte after a seek by up to 8x.
sources: https://github.com/goofw/sw/blob/main/server/0760.js

### Stremio: RAM-only mode = 15 MiB sliding window over a 45 MiB circular buffer
Server init (module 518): defaults are `{connections: 35, handshakeTimeout: 20000, timeout: 4000, virtual: true, swarmCap: {minPeers: 5, maxSpeed: 1677721.6}, growler: {flood: 0, pulse: 2621440}}`; and when `--no-cache` or `cacheSize == 0`: `defaults.buffer = 15728640` (15 MiB window), `defaults.circularBuffer = {type:'memory', size: 47185920}` (45 MiB ring), `defaults.swarmCap = {minPeers: 5, maxBuffer: 0.75}`. The engine throws `"circularBuffer can only be used with buffer"` — the window is mandatory when the store is bounded. The ring (module 791) allocates `size/pieceLength` slots and, on write, evicts the least-recently-accessed slot that is `committed && !isPieceSelected(idx) && !engine.lockedPieces.includes(idx)`, where `isPieceSelected` tests `p >= sel.readFrom && p <= sel.selectTo`. If nothing is freeable it throws `"circular buf is full, unable to free"`. Evicting also calls `engine.resetPiece(idx)` so the engine's bitfield stops claiming the piece is present — the exact bug class that bites TorrServer (see anacrolix #471).
sources: https://github.com/goofw/sw/blob/main/server/0518.js; https://github.com/goofw/sw/blob/main/server/0791.js

### Stremio: swarm capping / rate pulsing so streaming doesn't run at line rate
`updateSwarmCap(e, opts)` pauses the swarm when `downloadSpeed() > maxSpeed` (or `calcBuffer(e) > maxBuffer`, i.e. ring more than 75 % ahead) *and* more than `minPeers` unchoked wires exist, resuming otherwise (enginefs.js). Independently the engine's requester bails out with `if (swarm.downloaded > engine._flood && swarm.downloadSpeed() > engine._pulse) return true`. Defaults: soft limit 1.6 MiB/s, hard/pulse limit 2.5 MiB/s. This is what stops a 45 MiB ring from being overrun and keeps the tail of the window from being wasted after a seek.
sources: https://github.com/Stremio/enginefs/blob/master/enginefs.js; https://github.com/goofw/sw/blob/main/server/0518.js

### Stremio: MP4/MKV handling is client-driven probe → direct range play or /hlsv2 transcode
stremio-video's `withStreamingServer` builds the torrent URL as `{server}/{infoHash}/{fileIdx}?tr=...` (createTorrent.js), optionally POSTing to `{server}/{infoHash}/create` with `{torrent, peerSearch, guessFileIdx:{season,episode}}` to pick the episode file. It then calls `GET {server}/hlsv2/probe?mediaURL=<the range URL>` and plays the URL *directly in `<video>`* only if `isFormatSupported && areStreamsSupported && !hasEmbeddedSubtitles && supportedAudioTracks.length < 2`; otherwise it plays `{server}/hlsv2/{id}/master.m3u8?mediaURL=...&forceTranscoding=1`. So: no server-side remux on the direct path (byte ranges straight to the media element), and MKV/embedded-subtitle/multi-audio files fall back to server-side ffmpeg HLS where seeking becomes time-based rather than byte-based.
sources: https://github.com/Stremio/stremio-video/blob/master/src/withStreamingServer/withStreamingServer.js; https://github.com/Stremio/stremio-video/blob/master/src/withStreamingServer/createTorrent.js

### TorrServer: HTTP layer is http.ServeContent over an io.ReadSeeker — one Reader per request
`(*Torrent).Stream` creates `reader := t.NewReader(file)`, optionally `reader.SetResponsive()` when `BTsets.ResponsiveMode` (default true), sets ETag/DLNA headers, then hands everything to `http.ServeContent(resp, req, file.Path(), ts, reader)` and `defer t.CloseReader(reader)` (server/torr/stream.go). All Range parsing, 206/416 handling and multipart-range refusal is Go stdlib. Consequence: a player seek = a new HTTP request = a brand-new `torrstor.Reader` at the new offset, and the old reader is closed when its response ends. `t.CloseReader` also extends the torrent's `expiredTime` by `TorrentDisconnectTimeout` (default 30 s) so the torrent isn't dropped between seeks.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/stream.go; https://github.com/YouROK/TorrServer/blob/master/server/torr/torrent.go

### TorrServer: the per-reader window is cache-capacity-relative and split by ReaderReadAHead %
server/torr/storage/torrstor/reader.go `getOffsetRange()`: `prc = BTsets.ReaderReadAHead` (default 95, clamped 5..100); `readers = max(1, cache.GetUseReaders())`; `begin = pos − (capacity/readers)*(100−prc)/100`, `end = pos + (capacity/readers)*prc/100`, clamped to the file. With the default 64 MiB cache, 95 % and one reader that is ≈3.2 MiB behind the play head and ≈60.8 MiB ahead — the behind-part is what makes small backwards seeks instant. The window is expressed in *pieces* via `getPiecesRange()` → `Range{startPiece, endPiece, file}` using absolute torrent offsets (`(offset + file.Offset()) / pieceLength`). Two readers halve each other's window. Separately `updateRA()` runs every progress tick and calls `cache.AdjustRA(16<<20)` — a fixed 16 MiB anacrolix readahead on every reader (the old peers×pieceLength heuristic is commented out), and if `CacheSize == 0` the capacity itself becomes `readahead*3`.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/reader.go; https://github.com/YouROK/TorrServer/blob/master/server/torr/torrent.go

### TorrServer: the priority ladder, re-stamped for every live reader
`Cache.setLoadPriority(ranges)` (torrstor/cache.go) iterates live readers and, for each, walks from `readerPos` to the window end assigning anacrolix priorities to *incomplete* pieces: `i == readerPos` → `PiecePriorityNow`; `i == readerPos+1` → `PiecePriorityNext`; `readerPos < i <= readerRAHPos` → `PiecePriorityReadahead`; `readerRAHPos < i <= readerRAHPos+5` → `PiecePriorityHigh`; beyond → `PiecePriorityNormal`. Crucially it is throttled: `count := BTsets.ConnectionsLimit / len(readers)` (default 25) incomplete pieces get a priority per pass — i.e. concurrency-bounded, not window-bounded. `clearPriority()` first sets every piece outside the merged reader ranges to `PiecePriorityNone`. Both are serialized under `muPrio`. `mergeRange()` (ranges.go) sorts and coalesces overlapping reader windows so two readers on the same file don't double-count.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/cache.go; https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/ranges.go

### TorrServer: eviction pins the head and tail of the file (the moov-atom fix)
`Cache.getRemPieces()` collects the merged live-reader ranges, then marks for removal every piece with `Size > 0` that is `!inRanges(...)` **and** `!isIdInFileBE(...)`. `isIdInFileBE` protects `FileRangeNotDelete = max(pieceLength, 8<<20)` bytes at the *start* and at the *end* of each open file. Removal candidates are sorted by `Accessed` (LRU) and `cleanPieces()` drops just enough of them to get `filled` back under `capacity`. `setLoadPriority` also skips a reader whose current piece is inside the pinned head/tail region. Net effect: MP4 tail (`moov`), MKV cues/seekhead and container header survive any amount of seeking around the middle of the film.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/cache.go

### TorrServer: preload = head-of-file reader + a concurrent tail reader
`(*Torrent).Preload(index, size)` sets `startend = max(pieceLength, 8<<20)`, then runs two `file.NewReader()`s with `SetResponsive()` in parallel: the *end* reader seeks to `file.Length() − startend` and drains to EOF; the *start* reader reads `[0, size − startend)` with `SetReadahead(pieceLength*4)`, dropping readahead to 0 as it approaches the end of its range. Preload size comes from `apihelper.Preload`: `size = CacheSize * PreloadCache / 100` (defaults 64 MiB × 50 % = 32 MiB), clamped to `CacheSize`. If ffprobe is available it probes `http://127.0.0.1:{port}/play/{hash}/{index}` during preload to record `BitRate`/`DurationSeconds`. Status is exposed as `PreloadedBytes`/`PreloadSize` in the torrent state.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/preload.go; https://github.com/YouROK/TorrServer/blob/master/server/torr/apihelper.go

### TorrServer: idle-reader parking and the API surface
`Reader.checkReader()` parks a reader (`readerOff`: `SetReadahead(0)` and seek back to 0, so it stops claiming priority) if it hasn't been read for 60 s *and* another reader exists; any Read/Seek calls `readerOn()` to restore position and readahead. `Cache.GetUseReaders()` counts only live ones, and that count is what divides the per-reader window and the priority budget. API (server/web/api/route.go): `GET|HEAD /stream` and `/stream/*fname` with query params `link`, `index`, `play`, `preload`, `stat`, `save`, `m3u`, `fromlast`, `title`, `poster`, `category`; `GET|HEAD /play/:hash/:id`; `POST /torrents` (add/get/list/rem/drop), `POST /cache` (cache state incl. per-piece `Priority` and per-reader `{Start,End,Reader}`), `POST /settings`, `GET /playlist`, `GET /ffp/:hash/:id`. Settings that matter: `CacheSize` (64 MiB), `PreloadCache` (50 %), `ReaderReadAHead` (95 %), `ConnectionsLimit` (25), `ResponsiveMode` (true), `UseDisk`/`TorrentsSavePath`/`RemoveCacheOnDrop`, `TorrentDisconnectTimeout` (30 s).
sources: https://github.com/YouROK/TorrServer/blob/master/server/web/api/route.go; https://github.com/YouROK/TorrServer/blob/master/server/settings/btsets.go; https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/reader.go

### anacrolix/torrent's own reader semantics that TorrServer sits on top of
`reader.Seek` sets `r.reading = false` and `contiguousReadStartPos = newPos`, then `posChanged()`; `piecesUncached()` returns `[pos, pos+readahead)` in pieces but forces `ra = 0` when `!r.reading` — so a fresh reader or a just-seeked reader requests exactly one piece until the first Read arrives, which is precisely the anti-thrash behaviour you want on a scrub. `Torrent.readerPosChanged(from,to)` recomputes `_readerNowPieces`/`_readerReadaheadPieces` and re-prioritises only the affected ranges (two disjoint ranges if the seek jumped far). `Piece.purePriority()` raises to `PiecePriorityNow` for the reader's current piece and `PiecePriorityReadahead` for the rest of the window, then `ret.Raise(p.state().priority)` — meaning TorrServer's explicit `SetPriority` calls *max* with, not replace, the built-in reader priorities. `SetResponsive()` makes `available()` stop requiring `pieceComplete`, so bytes are served from an unverified piece as soon as the chunks are in — this is what makes TorrServer's time-to-first-frame short with large pieces. `updatePieceCompletion` refreshes completion for the whole readahead window on a read error, the fix for the bounded-cache stall.
sources: https://github.com/anacrolix/torrent/blob/master/reader.go; https://github.com/anacrolix/torrent/blob/master/torrent.go; https://github.com/anacrolix/torrent/blob/master/piece.go

### WebTorrent: same selection/critical design, plus an explicit rarest-vs-sequential switch
`lib/file-iterator.js` mirrors torrent-stream: `_criticalLength = Math.min((1024*1024/pieceLength)|0, 2)`, `_torrent._select(startPiece, endPiece, 1, null, true)` on construction, `_torrent.critical(index, index + this._criticalLength)` whenever the needed piece is missing, `_torrent._deselect(startPiece, endPiece, true)` on destroy. `lib/torrent.js`: `this.strategy = opts.strategy || 'sequential'`; `trySelectWire(hotswap)` either walks the selection sequentially or asks `_rarityMap.getRarestPiece(filter)`, and in both cases requests with `self._critical[piece] || hotswap`. Pipeline depth is time-based rather than a fixed 5: `getPiecePipelineLength(wire, PIPELINE_MIN_DURATION=0.5s / PIPELINE_MAX_DURATION=1s, pieceLength)`. `lib/server.js` is the same `range-parser` → 206 → `file[Symbol.asyncIterator](range)` shape. peerflix's server is identical in structure (`rangeParser`, `206`, `file.createReadStream(range)`).
sources: https://github.com/webtorrent/webtorrent/blob/master/lib/file-iterator.js; https://github.com/webtorrent/webtorrent/blob/master/lib/torrent.js; https://github.com/webtorrent/webtorrent/blob/master/lib/server.js; https://github.com/mafintosh/peerflix/blob/master/index.js

### Pitfall: a bounded cache that lies about piece completeness stalls every backwards seek
TorrServer #79 ("cache breaks when you seek back 5 minutes after watching 15") was traced by YouROK to anacrolix/torrent #471: "When reader seek start and begin read, client read piece as complete, but buffer is nil and completions impl sets to false. My piece return eof and client not readahead. Client read and reload torrent only in reader piece position." I.e. once your storage evicts a piece the engine still believes is complete, the reader gets EOF, the readahead window collapses to a single piece, and playback crawls. anacrolix's fix direction was to refresh completion for the entire readahead window on a read error (now in `reader.updatePieceCompletion`). Stremio dodges the same trap by calling `engine.resetPiece(idx)` at eviction time in the circular store.
sources: https://github.com/YouROK/TorrServer/issues/79; https://github.com/anacrolix/torrent/issues/471; https://github.com/goofw/sw/blob/main/server/0791.js

### Pitfall: cleared priorities that are never re-armed → silent permanent stall
TorrServer's cache.go carries two comments describing production bugs. (1) `priorityWatchdog` — "setLoadPriority is only reached through the cache cleanup path, which is driven by piece reads and writes… Should priorities ever end up cleared while a reader still needs data, nothing is downloaded, so no piece I/O happens, so cleanup never runs and the priorities are never restored — the torrent stalls indefinitely with peers connected." Fix: a 5 s ticker that calls `getRemPieces()` whenever `GetUseReaders() > 0`. (2) `clearPriority` — "This used to sleep for a second before clearing priorities. A reader created during that window could have its PiecePriorityNow/Next/Readahead reset to None right after setLoadPriority had assigned them, starving the player." Fix: a `muPrio` mutex ordering clearPriority against setLoadPriority. Both are exactly the seek path: seek closes the old reader (→ clearPriority) while the new reader is being created (→ setLoadPriority).
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/cache.go

### Pitfall: slow peers squat on the highest-priority chunks
anacrolix/torrent #698, filed from TorrServer: readahead ('R') and high ('H') pieces were completing before the 'Now'/'Next' piece at the cursor. anacrolix: "The newest request algorithm spreads requests out so that no chunk is requested more than once… However it will not reassign blocks unless it has no choice… Even if a slower peer is assigned pieces that are initially at the end of the readahead window, if the reader progresses up to that point and the slow peer is still working, it will now be the one allocated the highest priority blocks and won't relinquish those." Resolved by commits 112e9b2 (reduce stalling-peer impact) and 9cf5f66 (let fast connections steal more requests, especially at higher priorities). torrent-stream/webtorrent solved the same problem years earlier with `speedRanker` + `onhotswap` (cancel a slow peer's blocks on a critical piece) and a hard `REQUEST_TIMEOUT` (Stremio sets it to 4 s) that destroys the wire. libtorrent takes the third approach — `set_piece_deadline` / `torrent::request_time_critical_pieces()`, which sorts peers by estimated queue-drain time and pieces by deadline, and issues redundant requests once a piece exceeds average-time+deviation.
sources: https://github.com/anacrolix/torrent/issues/698; https://github.com/mafintosh/torrent-stream/blob/master/index.js; https://libtorrent.org/streaming.html

### Pitfall: MP4 moov atom at EOF, and container metadata generally
A non-faststart MP4 keeps its `moov` atom at the end, so the demuxer cannot start until it has the tail; a naive sequential-from-byte-0 engine downloads the whole film first. Both mature implementations pre-fetch and pin the tail: TorrServer's `Preload` runs a dedicated end-reader over the last `max(pieceLength, 8 MiB)` and `isIdInFileBE` refuses to evict head or tail pieces; Stremio's OpenSubtitles hasher fetches `bytes=0-65535` and `bytes=len-65536-len-1` with the `enginefs-prio: 10` header, which forces those pieces to the top of the selection list. Note this is not MP4-only — MKV Cues are commonly at EOF too, and MKV additionally forces Stremio into `/hlsv2` transcoding because `hasEmbeddedSubtitles` fails the direct-play check.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/preload.go; https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/cache.go; https://github.com/goofw/sw/blob/main/server/0741.js; https://ffmpeg-cookbook.com/en/articles/ffmpeg-faststart-web-playback/

### Pitfall: badly-behaved players generate request storms on one piece
torrent-stream #158 ("Issues Streaming to VLC"): after a few seeks the read path went into an effective infinite loop. Ivshti's diagnosis: "I've never been a huge fan of the logic in lib/file-stream. It lacks very solid debouncing/queuing. If the player goes insane (possible with VLC) it will generate a lot of reads on one piece." Stremio's fork responds with `this._readpipe = new bagpipe(2)` (max 2 concurrent store reads per stream) and `engine.lockedPieces` so an in-flight read can't have its buffer evicted. Practically, a player seeking rapidly opens and abandons many range requests, so selection/reader teardown must be tied to socket close (`eos()` / `defer CloseReader`) or stale high-priority selections accumulate and fight the live one.
sources: https://github.com/mafintosh/torrent-stream/issues/158; https://github.com/goofw/sw/blob/main/server/0792.js

### Pitfall: sequential selection is a bad swarm citizen
webtorrent #375: the README claimed "seamlessly switches between sequential and rarest-first piece selection strategy" but feross confirmed "the seamless switching code is missing… I can't remember if I never implemented it, or it never got committed." The stated intent is the right design: run rarest-first while the buffer ahead of the play head is healthy, and only fall back to sequential/critical when the buffer runs low. Today `strategy` defaults to `'sequential'` and never switches on its own. Stremio's practical mitigation is different — it caps download rate (soft 1.6 MiB/s, hard 2.5 MiB/s) and pauses the swarm once the ring is 75 % ahead, which limits how much of the swarm's capacity a sequential streamer consumes.
sources: https://github.com/webtorrent/webtorrent/issues/375; https://github.com/goofw/sw/blob/main/server/0518.js

### Pitfall: sparse files vs per-piece files on disk
torrent-stream/Stremio's disk store writes one file per torrent file under `{cachePath}/{fileIndex}` and seeks to the right offset, which produces large sparse files — on filesystems without sparse support (or when a player/AV tool reads the file directly) the apparent size is the full file even when 2 % is present, and `stat` size is useless as a progress signal. Stremio compensates with an explicit per-file `verified` bitfield persisted at `{path}/bitfield`, and on startup invalidates the bitfield for any file index whose backing file is missing. TorrServer's disk mode avoids sparse files entirely: `UseDisk` writes one file *per piece* into `{TorrentsSavePath}/{infohash}/` (a `.tsc` directory), so eviction is `os.Remove(piecePath)` and `RemoveCacheOnDrop` is a directory delete. If you want reliable resumability, persist an explicit completion bitmap rather than inferring it from file length.
sources: https://github.com/YouROK/TorrServer/blob/master/server/torr/storage/torrstor/cache.go; https://github.com/goofw/sw/blob/main/server/0760.js

RECOMMENDATIONS:
- Adopt the TorrServer shape as the skeleton: HTTP request → dedicated Reader object → stdlib range serving over an io.ReadSeeker. It gives you correct 206/416/If-Range handling for free and makes 'seek = new reader at new offset' the natural model, with reader lifetime bound to the response.
- Do not model a single global 'play head'. Model N live readers, merge their piece windows (TorrServer's `mergeRange`), and divide both the cache budget and the request-concurrency budget by the number of *active* readers. Park readers that haven't been read in ~60 s instead of deleting them, so a paused second audio/subtitle stream stops competing without being torn down.
- Make the window asymmetric around the play head — keep a small behind-margin (TorrServer: 5 % of the per-reader budget, ≈3 MiB at defaults). Short backwards scrubs are the single most common seek and they should never hit the network.
- Implement a priority ladder, not a binary select: Now (current piece) > Next (+1) > Readahead (window) > High (a few beyond) > Normal, and None for everything outside every reader's window. Cap how many *incomplete* pieces get a non-Normal priority per pass (TorrServer uses `ConnectionsLimit / readers`) so you don't flatten the priority signal across a 60 MiB window.
- Copy the two hard-won correctness rules from torrstor/cache.go verbatim: (a) serialize clear-priorities against set-priorities with one mutex — a seek's teardown must never race ahead of the new reader's setup and zero its priorities; (b) run a watchdog ticker (5 s) that re-arms priorities whenever readers are live, because any priority-update path driven only by piece I/O deadlocks the moment priorities are lost.
- When you evict from a bounded cache, you MUST tell the engine the piece is gone (Stremio's `engine.resetPiece`, anacrolix's `UpdateCompletion`). Otherwise the reader gets EOF on a piece the engine thinks is complete, readahead collapses, and every backwards seek stalls (anacrolix #471).
- Pin the first and last max(pieceLength, 8 MiB) of every open file against eviction, and prefetch the tail before or concurrently with the head. This is the whole answer to non-faststart MP4 `moov` atoms and to MKV Cues at EOF.
- Add a preemption mechanism, because priority alone does not reclaim already-issued requests. Either torrent-stream's hotswap (cancel a slow peer's blocks on a critical piece and reissue to a fast one, gated on `downloadSpeed()` and a `SPEED_THRESHOLD`), or libtorrent's deadline model (rank peers by estimated queue-drain time, allow duplicate requests once a piece exceeds mean+deviation). Also keep an aggressive per-request wire timeout — Stremio uses 4 s.
- If your torrents have large pieces (4–16 MiB is common on private trackers), steal Stremio's virtual-piece trick: schedule and prioritize at 512 KiB granularity, translate offsets on the wire, verify at the real piece boundary. It is the cheapest large win on time-to-first-frame after a seek.
- Serve unverified-but-present chunks (anacrolix `SetResponsive`) rather than waiting for a full-piece SHA-1, and keep the block scheduler from stalling: mark the play-head piece critical on every failed read, not once per stream, so the critical flag tracks the head as it slides.
- Do not run at line rate. Cap download speed and/or pause the swarm once the window is ~75 % filled ahead of the play head — a filled window that gets thrown away at the next seek is pure waste, and unbounded sequential downloading is what makes streaming clients bad swarm citizens (webtorrent #375).
- Keep the media-format decision on the client: expose a probe endpoint (Stremio's `/hlsv2/probe?mediaURL=`) and only fall back to server-side transcode/remux when the container, codecs, embedded-subtitle presence or audio-track count fail the direct-play test. Direct byte-range play to `<video>` is what makes seeking free; HLS turns it into segment-time seeking with a transcode restart.
- Bind selection/reader teardown to socket close, and make readers idempotent under request storms (bounded concurrent store reads, per-piece read locks). Assume the player will open and abandon a dozen range requests during a scrub.
- Persist an explicit completion bitfield instead of inferring completeness from sparse-file length; if you use disk, prefer one file per piece (TorrServer) over sparse per-file writes — eviction, resume and progress reporting all get simpler.

OPEN_QUESTIONS:
- Stremio's `server.js` is closed source. The engine and circular-buffer details above come from a third-party de-webpacked mirror (github.com/goofw/sw), which matches the public `Stremio/enginefs` API exactly (same `getDefaults`, `prewarmStream`, `enginefs-prio`, `circularBuffer`, `swarmCap`), but constants and behaviour may drift between server.js releases. Anything load-bearing should be re-verified against the bundle version you actually ship against.
- The `/hlsv2/{id}/master.m3u8` server side (whether it remuxes with `-c copy` when only the container is unsupported, or always re-encodes video) is not visible in any open Stremio repo; only the client-side decision in stremio-video is. Issue Stremio/stremio-service#77 requests 'use video transcoding only when needed', suggesting it over-transcodes today.
- TorrServer's `updateRA` currently pins anacrolix readahead at a fixed 16 MiB with the adaptive (peers × pieceLength / readers) formula commented out. Whether the fixed value was a deliberate simplification or a regression is not stated in the repo, and it interacts oddly with the separately-computed `getOffsetRange` window.
- How well each design behaves with two readers on *different files* of the same torrent (e.g. video + external subtitle) is untested here — TorrServer's `mergeRange` merges by piece index across files without checking the file identity of overlapping ranges, and `isIdInFileBE` iterates all ranges, so head/tail pinning may over-pin.
- No public issue was found quantifying Stremio's behaviour on seeks in RAM-only mode when the target is far outside the 15 MiB window and the 45 MiB ring is full of pinned/locked pieces; the store throws 'circular buf is full, unable to free' in that state, and the recovery path is unclear.

SUMMARY: librqbit (ikatson/rqbit, Apache-2.0, v9.0.1, last push 2026-08-20, 1.8k stars) is the only Rust BitTorrent library that ships a production-grade, play-head-driven piece prioritizer plus a seekable streaming reader, and it is the correct engine for this worker. Its `ManagedTorrent::stream(file_id) -> FileStream` implements `tokio::io::AsyncRead + AsyncSeek`; every seek moves a per-stream cursor that feeds `TorrentStreams::iter_next_pieces()`, a 32 MB look-ahead window interleaved round-robin across active streams and injected as `priority_pieces` into the piece picker — so a Range read at an arbitrary offset genuinely pulls those pieces first. Everything else falls into three buckets: dead (cratetorrent 2020/2022, bip_rs 2017, transmission-sys/libtorrent-sys 2019-2022 — no maintained embedding bindings exist), DHT-only (pubky/mainline, n0-mainline, librqbit-dht, equalitie/btdht), or too young to bet on (fx-torrent, irontide, libtortillas, swarmforge, mtorrent). The one genuine alternative is **fx-torrent** (yoep, Apache-2.0), whose `Torrent::prioritize_bytes(Range, PiecePriority)` + pluggable `PiecePickerFactory` is a better-shaped API for exactly this problem — but at 7 stars and 8 months old it is a research bet, not a foundation. Critically, this repo's own `ss-bridge` already embeds a vendored, patched librqbit 9.0.1, so the "embed vs sidecar" question is already answered in practice; the real wins now are in the bridge's HTTP layer, not in swapping engines.

### librqbit — piece prioritization is genuinely play-head driven
`crates/librqbit/src/torrent_state/streaming.rs`: each `FileStream` registers a `StreamState { file_id, file_abs_offset, position }`. `StreamState::queue()` (line ~44) computes the piece range `[position, position + PER_STREAM_BUF_DEFAULT)` — a 32 MB look-ahead — and `TorrentStreams::iter_next_pieces()` interleaves those windows round-robin across all active streams (shuffled for fairness). That iterator is passed as `priority_pieces` into `PieceTracker::acquire_piece` at `torrent_state/live/mod.rs:1440`. In `piece_tracker.rs:136-142` priority pieces are reserved BEFORE the naturally-queued pieces. So yes: a Range read at an arbitrary offset pulls those pieces first. Caveat: priority is applied at *acquisition* time only — a seek does not cancel already in-flight non-priority pieces, so seek latency ≈ (time for a peer to finish its current piece) + (fetch one piece).
sources: https://github.com/ikatson/rqbit/blob/main/crates/librqbit/src/torrent_state/streaming.rs; https://github.com/ikatson/rqbit/blob/main/crates/librqbit/src/piece_tracker.rs; https://github.com/ikatson/rqbit/blob/main/crates/librqbit/src/torrent_state/live/mod.rs

### librqbit — the streaming reader is a real AsyncRead + AsyncSeek
`pub async fn stream(self: Arc<Self>, file_id: usize) -> anyhow::Result<FileStream>` on `ManagedTorrent`, plus `Api::api_stream(idx, file_id)` (api.rs:514). `FileStream` impls `AsyncRead` (returns `Poll::Pending` and registers a waker when the current piece is missing; woken by `wake_streams_on_piece_completed`) and `AsyncSeek` (`start_seek` validates 0..=file_len and updates the shared `StreamState.position`). It also exposes `position()` and `len()`. Reads go through `TorrentStorage::pread_exact` inside `block_in_place`. Streaming a file works even if the file is NOT in `only_files` — priority pieces bypass the queue-selection filter, and `maybe_reconnect_needed_peers_for_file` wakes up peers that were dropped as not-needed.
sources: https://github.com/ikatson/rqbit/blob/main/crates/librqbit/src/torrent_state/streaming.rs; https://docs.rs/librqbit/latest/librqbit/

### librqbit — hidden concurrency ceiling: 8 simultaneous open streams by default
`FileStream` holds `_blocking_permit: OwnedSemaphorePermit` for its ENTIRE lifetime (streaming.rs, struct field + acquired in `stream()`). That semaphore is `BlockingSpawner::new(max_blocking_threads)` sized from `SessionOptions::runtime_worker_threads`, which defaults to `DEFAULT_BLOCKING_THREADS_IF_NOT_SET = 8` (session.rs:687-690). The rqbit binary exposes it as `--max-blocking-threads` / `RQBIT_RUNTIME_MAX_BLOCKING_THREADS`, default 8 (rqbit/src/main.rs:226-234). So the 9th concurrently-open FileStream blocks in `.await` until one is dropped. A browser video element plus subtitle fetches can easily open more than 8 parallel ranged requests. ### rqbit's own /torrents/{id}/stream/{file_idx} Range handling — verified line by line
`crates/librqbit/src/http_api/handlers/streaming.rs`. Always sets `Accept-Ranges: bytes` and a guessed `Content-Type`. ### ss-bridge's Range handler buffers the whole window in RAM — defeats progressive delivery
`src/server.rs:101-124`: `stream()` calls `engine.read_range(..)` which allocates `vec![0u8; len]` and `read_exact`s the FULL range before the response is constructed (`engine.rs:343-363`). With `MAX_RANGE = 64 MB` (server.rs:126) an open-ended `Range: bytes=N-` means the client waits for 64 MB to finish downloading before receiving byte 0, and each concurrent request costs up to 64 MB of RSS. Upstream rqbit does the opposite — `ReaderStream::with_capacity(stream, 65536)` over `stream.take(to_take)`, emitting each 64 KB chunk the moment its piece lands. Switching to `Body::from_stream(ReaderStream::new(stream.take(len)))` removes both the latency and the memory cliff.
sources: https://github.com/giulianoo0/ss-bridge/blob/main/src/server.rs; https://github.com/giulianoo0/ss-bridge/blob/main/src/engine.rs

### ss-bridge bug: suffix Range `bytes=-500` is served as `bytes=0-500`
`src/server.rs:127-144`: `spec.splitn(2,'-')` on `"-500"` yields `["", "500"]`; `"".parse::<u64>()` fails and `.unwrap_or(0)` makes `start = 0`, `end = 500`. The response is a 206 claiming `Content-Range: bytes 0-500/size` while the client asked for the LAST 500 bytes — the classic pattern for probing an MP4/MOV moov atom at the tail. Related: when `start > size-1`, `end < start` triggers the fallback branch and the server returns 206 with `bytes 0-…` instead of a 416. rqbit's own parser rejects suffix ranges (degrades to 200) rather than mis-serving them, so this is a bridge-local defect.
sources: https://github.com/giulianoo0/ss-bridge/blob/main/src/server.rs

### ss-bridge does not raise the blocking-permit ceiling
`src/engine.rs:155-162` builds `SessionOptions::default()` and sets only `fastresume = true` (plus listener options) — `runtime_worker_threads` is left `None`, so the FileStream permit pool is 8. The engine mitigates this with a slot pool (`MAX_SLOTS_PER_FILE = 2`, `MIN_POOLED_FILE = 32 MB`, engine.rs:29-32) that keeps long-lived cursors alive so their 64 MB priority window keeps rolling, and falls through to a throwaway `handle.stream(index)` when a slot is busy — but every throwaway stream also takes a permit for the duration of its 64 MB read. ### Ranked recommendation for the worker's engine
1. EMBED librqbit (current path — keep it). It is the only library with a shipping, battle-tested seek→piece-priority loop, and ss-bridge already depends on it with a valuable local fork. Embedding (not sidecar) is right here because the bridge needs CORS, a tray UI, an updater, and custom Range semantics — all of which mean owning the axum layer anyway, and because the storage-trait escape hatch is the only route to piece eviction later. 2. Drive rqbit as a sidecar — only worth it if you want to delete the vendored fork and the axum code entirely; you'd inherit a correct progressive-streaming Range handler for free, but lose the co-download patch, gain a supervised child process, and still have to work around the missing suffix-range support and the default 8-stream ceiling. Not worth the trade now. 3. fx-torrent — track it, don't switch. Its `prioritize_bytes` + `FileStream::seek/content_range` is the API you'd design from scratch; revisit in 6-12 months if it gains contributors, or mine its `piece_picker/strategy` design for the librqbit fork. 4. Build your own on mainline + peer-wire crates — only if you need something librqbit structurally cannot do (e.g. never touching disk). 5. Anything else (cratetorrent, bip_rs, transmission/libtorrent bindings, irontide, mtorrent, swarmforge, typebit) — do not use.

RECOMMENDATIONS:
- Stream the response body instead of buffering it: replace the `Vec<u8>` in `ss-bridge/src/engine.rs::read_range` + `src/server.rs::stream` with `Body::from_stream(ReaderStream::with_capacity(stream.take(len), 65536))`, mirroring rqbit's own handler. Today the client waits for the entire 64 MB window before receiving byte 0, and each in-flight request costs up to 64 MB of RSS.
- Fix the suffix-range bug in `ss-bridge/src/server.rs::parse_range`: `bytes=-500` is currently parsed as start=0,end=500 and served as a 206 claiming `Content-Range: bytes 0-500/size`. Detect the empty start component and map it to `size-500..size`; return 416 when `start > size-1` instead of silently falling back to offset 0.
- Set `SessionOptions::runtime_worker_threads = Some(32)` in `ss-bridge/src/engine.rs` (it is currently left at the default 8). Every open `FileStream` holds a blocking-pool permit for its whole lifetime, so the 9th concurrent ranged request blocks — a browser with a video element, subtitle fetches and a seek in flight can hit that.
- Convert the vendored `ss-bridge/vendor/librqbit` tree into a `[patch.crates-io]` entry pointing at a git fork of ikatson/rqbit, or into a small patch file applied at build time. The diff against librqbit 9.0.1 is only four files; carrying the full crate makes every upstream rebase a manual merge and hides the fork from `cargo audit`/dependabot.
- Offer the 'ss patch' co-download work upstream as a PR to ikatson/rqbit (`AcquireResult::Joined`, `InflightPiece.peers`, reverse-order missing-chunk requests). It is a genuine improvement to streaming seek latency with large pieces, it is the only substantive part of the fork, and upstreaming it would collapse the maintenance burden to a single tunable constant.
- Propose (or locally add) a `SessionOptions` knob for `PER_STREAM_BUF_DEFAULT` — the 32 MB look-ahead is a hard-coded const in `torrent_state/streaming.rs`, and it is the single most useful streaming tuning parameter. That one change alone would eliminate one of the four vendored-file diffs.
- If disk footprint becomes a concern for large files, implement a custom `TorrentStorage` (the trait is public and settable per-torrent via `AddTorrentOptions::storage_factory`; `storage::examples::inmemory` and `storage::middleware::write_through_cache` are working references) rather than waiting on rqbit issue #241.
- Keep a watch on fx-torrent (yoep/fx-torrent). Its `Torrent::prioritize_bytes(Range, PiecePriority)` and `FileStream::{seek, content_range}` are precisely the primitives this worker hand-rolls today; if it gains a second maintainer it becomes a serious migration candidate. Do not migrate now — 7 stars, 8 months old.

OPEN_QUESTIONS:
- Is the 64 MB `PER_STREAM_BUF_DEFAULT` in the vendored fork actually better than 32 MB in practice, or was it only raised to match `MAX_RANGE`? If the response body becomes a true stream, the two constants decouple and the look-ahead should be tuned against measured seek-to-first-byte, not against the range size.

AGENT: web:mediabunny-seek

SUMMARY: Yes — mediabunny can drive "seek to an arbitrary offset over a Range-served, partially-downloaded torrent," and it is in fact the only JS library that does it well today. Its `Source` abstraction is literally `read(start, end)` random access (`CustomSource` for a torrent-backed byte store, `UrlSource` for HTTP Range), and its demuxers never read the whole file: the MP4 demuxer walks top-level box headers and jumps straight to `moov` wherever it sits, the MKV demuxer walks Segment level-1 elements and follows the SeekHead to Cues (usually the tail). I verified this empirically on a 23 MB / 600 s file: seeking to 8:00 and copy-remuxing 20 s into HLS/CMAF read 4–7 % of the file in 7 reads and took ~50 ms, for moov-at-end MP4, faststart MP4, MKV and fMP4-with-mfra alike. The two hard caveats are (1) the `Conversion` API's `trim.start > 0` forces a full re-encode of both tracks — documented and confirmed in source and at runtime — so an offset copy-remux needs `EncodedPacketSink` + `EncodedVideoPacketSource` manually (or the patch this repo already carries); and (2) fragmented MP4 **without** an `mfra` index degrades to a linear moof scan that reads 100 % of the file at seek time. Nothing else in the 2026 landscape (ffmpeg.wasm, mp4box.js, hls.js/mux.js, libav.js) is a better fit; a custom WASM remuxer is not worth it.

### Custom byte Source with random-access read(start,end) — fully supported, first-class
`Source` is an abstract class whose entire contract is `_getFileSize()` + `_read(start, end, minReadPosition, maxReadPosition)` (src/source.ts:76-88). The public, documented way to implement one is `CustomSource({ getSize, read, dispose?, maxCacheSize?, prefetchProfile? })` where `read: (start, end) => MaybePromise<Uint8Array | ReadableStream<Uint8Array>>` and "You are guaranteed that `0 <= start < end < fileSize`" (src/source.ts:1356-1391). `read` may be async, so a torrent-backed source can simply await the pieces. Mediabunny is strict: a returned `Uint8Array` whose length != end-start throws (`options.read returned a Uint8Array with unexpected length`, src/source.ts:1496-1505). There is also a documented `source.on('read', ({start, end}) => ...)` event fired per underlying read (src/source.ts:52-59, `_dispatchRead`) — this is the hook for driving torrent piece prioritization. `Source.slice(offset, length)` yields a `RangedSource` for a file embedded in a larger file (src/source.ts:158-170).
sources: https://mediabunny.dev/guide/reading-media-files#customsource; https://mediabunny.dev/api/CustomSource; src/source.ts:76-88; src/source.ts:1356-1391; src/source.ts:1496-1505

### UrlSource issues open-ended HTTP Range requests and aborts them, rather than bounded ranges
`UrlSource` always sends `Range: bytes=${worker.currentPos}-` — an *open-ended* range, deliberately, "Always sending a range request is a good way to probe if the server supports them" (src/source.ts:915). It reads the response body stream incrementally and calls `abortController.abort()` the moment `worker.currentPos >= worker.targetPos` (src/source.ts:1004-1010). File size is deduced from `Content-Range` `/(\d+)` or `Content-Length` (src/source.ts:632-654). If the server answers non-206 it logs a warning and permanently degrades to `_transitionToSequentialMode`, a `ReadableStreamSource` where "reads into evicted regions will throw" (src/source.ts:667-700). Defaults: `parallelism: 2`, `maxCacheSize: 64 MiB`, exponential-backoff retry that gives up only on suspected CORS. A user-supplied `Range` header in `requestInit` is *not* passed through — it is parsed and reinterpreted as a fixed offset/length window into the resource (src/source.ts:795-825). Implication for a torrent bridge: an open-ended range plus abort means your bridge must handle client-abort cleanly and must not treat `bytes=N-` as "download to EOF". `CustomSource` (what this repo already uses for torrents) avoids that entirely.
sources: src/source.ts:905-925; src/source.ts:1004-1010; src/source.ts:632-700; src/source.ts:795-825; https://mediabunny.dev/api/UrlSource

### MP4 read pattern: header walk from byte 0, then a single contiguous jump to moov (wherever it is)
`IsobmffDemuxer.readMetadata()` loops top-level boxes reading only `MIN_BOX_HEADER_SIZE..MAX_BOX_HEADER_SIZE` bytes per box and advancing `currentPos = startPos + boxInfo.totalSize` — it *skips over* `mdat` without reading it. On finding `moov` it does one `requestSlice(filePos, boxInfo.contentSize)` for the whole moov (src/isobmff/isobmff-demuxer.ts:359-401). Sample tables are then parsed lazily out of the in-memory moov slice (`this.moovSlice.slice(internalTrack.sampleTableByteOffset)`, :548-552), so seeking is pure in-memory binary search; the only I/O per packet is `requestSlice(sampleInfo.sampleOffset, sampleInfo.sampleSize)` at the exact mdat offset (:3143-3147). Measured (moov-at-end, 23.3 MB / 600 s): metadata = 7 reads / 0.51 MB — `[0,7) [7,12) [12,16) [16,48) [48,56) [22815573,22815589) [22815589,23325667)` — i.e. ~50 bytes at the head then the moov at 97.8 % into the file. `getKeyPacket(480)` then cost exactly 1 read of 14 KB at offset 18.2 MB; streaming 10 s = 300 reads, 0.38 MB. Total 3.9 % of the file.
sources: src/isobmff/isobmff-demuxer.ts:359-401; src/isobmff/isobmff-demuxer.ts:543-556; src/isobmff/isobmff-demuxer.ts:3128-3150; https://mediabunny.dev/guide/reading-media-files

### MKV read pattern: EBML header walk, then SeekHead → Cues (tail read), then cluster-granular reads
`MatroskaDemuxer.readSegment()` walks level-1 elements, reads Info/Tracks/Cues/SeekHead contiguously when it meets them, and `break`s at the first Cluster, recording `clusterSeekStartPos` (src/matroska/matroska-demuxer.ts:440-500). It then sorts SeekHead entries by file position "so reading them exhibits a sequential pattern" and follows them to any metadata element it hasn't seen — which is how it reaches Cues at the end of the file (:503-530). Seeking is `performClusterLookup`, a `binarySearchLessOrEqual` over `cuePoints` plus a `clusterPositionCache` populated as clusters are read (:2269-2340). `readCluster` loads *the entire cluster* ("// Load the entire cluster", :637-640), so reads are cluster-granular, not sample-granular. Measured: metadata 19 reads / 0.083 MB with the last read at 99.6 % of the file (the Cues); `getKeyPacket(480)` = 2 reads / 0.078 MB; 10 s of packets = 10 reads / 0.386 MB. Total 2.4 %. **Without Cues** the lookup falls back to a linear cluster scan from `clusterSeekStartPos`, reading every cluster in full — the pathological case for MKV.
sources: src/matroska/matroska-demuxer.ts:440-530; src/matroska/matroska-demuxer.ts:605-640; src/matroska/matroska-demuxer.ts:2269-2340

### Fragmented MP4 without mfra reads the ENTIRE file on seek — the one real landmine
For fragmented ISOBMFF, mediabunny reads the last 4 bytes of the file, interprets them as the `mfra` size, and if `mfra` is there parses `tfra` into `fragmentLookupTable` for O(log n) seeking (src/isobmff/isobmff-demuxer.ts:428-460, :2063-2107). If `mfra` is absent, `performFragmentedLookup` walks moof headers from position 0 forward, calling `readFragment` (which reads each whole moof) until it finds the target (:3243-3345). Measured on identical content: `frag.mp4` (ffmpeg default, has mfra) → seek to 480 s = 1 read / 0.52 MB, total 5.6 % of file. `frag_nomfra.mp4` (`+skip_trailer`) → **seek phase alone = 8 reads / 23.05 MB = 100 % of the file**. Same for MKV without Cues. So the torrent pipeline should detect and either warn or fall back when the source is fMP4-without-mfra / MKV-without-Cues.
sources: src/isobmff/isobmff-demuxer.ts:428-460; src/isobmff/isobmff-demuxer.ts:3243-3345; src/isobmff/isobmff-demuxer.ts:2063-2107

### Conversion API CANNOT start a codec-copy at an arbitrary offset — trim.start > 0 forces a full transcode
`needsTranscode = !!trackOptions.forceTranscode || firstTimestamp < this._startTimestamp || ...` (src/conversion.ts:1361-1362) and for audio `const needsTrimming = firstTimestamp < this._startTimestamp` which is ANDed into the copy fast-path condition (src/conversion.ts:1623, 1628-1639). Since `firstTimestamp` is the track's *first* packet timestamp (~0), any `trim.start > 0` puts both tracks on the decode/re-encode path. The docs say so explicitly: "Setting `start` to a value other than the default will currently force a *transcode* of both video and audio. In a future version of Mediabunny, the fast 'packet copy path' … may be made available for any arbitrary trim range." Verified at runtime in Node (no H.264/AAC codecs): `trim.start=undefined` → 1 discarded track, video copies; `trim.start=480` → `isValid=false`, both tracks discarded as `undecodable_source_codec`, proving both were routed to the transcode path.
sources: https://mediabunny.dev/guide/converting-media-files#trimming; src/conversion.ts:1361-1362; src/conversion.ts:1623-1640

### Bonus bug this project is probably already hitting: AAC-in-MP4 negative first timestamp silently forces an audio transcode even with NO trim
When `trim.start` is unset, `_startTimestamp = Math.max(await input.getFirstTimestamp(filteredTracks), 0)` (src/conversion.ts:912-925). ffmpeg-produced MP4s give AAC a negative first timestamp from the encoder-delay edit list — measured `-0.0232 s` on a plain `ffmpeg -c:a aac` file, while video is `0`. So `_startTimestamp` clamps to 0, `needsTrimming = -0.0232 < 0` is true, and the AAC track is re-encoded even though a copy was possible. Confirmed: default `Conversion.init` reported `discardedTracks: ['undecodable_source_codec']` (the audio), while `trim: { start: await input.getFirstTimestamp() }` (i.e. -0.0232) gave `discardedTracks: []` and copied both. The same MKV had first timestamp 0 and was unaffected. Note that the ss patch, which deletes `needsTrimming` from the audio condition, incidentally fixes this too.
sources: src/conversion.ts:912-926; src/conversion.ts:1623-1640; https://mediabunny.dev/guide/converting-media-files#trimming

### The supported way to do an offset copy-remux: EncodedPacketSink + EncodedPacketSource, and it works end-to-end
`EncodedPacketSink` gives frame-accurate random access without decoding: `getKeyPacket(timestamp, { verifyKeyPackets })` returns the last key packet at or before a timestamp (and re-checks the real NAL/OBU type when `verifyKeyPackets` is on, walking back if the container lied — src/media-sink.ts:239-270); `getPacket`, `getNextPacket`, `getNextKeyPacket`, and `packets(startPacket, endPacket, options)` which "will intelligently preload packets based on the speed of the consumer" (src/media-sink.ts:302-345). `metadataOnly: true` yields packets with placeholder data so "only the metadata section of the file must be read." Output side: `EncodedVideoPacketSource` / `EncodedAudioPacketSource` accept `packet.clone({ timestamp: packet.timestamp - base })`; the muxer requires non-negative timestamps and that the first packet of each track be a key packet (src/muxer.ts:45-56), and forbids a timestamp below the previous GOP's max (:66-76). I built this end-to-end: seek to 480 s, copy H.264 + AAC to HLS with CMAF or TS segments — 5 segments emitted via `onSegment`, ~50 ms wall time, 7 source reads.
sources: https://mediabunny.dev/guide/media-sinks#encodedpacketsink; src/media-sink.ts:239-345; src/muxer.ts:45-78; src/media-source.ts:194-225

### HLS/CMAF output is complete and callback-driven
`HlsOutputFormat` writes a master playlist, N media playlists and segments through a `PathedTarget(rootPath, ({path, mimeType, isRoot}) => Target)`. Options (src/output-format.ts:1204-1291): `segmentFormat` (a single OutputFormat or an array — "the first format that can contain all tracks of the segment" wins, so you can mix ADTS audio + TS video), `targetDuration` (default 2 s; segments only ever split on key frames), `live: true` (playlists re-emitted on every update, `#EXT-X-ENDLIST` only when tracks close), `maxLiveSegmentCount` + `onSegmentPopped`, `singleFilePerPlaylist` (emits `#EXT-X-BYTERANGE`; with a fragmented-MP4 segment format the single file is also a standalone valid fMP4), and `getPlaylistPath` / `getSegmentPath` / `getInitPath`. Callbacks: `onMaster(content)`, `onPlaylist(content, info)`, `onInit(target, info)`, `onSegment(target, info)`. `HlsOutputSegmentInfo` is `{ n, isSingleFile, format, playlist }` — note it carries **no duration or start timestamp** (src/output-format.ts:1188-1197), so segment timing must be tracked on your side. Subtitles in HLS are explicitly not supported yet. Separately, `Mp4OutputFormat({ fastStart: 'fragmented', minimumFragmentDuration })` and `CmafOutputFormat({ minimumFragmentDuration })` give plain fMP4/CMAF output.
sources: https://mediabunny.dev/guide/writing-hls; src/output-format.ts:1188-1291; src/output-format.ts:352-405

### Codec-copy limits: CMAF segments take everything, MPEG-TS segments take only AVC/HEVC
`MpegTsOutputFormat.getSupportedCodecs()` = `VIDEO_CODECS.filter(['avc','hevc'])` + `AUDIO_CODECS.filter(['aac','mp3','ac3','eac3','dts'])` (src/output-format.ts:1153-1158). `CmafOutputFormat`/`Mp4OutputFormat` accept all of `avc, hevc, vp9, av1, vp8, prores` plus all non-PCM audio and ISO/IEC 23003-5 PCM (src/output-format.ts:385-405). Verified: copying VP9+Opus and AV1 into HLS/CMAF works; into HLS/TS both throw `Codec 'vp9' cannot be contained within HTTP Live Streaming (HLS). Supported video codecs are: 'avc', 'hevc'.` AAC copy needs no decoder at all (it copied fine in Node, which has no AAC decoder). AAC *encode* is missing in some browsers; `@mediabunny/aac-encoder` is a size-optimized FFmpeg AAC-LC WASM build registered via the custom-coder API — and note a registered custom encoder takes absolute priority over WebCodecs, so register it only behind an `AudioEncoder.isConfigSupported` check (which this repo already does). AC-3/E-AC-3/DTS/ProRes decode come from separate `@mediabunny/*` WASM packages.
sources: src/output-format.ts:1153-1158; src/output-format.ts:385-405; https://mediabunny.dev/guide/extensions/aac-encoder; https://mediabunny.dev/guide/supported-formats-and-codecs

### Prefetch profiles decide the torrent read amplification — and can head-of-line-block a seek
Three profiles (src/source.ts:1854-1908): `none` (exact ranges), `fileSystem` (64 KiB page-aligned bidirectional padding), `network` (64 KiB back-padding, a 0.5 MiB `URL_SOURCE_MIN_LOAD_AMOUNT` floor per read, and exponential growth of a worker's read region up to an 8 MiB extension when successive reads cross the worker's midpoint). `UrlSource` hardcodes `network`; `CustomSource` defaults to `none`. Measured on the same 480 s→500 s copy-remux of a moov-at-end MP4: `network` = 7 reads / 5.30 MB (22.7 % of file) vs `none` = 611 reads / 1.29 MB (5.5 %). MKV: 7/4.92 MB vs 42/0.93 MB. The hazard: `ReadOrchestrator.createWorker` evicts only *idle* workers and otherwise returns null, queueing the read — "All workers are still running, we can't create a new one" (src/source.ts:2242-2268); a running worker is never truncated. `CustomSource` hardcodes `maxWorkerCount: 2` (src/source.ts:1438) and `UrlSource` defaults `parallelism: 2`. So a seek arriving while both workers are chasing an 8 MiB prefetch is blocked behind up to ~16 MiB of now-useless download. Disposing the `Input` and rebuilding it per region is the only lever that truncates in-flight prefetch.
sources: src/source.ts:1854-1908; src/source.ts:2242-2268; src/source.ts:1438; src/source.ts:845

### What the byte-access pattern demands from the torrent side
Concretely, in order: (1) **head, ~64 KB** — format sniffing (`_canReadInput` reads 4–12 bytes at offset 0 for every registered format, src/input-format.ts:77,378,418) plus the ftyp/EBML header walk; (2) **tail** — for moov-at-end MP4 a single contiguous slice of the whole moov (0.5 MB in my 600 s test, but tens of MB for a 3 h film with a large stbl); for MKV the Cues element reached through the SeekHead; for fMP4 the *last 4 bytes* then the mfra. So the torrent must be able to serve the last piece(s) first — a tail seek in the swarm, not a full download. (3) **one seek read** at the mdat/cluster offset for the target keyframe, then **forward-sequential** reads from there. Two operational requirements follow: reads must eventually settle (a `CustomSource.read` that never resolves parks one of only two workers and can deadlock the demuxer — give reads a deadline and reject rather than hang), and piece priority should be driven from `source.on('read', ({start,end}))`, raising priority for `[start, start + N MB]` on the first read after each seek. Restricting `formats` to `[MP4, MKV, ...]` instead of `ALL_FORMATS` also trims the sniffing reads.
sources: src/input-format.ts:77; src/source.ts:52-59; src/isobmff/isobmff-demuxer.ts:428-440; src/matroska/matroska-demuxer.ts:503-530

### Measured end-to-end: seek to 8:00 and remux 20 s to HLS
600 s / 23 MB H.264+AAC test file, `CustomSource` with `prefetchProfile: 'network'`, manual `EncodedPacketSink` → `EncodedVideoPacketSource`/`EncodedAudioPacketSource` → `HlsOutputFormat`. moov-at-end MP4 → CMAF segments: 8 files (init 1 KB + 5×~150 KB segments + 2 playlists), 5.30 MB read in 7 reads, **45 ms**. Same to MPEG-TS segments: 5×~197 KB, 52 ms. MKV → CMAF: 4.92 MB in 7 reads, 52 ms. fMP4-with-mfra → 4.97 MB, 28 ms. Plain fMP4 output (`Mp4OutputFormat({fastStart:'fragmented'})`) of the same range: 0.77 MB out, 46 ms. With `prefetchProfile: 'none'` the same MP4 job read only 1.29 MB but issued 611 reads (one per sample) — MKV only 42 (cluster-granular). This is roughly 400× realtime for a pure copy, versus the 96 s-to-first-segment / 215 s-to-master that the transcode path cost per this repo's own commit d36576c.
sources: src/media-sink.ts:302-345; src/output-format.ts:1204-1291

### The ss patch against conversion.js is sound, but check three edges
web/patches/mediabunny+1.55.2.patch deletes `firstTimestamp < this._startTimestamp` from video `needsTranscode` and `!needsTrimming` from the audio copy condition, then seeks the sink to the right start packet. Three things to watch. (a) The video path snaps *forward* to `getNextKeyPacket` when the trim start isn't on a keyframe; the first emitted timestamp is then `kf - start > 0` while audio starts at ~0, so the output opens with a video gap — harmless only because `snapToKeyframe` in clientMedia.ts already aligns `startSeconds` to a keyframe first. If that ever drifts, A/V will offset. (b) `needsPadding = firstTimestamp > _startTimestamp && !supportsTimestampedMediaData` is left in place, but ISOBMFF returns `supportsTimestampedMediaData === true` (src/output-format.ts:277-279), so it is inert for CMAF — fine. (c) The patch keeps `verifyKeyPackets: true` on both `getKeyPacket` and the `packets()` iteration; that forces real packet data to be read and NAL/OBU-parsed for every packet, which is correct but not free. Upstream has signalled intent to make the copy path work for arbitrary trims, so this patch should be revisitable rather than permanent — worth filing the use case as an issue so the API lands officially.

### Alternatives all lose on this specific job
**ffmpeg.wasm**: the official perf page benchmarks a WebM→MP4 at 5.2 s native vs 128.8 s single-thread (~25×) and 60.4 s multithread (~12×), and the core is a multi-MB WASM download (issue #866 is literally titled '4.80MB SIZE WASM!!!'); it also has no random-access source abstraction — you feed it a whole file in MEMFS, which defeats the entire partial-torrent premise. Mediabunny is ~5 kB gzipped at the low end thanks to tree-shaking. **mp4box.js**: MP4/ISOBMFF only (no MKV — a non-starter for torrent releases), no VP9/AV1-in-MKV story, and its partial-download flow is a manual appendBuffer/`seek()`-returns-offset dance that has been an open ergonomics complaint since gpac/mp4box.js#26 and #410. **hls.js / mux.js**: their transmuxer is TS/AAC→fMP4 only, built to feed MSE, not a general-purpose MP4/MKV remuxer. Shaka is in the same boat. **libav.js** (Yahweasel): real ffmpeg demux/mux in WASM with a WebCodecs bridge, and its own docs concede muxing/demuxing is I/O-bound anyway — but it's a much larger download and you'd still write the seek/segment orchestration yourself. **Custom WASM remuxer in 2026**: no. Mediabunny already gives you exactly the two primitives a custom remuxer would exist to provide (byte-range Source + packet-level copy), it is MPL-2.0 and forkable/patchable in place (as this repo already does), and the actual gap — offset copy-remux — is a ~40-line patch, not a codebase.
sources: https://ffmpegwasm.netlify.app/docs/performance/; https://github.com/ffmpegwasm/ffmpeg.wasm/issues/866; https://github.com/gpac/mp4box.js/issues/410; https://github.com/gpac/mp4box.js/issues/26; https://github.com/Yahweasel/libav.js/; https://github.com/Yahweasel/libavjs-webcodecs-bridge

RECOMMENDATIONS:
- Keep mediabunny. It is the only library whose core abstraction (`Source._read(start,end)`) matches a torrent piece store, and the measurements confirm a seek to 8:00 + 20 s HLS copy costs ~50 ms and <5 % of the file across moov-at-end MP4, faststart MP4, MKV and fMP4-with-mfra.
- Detect the two pathological layouts before committing to a source: fragmented MP4 without `mfra`, and MKV without Cues. Both turn a seek into a 100 %-of-file linear scan (measured: 23.05 MB read for one `getKeyPacket` on a 23 MB fMP4 with `+skip_trailer`). Probe by timing/byte-counting a `getKeyPacket` near the end during planning, and surface a 'this file cannot be seeked cheaply' verdict rather than stalling the room.
- Reconsider `prefetchProfile: 'network'` for the torrent CustomSource. It cost 5.30 MB vs 1.29 MB for the same job, and its 8 MiB worker extension can head-of-line-block a seek behind two busy workers (`maxWorkerCount` is hardcoded to 2 for CustomSource, src/source.ts:1438). Since ss-bridge is on loopback, reads are cheap once pieces exist — `'fileSystem'` gets page-aligned batching without the 0.5 MiB floor and the exponential growth. Measure both against a real swarm.
- Drive torrent piece priority from `source.on('read', ({start,end}) => ...)` rather than guessing. On the first read after a keyframe snap, raise priority for `[start, start + N MB]` forward; and always pre-prioritize the tail (last piece) plus the head at open, since every container needs a tail read (moov / Cues / mfra) before anything else can happen.
- Give `CustomSource.read` a deadline that rejects. A read that never resolves parks one of only two read workers and can deadlock the demuxer with no error surfaced — the failure mode looks like a room that hangs in 'preparing' forever.
- Fix the AAC negative-first-timestamp transcode even if you keep the patch: ffmpeg MP4s give AAC `firstTimestamp = -0.0232 s`, which makes `needsTrimming` true and re-encodes audio *even with no trim at all*. Unpatched, `trim: { start: await input.getFirstTimestamp() }` restores the copy path for both tracks; patched, verify with a test that a plain AAC MP4 reports `discardedTracks: []`.
- Track segment timing yourself — `HlsOutputSegmentInfo` is only `{ n, isSingleFile, format, playlist }` with no duration or start timestamp (src/output-format.ts:1188-1197). The current `segmentCounts × SEGMENT_SECONDS` estimate in clientMedia.ts is right only while every segment hits the target duration; a long GOP forces a longer segment and the produced-edge math drifts.
- Consider migrating off the patch toward a hand-rolled pump (`EncodedPacketSink` → `EncodedVideoPacketSource`/`EncodedAudioPacketSource`) for the video-copy path, keeping `Conversion` only for the audio-transcode tracks. It is ~40 lines (I verified it end-to-end into both CMAF and TS HLS), removes the patch-package pin on 1.55.2, and lets you upgrade mediabunny freely. Either way, file the arbitrary-offset copy use case upstream — the docs already say the fast copy path 'may be made available for any arbitrary trim range'.
- Do not build a custom WASM remuxer, and do not add ffmpeg.wasm as a fallback. ffmpeg.wasm is 12–25× slower than native by its own benchmarks, ships multiple MB of WASM, and has no random-access source model — it would require downloading the whole torrent file first, which is the exact thing this architecture exists to avoid.

OPEN_QUESTIONS:
- How large is the moov for a real 2–3 h release? Mediabunny reads it as one contiguous slice; a 60 s test gave 0.5 MB, but a long film with a dense stbl can be tens of MB, and that is a single blocking tail read before anything plays. Worth measuring on an actual torrent to size the 'preparing' wait.
- Does ss-bridge handle an aborted open-ended range gracefully? Not currently exercised (torrents go through CustomSource), but plugin URLs go through UrlSource, which always sends `Range: bytes=N-` and aborts mid-response.
- Should the fMP4-without-mfra / MKV-without-Cues case fall back to something, or just be refused? A sequential-from-zero remux is technically possible but would take as long as downloading the file.
- Is HEVC copy-to-CMAF actually playable for the room's viewers? Mediabunny will happily copy it, but hls.js/MSE HEVC support is browser- and platform-dependent — this is a player-side constraint, not a mediabunny one, and the same applies to Opus-in-CMAF.
- Upstream's roadmap for offset copy-remux — worth opening an issue with the measured numbers (96 s vs 2.4 s to a full master) since that is the strongest possible argument for the feature.

AGENT: web:signed-worker-security

SUMMARY: Use both layers, not one: mTLS with a private CA for channel/peer identity, plus a detached Ed25519 signature over each job envelope for job authorization. mTLS answers "is this really my server / is this really my worker"; the detached signature answers "did the operator actually authorize this exact job", survives a compromised queue/relay/proxy, and is offline-auditable — the BOINC model, where the code-signing private key lives on a machine that is never networked and the client refuses anything unsigned. Enrollment should follow the Tailscale/headscale preauth-key and GitHub Actions runner pattern: a one-time, short-TTL pairing token that lets the worker generate its own keypair locally, send a CSR, and receive a short-lived cert it then auto-renews over the existing mTLS channel (SPIRE renews at 50% of lifetime). The single most important enforcement decision is that a job carries an infohash (or verified metainfo bytes), never a URL — infohashes are self-authenticating, so the worker can prove it fetched what was signed, and every other constraint (size caps, file-count caps, extension allowlist, single-file selection, path sanitization, `url-list` web-seed stripping) is applied to the verified metainfo before a single byte of content is written. Crate picks for 2026: rustls 0.23 + tokio-rustls + tokio-tungstenite (WSS, outbound-only), ed25519-dalek 3.0.0 with `verify_strict`, rcgen 0.14.9 for the CA/CSR path, librqbit for the torrent engine, and either a raw detached Ed25519 envelope or PASETO v4.public (rusty_paseto) — not JWT, and not Biscuit unless you actually need attenuated delegation. The serious residual risks are legal rather than cryptographic: seedbox/VPS operators who specifically target BitTorrent users are much less likely to get DMCA safe harbor, and every worker's IP is publicly visible in the swarm.

### Recommended architecture: two independent layers (transport identity + job signature)
Layer 1 = mTLS over an outbound-only connection, private CA, worker pins the CA as its only trust anchor. Layer 2 = every job is a detached Ed25519 signature over a canonical envelope, verified by the worker against a pinned signer public key set, independent of how the bytes arrived. Do NOT pick one: mTLS alone means anyone who compromises the control server, a queue, a TLS-terminating proxy, or a load balancer can inject jobs and leaves no non-repudiable record; detached signatures alone leave the transport unauthenticated (no worker identity, no per-worker targeting, no revocation, no confidentiality of job metadata). The layered split is exactly BOINC's: transport/scheduler is one thing, and separately 'the BOINC client will only run programs with valid signatures', with the code-signing private key on 'a computer that is never connected to a network'.
sources: https://boinc.berkeley.edu/wiki/BOINC_Security; https://github.com/BOINC/boinc/wiki/BOINC_Security

### Who holds which key (5 keys total)
1) CA root key (Ed25519 or P-256) — generated with rcgen, kept OFFLINE on the owner's machine, used only to sign an issuing/intermediate cert and the signed trust bundle. Root cert (public) is compiled into the worker binary or shipped as a config file; it is the worker's ONLY trust anchor. 2) Issuing CA key — online on the control server, signs worker certs on enrollment/renewal; rotate ~yearly. 3) Server TLS cert — issued by the issuing CA; worker verifies it against the pinned root, so no public CA and no WebPKI involvement. 4) Job signing key (Ed25519) — ideally on a separate signer host/HSM, never the same process that serves the API; its PUBLIC key is in the trust bundle. 5) Worker key — generated ON the worker at enrollment and never transmitted; only the CSR/public key leaves the box. That last point mirrors the GitHub Actions runner: at config time 'an RSA public/private key pair is created', the private key stays local under DPAPI/chmod, only the public key goes to the service, and 'your credentials are never used for registering the runner'. SPIRE does the same: 'the SPIRE Agent generates the key pair, obtains a signed certificate from the SPIRE Server's CA'.
sources: https://github.com/actions/runner/blob/main/docs/design/auth.md; https://spiffe.io/docs/latest/spire-about/spire-concepts/; https://github.com/rustls/rcgen

### Enrollment / pairing flow (token pairing, not manual certs)
Recommended flow: operator runs `ctl enroll create --ttl 15m --one-shot` → gets `wkenroll_<random>`; operator pastes it into the worker's env/config; worker generates an Ed25519 keypair, builds a CSR (rcgen `CertificateSigningRequest`), POSTs {token, csr, machine fingerprint} over plain TLS (server cert pinned to the private CA) to /enroll; server validates the token, burns it, issues a cert with the worker id in the SAN (a `spiffe://`-style URI SAN or a simple `worker:<uuid>` URI SAN is cleanest), returns cert + trust bundle; worker discards the token and never uses plain TLS again. This is the headscale/Tailscale preauth-key UX — keys can be `--reusable`, `--expiration`, `--ephemeral`, and 'Tailscale automatically revokes one-off keys after they are used' — combined with the Actions registration-token→keypair exchange. Keep manual cert issuance only as an air-gapped fallback (operator signs a CSR offline and drops cert.pem on the box). Concourse's TSA is the even-simpler variant if you want zero CA: each worker holds an SSH key and 'the public key must be listed in the web node's authorized worker keys file' — an explicit allowlist of worker public keys, which is very reasonable for a fleet under ~50 workers.
sources: https://headscale.net/stable/ref/registration/; https://tailscale.com/docs/features/access-control/auth-keys; https://github.com/actions/runner/blob/main/docs/design/auth.md; https://github.com/concourse/concourse/blob/master/tsa/README.md

### Key rotation (three separate schedules)
Worker certs: issue SHORT (24h–7d) and auto-renew over the already-authenticated mTLS channel at ~50% of remaining lifetime — SPIRE issues X.509-SVIDs with a one-hour default lifetime and 'the SPIRE Agent proactively monitors SVID lifetimes and triggers renewal at a configurable threshold (typically 50% of lifetime)'. Rotation-by-renewal means you never need a revocation story for the common case. Job signing key: put a `kid` in every envelope and have the worker trust a SET of public keys from the signed trust bundle; roll = publish new key in bundle → wait one bundle-propagation period → switch signer → drop old key. The bundle must be signed by the OFFLINE root so a compromised control server cannot add its own job-signing key. CA: intermediate ~1y, root ~10y, cross-publish both intermediates in the bundle during overlap. Revocation: rustls supports CRLs directly via `WebPkiClientVerifier::builder(roots.into()).with_crls(crls).build()`, but for a small fleet a server-side worker-id allowlist plus short cert TTLs is simpler and strictly more timely. Buildkite's answer to long-lived tokens is the same shape: 'use the Buildkite APIs to set the expiration date for agent tokens... automated token rotation'.
sources: https://spiffe.io/docs/latest/spire-about/spire-concepts/; https://docs.rs/rustls/latest/rustls/server/struct.WebPkiClientVerifier.html; https://buildkite.com/docs/agent/v3/securing

### The signed job envelope: exact fields and what the worker verifies
Envelope (sign the EXACT bytes transmitted, never a re-serialization): {v:1, kid, job_id (uuid), worker_id, iat, nbf, exp (iat+300s), nonce (128-bit random), kind:"video_torrent", infohash_v1 and/or infohash_v2, metainfo_sha256 (optional, if the metainfo is inlined), tracker_allowlist[], limits:{max_total_bytes, max_files, max_file_bytes, allowed_extensions[], deadline_secs}, select:{strategy:"largest_video"|"index", index}, output:{...}, worker_cert_spki_sha256}. Worker verification order, fail-closed at every step: (1) `kid` is in the pinned trust bundle; (2) Ed25519 `verify_strict()` over `DOMAIN_SEP || envelope_bytes` — use verify_strict, not verify, because it 'prevents weak key forgery attacks' where a special public key can sign any message; (3) worker_id == own id AND worker_cert_spki_sha256 == hash of own presented client cert (channel binding: a job stolen off another worker's wire is useless); (4) now >= nbf and now < exp with ≤60s skew; (5) nonce not present in a persistent seen-nonce store (redb/sqlite) with TTL = exp window; (6) job_id never executed before (separate idempotency table); (7) only then the content constraints below. RFC 9421 standardises exactly this triple — `created`, `expires`, and 'nonce: a random unique value generated for this signature' — and real deployments back it with 'in-memory caches that reject duplicate nonces as potential replay attacks'.
sources: https://www.rfc-editor.org/rfc/rfc9421.pdf; https://lib.rs/crates/ed25519-dalek; https://datatracker.ietf.org/doc/rfc9421/

### Crate: rustls for mTLS, concrete API
Server side: build a `RootCertStore` containing ONLY your private CA, then `WebPkiClientVerifier::builder(roots.into()).build()` (add `.with_crls(crls)` for revocation; deliberately do NOT call `.allow_unauthenticated()`), and hand the resulting `Arc<dyn ClientCertVerifier>` to `ServerConfig::with_client_cert_verifier`. Worker side: a `ClientConfig` whose root store contains only the private CA root — this is a hard pin, so a compromised public CA or a corporate MITM proxy cannot impersonate the control server. Use rustls 0.23.x + tokio-rustls; rustls is Rust-memory-safe by construction and implements TLS 1.2/1.3 for both roles.
sources: https://docs.rs/rustls/latest/rustls/server/struct.WebPkiClientVerifier.html; https://github.com/rustls/rustls; https://docs.rs/rustls/latest/rustls/

### Crate: transport — tokio-tungstenite (WSS) over quinn/QUIC or gRPC
Pick WSS via tokio-tungstenite on top of tokio-rustls. It gives one long-lived outbound connection for job push + heartbeat + progress, passes corporate proxies and firewalls, and needs no NAT work: 'all agents connecting outbound to a server cluster makes NAT a non-issue'. quinn/QUIC is the wrong default here — 'many corporate firewalls block UDP except for well-known ports, and some drop UDP traffic to port 443 entirely', and 'an agent behind a NAT still cannot accept inbound QUIC connections without a relay or STUN-based hole-punching'. gRPC bidi streaming (tonic) is viable if you already speak protobuf, but 'gRPC is built on top of TCP and inherits all of its reachability limitations' and HTTP/2-unaware proxies force a WebSocket fallback anyway — which is what you'd have built in the first place. Consider quinn only if the worker must also serve media back at scale. Architecturally this is Concourse's TSA: 'workers no longer need to be internet routable... they open a reverse tunnel through the TSA'.
sources: https://docs.spectrocloud.com/architecture/grps-proxy/; https://pilotprotocol.network/learn/grpc-udp-transport; https://github.com/concourse/concourse/blob/master/tsa/README.md

### Crate: ed25519-dalek 3.0.0 (July 2026)
Latest stable is 3.0.0, released 2026-07-06, Rust edition 2024, MSRV 1.85. Enable `pkcs8` for key serialization and keep the default `zeroize` (automatic key zeroing) and `fast` features. Use `VerifyingKey::verify_strict()` on the worker. If you ever batch-verify a backlog, note `verify_batch()` 'skips weak key checks — users should call is_weak() beforehand'. The crate deliberately does not do deterministic signing 'due to pitfalls like re-used nonce accidentally revealing the secret key' — relevant only on the signer side, and it is handled for you.
sources: https://lib.rs/crates/ed25519-dalek; https://docs.rs/ed25519-dalek/latest/ed25519_dalek/fn.verify_batch.html

### Crate: rcgen 0.14.9 for the private CA and CSR issuance
rcgen 0.14.9 (released 2026-08-10, 100% documented) is the right tool for both the offline root and the online issuing CA. Relevant types: `KeyPair`, `CertificateParams` (with `self_signed()` for the root and `signed_by()` for anything below it), `Issuer` ('an issuer that can sign certificates'), `CertificateSigningRequest`, and `CertificateSigningRequestParams` ('parameters for a certificate signing request') for the server side that parses the worker's CSR. DER inputs/outputs use `rustls-pki-types`, so the artifacts 'plug straight into a rustls ClientConfig/ServerConfig' with no PEM shuffling. `rustls-cert-gen` is a ready-made CLI if you want to bootstrap the root by hand rather than write code. Remember to set SANs meaningfully — a common self-signed-CA failure is a cert with no/incorrect subjectAltName.
sources: https://docs.rs/rcgen; https://github.com/rustls/rcgen; https://lib.rs/crates/rustls-cert-gen

### Token format: detached Ed25519 or PASETO v4.public — not JWT, not Biscuit
First choice: your own envelope + detached Ed25519, because the parser is 'split on the last dot, base64-decode, verify, then serde_json::from_slice' and there is no algorithm negotiation to get wrong. Second choice, if you want a vetted format with canonicalization (PAE) and registered exp/nbf claims for free: PASETO v4.public via rusty_paseto (actively maintained, latest release Dec 2025; ships V4 local+public). PASETO's structural advantage over JWT is precisely the thing you care about: 'the cryptographic algorithm is not negotiated per token; the version in the token prefix pins a single algorithm pair', shrinking 'the surface area for the algorithm-confusion vulnerabilities that have produced most JWT CVEs'. Skip JWT. Skip Biscuit for v1 — it is for 'capability-based authorization where token-attenuation matters... delegation with attenuation, issuing capabilities that downstream code can scope further', and it pays for that with per-block single-use keypairs and a Datalog engine. A one-hop server→worker job has nothing to attenuate. Revisit Biscuit only if you later let third parties submit jobs that the server re-scopes before forwarding.
sources: https://guptadeepak.com/ciam-compass/guides/paseto-explained/; https://www.biscuitsec.org/docs/help/faq/; https://crates.io/crates/rusty_paseto; https://fly.io/blog/api-tokens-a-tedious-survey/

### Constraint enforcement #1: infohash, never a URL — the design decision that does the most work
The job must reference content by BitTorrent v1 SHA-1 infohash and/or v2 SHA-256 infohash (BEP 52), with an optional tracker allowlist — never a magnet with arbitrary parameters, never an HTTP URL, never a search string. The worker fetches metadata over the wire (ut_metadata/BEP 9) and recomputes the infohash: if it doesn't match the signed value, abort. This makes the reference self-authenticating, so a compromised control plane cannot point the worker at attacker-chosen bytes without also holding the job signing key. If you inline the metainfo instead, sign `metainfo_sha256` and compare the exact bencoded bytes. Corollary the design must not miss: strip or allowlist `url-list` (BEP 19 web seeds) in the metainfo — it is an attacker-supplied arbitrary-URL field inside an otherwise self-authenticating structure, and honoring it silently re-introduces the 'worker will fetch any URL' capability you just designed out.
sources: https://www.bittorrent.org/beps/bep_0003.html; https://www.bittorrent.org/beps/bep_0052.html

### Constraint enforcement #2: metainfo validation before any bytes are written — path traversal is the live bug class
Validate the parsed metainfo BEFORE download: reject if file count > max_files; reject if summed `length` > max_total_bytes or any file > max_file_bytes (both are in the metainfo, so this is a pre-flight check, not a runtime abort); reject non-video extensions. Then sanitize every path: reject any component equal to `.` or `..`, any absolute path, any empty component, embedded NUL, `/` or `\\` inside a component, non-UTF-8 sequences, and Windows reserved names. This is not theoretical — a real CVE-class bug in Net::BitTorrent (<2.1.0) validated path components only on the .torrent ingest path, so 'the peer and magnet metadata path... passes attacker-supplied file names straight to Storage::add_file... where Path::Tiny's child() does not collapse ".."', and 'because the peer also controls the piece hashes and the served bytes, content verification passes, so a malicious magnet or peer writes attacker-chosen content to an attacker-chosen path on the downloading host'. Note the second-order lesson: validating at torrent-file ingest is NOT enough when metadata can also arrive from peers. BEP 52 itself states implementations 'must be prepared to sanitize' names that 'may contain invalid UTF-8 sequences or characters and names that are reserved on specific filesystems'.
sources: https://metacpan.org/release/SANKO/Net-BitTorrent-0.074000_012/view/lib/Net/BitTorrent/Protocol/BEP03.pod; https://www.bittorrent.org/beps/bep_0052.html; https://github.com/bittorrent/bittorrent.org/blob/master/beps/bep_0052.rst

### Constraint enforcement #3: single-file selection is enforcement, not a preference
Don't download the pack and then delete extras — set every non-selected file's priority to 0 so the bytes are never requested or written. librqbit supports 'selective file downloads using regex patterns' plus `list_only=true` to enumerate a torrent's files without downloading, which maps directly to a two-phase 'fetch metainfo → validate → select → start' worker flow; its `Session` type is the programmatic entry point and it is explicitly 'used as a backbone of rqbit... can be used as a library'. If you need finer control, libtorrent exposes per-file `file_priority` and per-torrent DHT/PEX/LSD flags ('a feature to disable DHT, PEX and LSD on a per-torrent basis'). Rule of thumb for the selector: pick the single largest file whose extension is in {.mkv,.mp4,.webm,.m4v,.mov,.avi,.ts} and whose length is within caps; optionally allow one subtitle file under ~2 MB; refuse the job if no such file exists.
sources: https://github.com/ikatson/rqbit/blob/main/README.md; https://docs.rs/librqbit/latest/librqbit/; https://github.com/arvidn/libtorrent/commit/7a2085063219ae36f7f21c911b3873237a06f690

### Constraint enforcement #4: content sniffing + OS-level containment
Extension checks are advisory; add magic-byte verification once the first pieces of the selected file land: ISO-BMFF/MP4 via the `ftyp` box, Matroska/WebM via EBML magic `[0x1a,0x45,0xdf,0xa3]`. Rust options: `infer` (no magic-file DB needed), `media_infer` (purpose-built for media containers by magic bytes), or `mimetype-detector` ('proper MP4 ftyp box parsing... proper EBML parsing for Matroska'); `mp4box` if you want to walk the box tree and confirm a real video track. Abort and delete on mismatch. Underneath that, containment must be OS-enforced, because a metainfo parser bug is always possible: run each job under a per-job directory beneath one fixed root, open with O_NOFOLLOW, and wrap the worker in a systemd unit with ProtectSystem=strict / ReadWritePaths=<root> / PrivateTmp / NoNewPrivileges (or a container with a single bind mount). Add a per-job byte accountant that kills the job at the cap plus a disk high-water mark that refuses new jobs.
sources: https://github.com/bojand/infer; https://github.com/Ayush1325/media_infer; https://crates.io/crates/mimetype-detector/0.1.0; https://crates.io/crates/mp4box

### Abuse and exposure: seeding, ports, discovery, rate limits
Concrete knobs: (a) stop seeding at completion / ratio 0 — uploading is the distribution act that draws notices, though note this is leeching and some trackers will ban it; (b) disable DHT, PEX and LSD so the worker is not advertised beyond the trackers you allowlisted (qBittorrent/libtorrent both expose these; BEP 27's private flag 'is intentionally placed in the info section... so that it cannot be disabled or removed without changing the identity of the torrent', but 'even if a torrent has the private flag, some clients would still allow DHT or PEX unless you turn them off yourself'); (c) do not open an inbound BitTorrent port — 'without port forwarding, you can only make outgoing connections (passive mode)', which costs connectivity but keeps the worker's only listening surface at zero, consistent with the outbound-only control channel; (d) per-worker limits: max concurrent jobs, per-job wall-clock deadline, daily byte budget, and an infohash denylist the server enforces before signing. The IP-exposure fact must be disclosed to whoever runs the worker — Stremio formalises exactly this as a manifest field, `behaviorHints.p2p`: 'if the addon includes P2P content, such as BitTorrent, which may reveal the user's IP to other streaming parties'.
sources: https://github.com/qbittorrent/qBittorrent/wiki/How-to-Disable-DHT,-PeX,-and-LPD; https://www.bittorrent.org/beps/bep_0027.html; https://github.com/arvidn/libtorrent/issues/3769; https://github.com/Stremio/stremio-addon-sdk/blob/master/docs/api/responses/manifest.md

### Legal exposure of operating the fleet (this is the real risk, not the crypto)
Two distinct exposures. The worker operator: the box's IP sits in the swarm and 'a seedbox does not change what's legal; infringing content is infringing wherever you download it. What it changes is exposure: the server's IP is in the swarm instead of your home IP' — and providers must forward DMCA notices to the user. The fleet operator (you, the one signing jobs): the DMCA safe-harbor analysis turns on whether you look like a neutral provider or a BitTorrent-targeted one — Duke's analysis concludes general VPS providers 'are likely to find refuge in DMCA safe harbor provisions as long as they conscientiously comply with the DMCA', while 'virtual private server providers specifically targeting BitTorrent users ("seedbox providers") are much less likely to receive DMCA safe harbor protection'. A central server that signs 'download this torrent' instructions and dispatches them to third-party machines is closer to the second category and arguably to inducement. Minimum hygiene: published abuse contact and takedown process, DMCA agent registration if you plan to claim safe harbor, an infohash denylist enforced at signing time, job logs with retention, and — if workers run on volunteers' networks — explicit informed consent covering the IP-exposure point.
sources: https://scholarship.law.duke.edu/context/dltr/article/1264/viewcontent/DMCA_Safe_Harbors_for_Virtual_Private_Server_Providers___Wang.pdf; https://dltr.law.duke.edu/2014/11/08/dmca-safe-harbors-for-virtual-private-server-providers-hosting-bittorrent-clients/; https://www.rapidseedbox.com/blog/are-seedboxes-legal

### Prior art mapping, condensed
BOINC → 'each project has a code-signing key pair... keep the private key only on a computer that is never connected to a network... the BOINC client will only run programs with valid signatures', with a SEPARATE key pair for uploads. Take: separate signing key from transport key; keep the signer off the API host; worker holds only public keys. GitHub Actions runner → time-limited registration token, runner-generated RSA keypair (public key only leaves the box), then RSA-signed requests exchanged for short-lived OAuth tokens that are never persisted; JIT runners are 'single-use and auto-deregister after completing one job', which 'limits the exposure of long-lived credentials'. Take: pairing token → local keypair → short-lived credential; consider ephemeral workers. Concourse TSA → 'each worker node verifies its registration with the web node via a SSH key. The public key must be listed in the web node's authorized worker keys file', over an outbound reverse tunnel. Take: an explicit public-key allowlist is a legitimate small-fleet substitute for a CA. Tailscale/headscale → preauth keys with --reusable/--expiration/--ephemeral and auto-revocation of one-off keys. Take: the enrollment UX. SPIRE → agent-generated keypair, CA-issued 1h SVIDs, auto-rotation at 50% lifetime, 'a stolen workload credential expires within the hour instead of staying valid for months'. Take: cert lifetimes and the renewal trigger. Stremio → addons are just web services returning a manifest; 'they aren't locally installed code that alter the way Stremio works... this makes them simple and safe, but limits what they're capable of doing'. Take: constrain by narrowing the protocol, not by sandboxing arbitrary instructions — which is precisely 'the job may contain an infohash and nothing else'.
sources: https://boinc.berkeley.edu/wiki/BOINC_Security; https://github.com/actions/runner/blob/main/docs/design/auth.md; https://github.blog/changelog/2023-06-02-github-actions-just-in-time-self-hosted-runners/; https://github.com/concourse/concourse/blob/master/tsa/README.md; https://headscale.net/stable/ref/registration/; https://spiffe.io/docs/latest/spire-about/spire-concepts/; https://deepwiki.com/Stremio/stremio-web/7.2-addon-protocol-and-manifests

RECOMMENDATIONS:
- Build v1 as: outbound WSS (tokio-tungstenite + tokio-rustls, rustls 0.23) with mTLS against a private CA, carrying jobs that are detached-Ed25519-signed envelopes. Both layers, verified independently, fail-closed.
- Generate the root CA offline with rcgen 0.14.9 and never put its key on the control server; run an online issuing CA that only signs worker CSRs. Compile the root cert into the worker as its sole trust anchor.
- Enrollment: one-shot, 15-minute pairing tokens (headscale-style). Worker generates its own Ed25519 keypair, sends only a CSR, gets a 7-day cert with a `worker:<uuid>` URI SAN, auto-renews at 50% lifetime over mTLS. Token is burned server-side on first use.
- Put a `kid` on every signed job and ship the trusted-signer public key set in a trust bundle signed by the OFFLINE root — otherwise a compromised control server can mint its own job-signing key and the second layer buys you nothing.
- Verify in this order and abort on the first failure: kid known → ed25519-dalek `verify_strict` over DOMAIN_SEP||bytes → worker_id matches self AND envelope binds to this worker's cert SPKI hash → nbf/exp within 60s skew → nonce unseen (persistent store) → job_id not already executed → metainfo constraints.
- Make the job schema physically incapable of expressing 'fetch this URL': infohash (v1 and/or v2) plus a tracker allowlist, full stop. Recompute the infohash from fetched metadata before proceeding, and strip or allowlist `url-list` web seeds.
- Validate metainfo pre-flight — file count, total size, per-file size, extension allowlist — then sanitize every path component (reject `..`, absolute, empty, NUL, separators, non-UTF-8, Windows reserved names) on BOTH the .torrent ingest path and the peer/magnet metadata path. The Net::BitTorrent CVE happened because only the first path was checked.
- Enforce single-file selection by setting all other files to priority 0 before starting (librqbit selective download / libtorrent file_priority) rather than downloading-then-deleting, and sniff magic bytes (ftyp / EBML) on the first pieces with `infer` or `mimetype-detector` before committing to the rest.
- Back the application checks with OS containment: per-job directory under one fixed root, O_NOFOLLOW, systemd ProtectSystem=strict + ReadWritePaths + NoNewPrivileges (or a container with one bind mount), a byte accountant that kills at the cap, and a disk high-water mark that refuses new jobs.
- Harden the torrent side: no inbound listening port (passive mode), DHT/PEX/LSD off, stop seeding at completion, per-worker concurrent-job and daily-byte budgets, and a server-side infohash denylist checked at signing time.
- Use a raw detached Ed25519 envelope, or PASETO v4.public via rusty_paseto if you want a standard format. Do not use JWT. Do not reach for Biscuit unless third parties start submitting jobs that you re-scope before forwarding.
- Treat the legal design as a first-class deliverable alongside the crypto: published abuse contact, takedown workflow, job logs with retention, infohash denylist, and — for volunteer-run workers — explicit consent covering the fact that their IP is publicly visible in every swarm they join.

OPEN_QUESTIONS:
- Who physically runs the workers — the owner on rented VPSes, or volunteers on home connections? This flips the legal analysis (direct exposure vs. inducement + consent obligations) and decides whether ephemeral/JIT-style workers are even meaningful.
- Does the worker have to serve the downloaded video back out (HTTP range streaming, upload to object storage)? If so it needs an egress design, becomes a CDN node, and the 'no arbitrary URLs' rule needs an explicit signed-destination carve-out.
- Which infohash versions must be supported — v1 SHA-1 only, or v2/hybrid (BEP 52)? This constrains the torrent engine choice and the exact shape of the signed reference.
- Is an offline root CA operationally realistic for this owner, or should v1 accept a hot single-tier CA plus very short cert TTLs? The offline root only pays off if someone will actually keep it offline.
- Fleet size and churn: under ~50 stable workers, a Concourse-style authorized-worker-public-keys allowlist may be strictly simpler than running a CA at all. Above that, or with autoscaling, the CA + pairing-token path wins.
- Does librqbit expose per-file priority control before download starts (as opposed to filename-regex selection at add time), and can it disable DHT/PEX/LSD per torrent? If not, the choice is libtorrent bindings versus patching librqbit — worth verifying against the current source before committing.
- Jurisdiction of the control server and of the workers, and whether the owner intends to register a DMCA agent and claim safe harbor at all.

AGENT: web:piece-scheduling-theory

SUMMARY: Streaming piece scheduling is not "sequential download" — it is a deadline system layered on a rarest-first swarm, plus an aggressive cancel/re-request policy at the play head. The two reference designs diverge in an important way: anacrolix/torrent is *reader-driven* (readers publish a byte window; pieces inherit `Now`/`Readahead` priority from it; the request heap sorts by priority then rarity then index), while libtorrent is *deadline-driven* (`set_piece_deadline`, and `request_time_critical_pieces()` actively assigns the most urgent pieces to the peers with the lowest estimated download-queue time, once per second). anacrolix's stability comes from a readahead window that *grows with contiguous reading and collapses to zero on seek*; its stalls come from three concrete places — priority inversion (`PiecePriorityReadahead` outranks `PiecePriorityHigh`), a global 64 MiB unverified-bytes scan cutoff, and, most importantly, **no cancellation path when a reader abandons a region**: `cancelRequestsForPiece` is only ever called from `onPieceCompleted`, so after a seek the abandoned chunks keep occupying peer request slots until they arrive. For a Rust worker, librqbit is the closest structural reference (32 MiB per-stream lookahead, round-robin interleave across concurrent streams, `Drop` on the stream to retract the window), and TorrServer is the closest behavioural reference to the Go server being replaced (head preload + `max(piece_length, 8 MiB)` tail preload for moov/Cues, reader windows that split cache capacity by active reader count, and idle-reader demotion after 60 s). This repo's consumer is mediabunny issuing **closed** ranges out of order during container probing, then sequential reads, with a second concurrent reader for subtitle extraction — so multi-head scheduling and abort-driven priority retraction are first-class requirements, not edge cases.

### anacrolix priority model: the exact enum and who gets which level
`types/types.go` defines `PiecePriority byte` with iota ordering: `None=0, Normal=1, High=2, Readahead=3, Next=4 (deprecated), Now=5`. `Torrent.readerPiecePriorities()` assigns `Now` to *only the first piece* of each reader window (`now.Add(begin)`) and `Readahead` to the entire rest (`readahead.AddRange(begin+1, end)`). `Piece.purePriority()` then `Raise()`s across file priority, reader-now, reader-readahead, and explicit piece priority — max wins. Critical consequence: `Readahead(3) > High(2) > Normal(1)`, so *any* reader's speculative readahead outranks a file you explicitly marked High. That is the shape of the reported streaming regression in issue #698 (readahead/high blocks arriving before the block the play head is actually blocked on).
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/types/types.go; https://github.com/anacrolix/torrent/blob/master/piece.go; https://github.com/anacrolix/torrent/blob/master/torrent.go; https://github.com/anacrolix/torrent/issues/698

### anacrolix readahead window: what makes it stable
`reader.piecesUncached()` computes the window as `byteRegionPieces(pos, ra)` where `ra` comes from `ReadaheadFunc(ReadaheadContext{ContiguousReadStartPos, CurrentPos})`. The default is `CurrentPos - ContiguousReadStartPos` — the window is exactly as long as the contiguous run read so far, so it grows additively while playback is smooth and is worth nothing on a cold reader. Two guards do the stabilising work: `if ra < 1 { ra = 1 }` (a zero-width `[x,x)` range means 'want nothing') and `if !r.reading { ra = 0 }`. `reading` is set true only inside `readContext` when `len(b) > 0`. So a brand-new reader, or one that just seeked, prioritises exactly one piece until the first byte is actually demanded — speculative bandwidth is never spent on a head nobody is reading from.
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/reader.go

### anacrolix seek semantics
`reader.Seek` does: `if newPos != r.pos { r.reading = false; r.pos = newPos; r.contiguousReadStartPos = newPos; r.posChanged() }`. That collapses readahead to 0 and resets the growth baseline, so the window restarts at 1 piece and re-grows. `posChanged()` diffs the cached `pieceRange` against the new one and calls `Torrent.readerPosChanged(from, to)`, which recomputes the reader bitmaps and calls `updatePiecePriorities` over either two disjoint ranges or one merged span — i.e. the *old* window is repriced in the same pass as the new one. This is the right shape: seek is a range diff, not a full-torrent repriorityise.
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/reader.go; https://raw.githubusercontent.com/anacrolix/torrent/master/torrent.go

### anacrolix stall cause #1 — abandoned requests are never cancelled on seek
`Torrent.cancelRequestsForPiece(piece)` exists and loops `cancelRequest` over the piece's chunk range, but grep shows exactly one caller: `Torrent.onPieceCompleted` (torrent.go:2740). Nothing in the reader-position path cancels. `applyRequestState` only *adds* requests up to `nominalMaxRequests()` and only cancels via steal (`t.cancelRequest(req)` when another peer takes the request) or `deleteAllRequests` on choke. Meanwhile `updatePeerRequestsForPiece` early-returns for pieces no longer in `_pendingPieces`, and `isLowOnRequests()` is `Requests.IsEmpty() && Cancelled.IsEmpty()` — so a peer only recomputes its desired state once its queue fully drains. Net effect: after a seek, every peer keeps its pipeline full of chunks from the region you just abandoned, and the new play-head pieces cannot be requested until those land. This is the single largest source of post-seek stall.
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/torrent.go; https://raw.githubusercontent.com/anacrolix/torrent/master/requesting.go; https://raw.githubusercontent.com/anacrolix/torrent/master/peerconn.go

### anacrolix stall cause #2 — the 64 MiB unverified-bytes scan cutoff
`requestStrategy.GetRequestablePieces` scans the priority-ordered btree and accumulates `allTorrentsUnverifiedBytes += pieceLength` for every piece it considers; when that reaches `input.MaxUnverifiedBytes()` it `break`s. `config.go` defaults `MaxUnverifiedBytes: 64 << 20`. With 8–16 MiB pieces that is 4–8 pieces of scan depth *across all torrents sharing the storage group*. If a second reader (thumbnail head, subtitle pass) sits earlier in the order, the playback head's pieces can fall past the cutoff and simply never enter any peer's candidate list. Symptom: download rate stays high, play head does not advance.
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/internal/request-strategy/order.go; https://raw.githubusercontent.com/anacrolix/torrent/master/internal/request-strategy/NOTES.md; https://raw.githubusercontent.com/anacrolix/torrent/master/config.go

### anacrolix two-level ordering (global piece order + per-peer request heap)
Global: `pieceOrderLess` sorts by Priority desc, `Partial` desc (finish started pieces first), `Availability` asc (rarest-first), Index asc, then infohash. Per-peer: `desiredPeerRequests.lessByValue` sorts by allowed-fast (when choked), then piece priority, then 'already requested from this peer', then 'unrequested by anyone', then steal heuristics (fewest outstanding, most-recently-requested is the best cancel candidate), then `Availability` asc — and only then, *if the class is `PiecePriorityReadahead`*, by ascending piece index; otherwise by `t.pieceRequestOrder[i]`, which is `rand.Perm(numPieces())` (a per-torrent random affinity for swarm health). The in-source TODO is explicit that readahead ordering should also weigh distance from the reader position 'so that reads earlier in a torrent don't starve reads later in the torrent'. So rarest-first survives *as a tiebreak inside a priority class* — that is anacrolix's swarm-health compromise.
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/requesting.go; https://raw.githubusercontent.com/anacrolix/torrent/master/internal/request-strategy/order.go; https://raw.githubusercontent.com/anacrolix/torrent/master/torrent.go

### anacrolix responsive mode (sub-piece reads)
`Reader.SetResponsive()` makes `available()` skip the `t.pieceComplete(...)` gate and check `t.haveChunk(req)` instead, so reads return as soon as the 16 KiB chunks land, before the piece hash is verified. Doc comment: 'Don't wait for pieces to complete and be verified... May be deprecated, although BitTorrent v2 will mean we can support this without piece hashing.' This is the direct lever against hash-verify latency on first bytes, at the cost of possibly serving unverified data. TorrServer uses it unconditionally for preload readers and behind a `ResponsiveMode` setting for streams.
sources: https://raw.githubusercontent.com/anacrolix/torrent/master/reader.go; https://raw.githubusercontent.com/YouROK/TorrServer/master/server/torr/stream.go

### libtorrent time-critical algorithm (the deadline design, in full)
From docs/streaming.rst: pieces carry deadlines (`set_piece_deadline(index, ms_until_due, flags)`), are kept sorted earliest-deadline-first, and `torrent::request_time_critical_pieces()` runs **once per second**. It builds a peer list sorted by *download queue time* = `outstanding_bytes / estimated_download_rate`, **discards the slowest 10th percentile**, and excludes peers that are choking us, uninteresting, on parole, disconnecting, snubbed, or already over their outstanding-request cap. It then walks pieces in deadline order, requesting blocks from the current piece until it can't, sending each request to the peer with the lowest queue time and re-sorting that peer after every request. Peers lacking the piece are skipped for that piece only. The loop terminates when the top peer's queue time exceeds **2 seconds** (once/sec cadence keeps queues full with margin). Rate estimation fallbacks: if no payload in 30 s use the peak rate; if fewer than 2 blocks (32 KiB) received and unchoked less than 5 s ago, use the swarm-average rate of peers with outstanding requests.
sources: https://raw.githubusercontent.com/arvidn/libtorrent/master/docs/streaming.rst; https://www.libtorrent.org/reference-Torrent_Handle.html

### libtorrent adaptive timeouts and per-piece endgame ('busy requests')
streaming.rst: each torrent keeps a running average of piece download time and of the deviation from that mean. A time-critical piece is considered timed out once its elapsed time exceeds `avg + avg_deviation/2`. This scales: `timeouts = elapsed / (avg + avg_dev/2)`, and **each timeout permits one additional 'busy request'** — a duplicate request for a block already outstanding at another peer. Never twice from the same peer. This is endgame localised around the play head rather than at the end of the torrent, and it is explicitly framed as a zero-sum tradeoff: 'Any block you request that is not urgent will take away from the bandwidth you get for peers that are urgent.' Also: buffer all requests generated in one pass and flush them together so they coalesce into one packet.
sources: https://raw.githubusercontent.com/arvidn/libtorrent/master/docs/streaming.rst

### libtorrent's sequential_download is explicitly declared inadequate for streaming
streaming.rst frames the two modes as different ways of managing peer request queues: `sequential_download` 'will simply wait until a queue slot opens up, and request the next piece in the sequence... it's sub-optimal for streaming: piece 0 may be requested from a slow peer, and fast peers will get requests for later-index pieces instead of retrying more-critical ones.' The time-critical logic instead does 'active management of peer request queues, such that the most time-critical pieces occupy the best queue slots, across all peers.' This is the sentence to design against: a purely sequential Rust picker will reproduce exactly the described failure.
sources: https://raw.githubusercontent.com/arvidn/libtorrent/master/docs/streaming.rst; https://libtorrent.org/streaming.html

### libtorrent settings that interact with streaming
`whole_pieces_threshold=20` (if a whole piece can be fetched in ≤N seconds, prefer requesting whole pieces from that peer — good for hash locality, bad for first-byte latency on huge pieces); `piece_timeout=20`; `request_timeout=60` (per 16 KiB block, then re-request elsewhere); `request_queue_time=3` (queue depth expressed in seconds of the peer's rate, i.e. pipeline depth is bandwidth-derived, not a constant); `max_out_request_queue=500` hard ceiling; `strict_end_game_mode=true` (a block may only be duplicated when every remaining piece has at least one request — note the time-critical path *bypasses* this via busy requests); `prioritize_partial_pieces=false` by default (rarity wins over finishing partials, which is wrong for streaming — partials near the head should win).
sources: https://www.libtorrent.org/reference-Settings.html

### librqbit — closest Rust reference for window + multi-head
`crates/librqbit/src/torrent_state/streaming.rs`: `PER_STREAM_BUF_DEFAULT = 32 * 1024 * 1024` ('32 mb lookahead by default'). Each `StreamState` computes `queue()` as the piece range `[pos, pos+32MiB)` clamped to the file. `TorrentStreams::iter_next_pieces` collects one such iterator per active stream, **shuffles the vector** ('Shuffle to decrease determinism and make queueing fairer'), then round-robin interleaves them — 'Interleave 1st, 2nd etc pieces from each active stream in turn'. Piece completion wakes only streams whose `current_piece` matches (`wake_streams_on_piece_completed`). `impl Drop for FileStream` calls `drop_stream(stream_id)`, so an aborted HTTP request retracts its window immediately. `stream()` also calls `maybe_reconnect_needed_peers_for_file` to wake peers dropped as 'not needed'. The picker consumes this as `priority_pieces` in `acquire_piece`, alongside `peer_avg_time` and a `can_steal` predicate, returning `Reserved | Stolen{piece, from_peer} | NoneAvailable`.
sources: https://raw.githubusercontent.com/ikatson/rqbit/main/crates/librqbit/src/torrent_state/streaming.rs; https://raw.githubusercontent.com/ikatson/rqbit/main/crates/librqbit/src/torrent_state/live/mod.rs; https://raw.githubusercontent.com/ikatson/rqbit/main/crates/librqbit/src/chunk_tracker.rs

### librqbit's Range handler — copy the structure, not the 416 rule
`http_api/handlers/streaming.rs` sets `Accept-Ranges: bytes` always, parses only `bytes=start-[end]` (single range, open-ended supported), seeks, sets `Content-Length` to the range span and `Content-Range: bytes {start}-{end-1}/{len}`, returns 206, and wraps in `ReaderStream::with_capacity(stream, 65536)`. It does **not** support suffix ranges (`bytes=-N`) and it returns 416 when `end > stream.len()` — RFC 9110 §14.1.2 says a last-byte-pos beyond the length 'can be treated as equal to the current length minus one', i.e. clamp, don't reject. Safari in particular sends ranges it expects clamped. Do not port that branch.
sources: https://raw.githubusercontent.com/ikatson/rqbit/main/crates/librqbit/src/http_api/handlers/streaming.rs; https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests

### TorrServer — the Go/anacrolix design the old server most resembles
Two mechanisms worth porting. (1) Preload (`server/torr/preload.go`): `startend := Info().PieceLength; if startend < 8<<20 { startend = 8<<20 }` — it opens a head reader (`SetResponsive()`, readahead `pieceLength*4`) and, concurrently in a goroutine, a **tail reader seeked to `file.Length() - startend`** with readahead 0, reading in 32 KiB chunks. That is the moov/Cues fetch, done as a real reader so it inherits `Now`/`Readahead` priority instead of needing a separate priority API. (2) Reader windows (`storage/torrstor/reader.go`): `getOffsetRange()` is `begin = pos - (capacity/readers)*(100-pct)/100`, `end = pos + (capacity/readers)*pct/100` — the window has a **behind portion** (for the browser re-reading bytes it already consumed) and the cache is divided by the number of *active* readers. `checkReader()` demotes a reader idle >60 s (`readerOff`: readahead 0 and seek to 0) whenever more than one reader exists, and `Close()` triggers `cache.getRemPieces()`.
sources: https://raw.githubusercontent.com/YouROK/TorrServer/master/server/torr/preload.go; https://raw.githubusercontent.com/YouROK/TorrServer/master/server/torr/storage/torrstor/reader.go; https://deepwiki.com/YouROK/TorrServer/3.8-streaming-and-playback

### torrent-stream / WebTorrent — the 'critical window' and hotswap heuristics
`torrent-stream/lib/file-stream.js`: `this._critical = Math.min(1024 * 1024 / pieceLength, 2) | 0` — when the stream blocks on a piece it calls `engine.critical(piece, width)`, marking roughly 1 MiB (capped at 2 pieces) as critical. `critical[i]` is passed as the `hotswap` flag to `_request`, which permits taking an already-reserved block. WebTorrent's `_hotswap(wire, index)`: only a wire with `downloadSpeed() >= BLOCK_LENGTH` may hotswap; it finds the slowest wire holding a reservation on that piece with `otherSpeed < SPEED_THRESHOLD (= 3 * BLOCK_LENGTH ≈ 48 KiB/s)` and `2 * otherSpeed <= speed`, nulls its reservation and cancels its outstanding blocks for that piece. `speedRanker()` is the preventive half: for a slow wire it computes `secs = max(1, wire.requests.length) * BLOCK_LENGTH / speed` and refuses a piece if any faster wire that has it could cover the `missing` bytes within that time — i.e. don't let a slow peer squat the play head. Selections are sorted by priority and `shufflePriority` rotates within an equal-priority run for fairness.
sources: https://raw.githubusercontent.com/mafintosh/torrent-stream/master/lib/file-stream.js; https://raw.githubusercontent.com/mafintosh/torrent-stream/master/index.js; https://raw.githubusercontent.com/webtorrent/webtorrent/master/lib/torrent.js

### Container gotcha: MP4 moov and Matroska Cues both live at the tail in the general case
MP4: the moov atom is conventionally written last because it is only complete once all samples are muxed; `-movflags +faststart` relocates it, but torrent releases are not faststart. Until moov is read the demuxer knows nothing — no codecs, no sample table, no seeking. Matroska (RFC 9559 / matroska.org 'Element Ordering'): 'If the Cues Element is present, then it SHOULD either be stored before the first Cluster Element or be referenced by a SeekHead Element'; in practice Cues are typically written after all Clusters. If the first SeekHead does not itself name Cues, players treat the file as non-seekable. Practical rule: on open, prime **head and tail concurrently** — head for ftyp/EBML header + track info, tail for moov/Cues — and size the tail at `max(piece_length, 8 MiB)` (TorrServer's number) rather than a fixed byte count, so it is at least one piece.
sources: https://www.matroska.org/technical/ordering.html; https://datatracker.ietf.org/doc/rfc9559/; https://www.matroska.org/technical/streaming.html; https://milankragujevic.com/torrent-streaming-in-depth; https://github.com/qbittorrent/qBittorrent/discussions/20280

### Piece size vs Range granularity, and hash-verify latency on first bytes
BitTorrent v1 hashes are per-piece: a 16 MiB piece must arrive in full and hash-verify before a single verified byte can be served. Browsers, by contrast, open with a 1–2 byte probe. Two mitigations. (a) Serve unverified chunks (anacrolix `SetResponsive`), accepting that a bad peer can poison the first bytes. (b) BitTorrent v2 (BEP 52) builds a merkle tree 'with a branching factor of 2, constructed from 16KiB blocks of the file', and the metainfo `piece layers` dict stores 'concatenated hashes of one layer within that merkle tree', with 'the layer chosen so that one hash covers piece length bytes'; peers exchange hash requests specifying 'a pieces root, base layer, index, length, and proof layers' — which lets you verify at 16 KiB granularity without the whole piece. If the worker supports v2/hybrid torrents, wire block-level verification and drop responsive mode's trust assumption for those.
sources: https://www.bittorrent.org/beps/bep_0052.html; https://raw.githubusercontent.com/anacrolix/torrent/master/reader.go

### Choking on unpopular swarms — the cold-start problem the Fast Extension exists for
BEP 6 rationale: a new peer with nothing to trade 'takes several minutes to ramp up before it can effectively engage in BitTorrent's tit-for-tat', receiving occasional optimistic unchokes but unable to reciprocate enough to stay unchoked. Allowed Fast gives a deterministic small set (currently 10) of pieces a peer may request **while choked**. Reject Request makes choke-while-requests-outstanding unambiguous ('Choke no longer implicitly rejects all pending requests'), which matters because anacrolix's `deleteAllRequests("choked by non-fast PeerConn")` throws away the whole pipeline on a non-fast peer's choke — an instant stall on a thin swarm. Have All / Have None save the bitfield round trip. On an unpopular swarm the streaming picker must also over-connect: librqbit calls `reconnect_all_not_needed_peers()` the moment a stream opens, and libtorrent's time-critical peer list explicitly excludes choked/snubbed/on-parole peers rather than waiting on them.
sources: https://www.bittorrent.org/beps/bep_0006.html; https://www.bittorrent.org/beps/bep_0003.html; https://raw.githubusercontent.com/anacrolix/torrent/master/peerconn.go; https://raw.githubusercontent.com/ikatson/rqbit/main/crates/librqbit/src/torrent_state/streaming.rs

### Swarm health: the BiToS split, and why pure sequential is antisocial
BiToS (Vlavianos, Iliofotou, Faloutsos, GI'06) partitions undownloaded pieces into a High Priority Set (near the play head) and a Remaining Pieces Set, and picks from the HPS with probability p and from the remainder with probability 1−p, using **rarest-first inside each set**. Their result: p ≈ 0.8 with a modest HPS performs best, because the 20 % spent outside the window 'acquires rare pieces before they become extinct and increases the diversity of exchanged pieces between peers'. This is the citable justification for reserving a slice of request slots for rarest-first outside the play window — and it converges with what anacrolix already does implicitly by using availability as the tiebreak inside every priority class and `rand.Perm` as the final ordering for non-readahead pieces.
sources: http://alumni.cs.ucr.edu/~aggelos/papers/BiToS.pdf; https://www.bittorrent.org/beps/bep_0003.html; https://raw.githubusercontent.com/anacrolix/torrent/master/requesting.go

### HTTP Range contract the range server must honor (RFC 9110)
§14.1.2: `bytes=a-b` inclusive; `bytes=a-` means everything from a onward; `bytes=-N` is a **suffix** meaning the last N bytes (browsers and demuxers use this to grab moov/Cues); a last-byte-pos beyond the length 'can be treated as equal to the current length minus one' — clamp, never 416. §15.5.17: 416 only when the byte-range-set is genuinely unsatisfiable (first-byte-pos >= length), and the 416 response should carry `Content-Range: bytes */<len>`. §14.3: advertise `Accept-Ranges: bytes`. §15.3.7: 206 carries `Content-Range: bytes a-b/len` and `Content-Length` equal to the *span*, not the file size. §14.2 permits ignoring Range, but browsers will punish you: Safari probes with a tiny range and refuses to render `<video>` unless it gets a 206, and it reconnects every few MB, so every reconnect is a fresh Range that must be served promptly.
sources: https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests; https://blog.logrocket.com/streaming-video-in-safari/; https://corevo.io/the-weird-case-of-video-streaming-in-safari/; https://www.zeng.dev/post/2023-http-range-and-play-mp4-in-browser/

### This repo's actual consumer shape (constrains the design)
The bridge is addressed at `http://127.0.0.1:32227` (`web/src/localHelper.ts`, `HELPER_ORIGIN`), and reads go through `GET /stream/{id}/{fileIndex}` with `Range: bytes=${start}-${endInclusive}` — accepting either 200 or 206 (`response.ok && status !== 206` is the failure test), so the server must not assume the client tolerates only one form. The real reader is mediabunny: `web/src/pipeline/mediaInput.ts` builds a `CustomSource` whose read is `fetch(url, { headers: { Range: 'bytes=' + start + '-' + (end-1) } })` and a `UrlSource(url)` for the direct case; `web/src/pipeline/remuxJob.ts` does the same and additionally runs a **separate** subtitle-extraction pass reading `SUBTITLE_SLICE_BYTES` slices concurrently with the remux. So: closed ranges, small and out-of-order during container probing (box/EBML walking), then long sequential runs, with at least two live read heads. Multi-head interleaving and per-request window retraction on abort are load-bearing, not optional.
sources: /home/minelli/projects/ss/web/src/localHelper.ts; /home/minelli/projects/ss/web/src/pipeline/mediaInput.ts; /home/minelli/projects/ss/web/src/pipeline/remuxJob.ts; /home/minelli/projects/ss/web/src/torrent.ts

RECOMMENDATIONS:
- MODEL: keep two separate layers, exactly as libtorrent and anacrolix both do. Layer 1 is a set of registered *read heads* (one per in-flight HTTP Range response), each publishing `{file, pos, window_len, last_read_at, contiguous_start}`. Layer 2 is a picker that derives per-piece urgency from the union of heads and nothing else. Never let an HTTP handler poke piece priorities directly — it makes cancellation impossible to get right.
- PRIORITY CLASSES: use four, ordered `Now > Readahead > Normal > None`, and — unlike anacrolix — put an explicit `Critical` (or a deadline number) *above* `Readahead` rather than below it. anacrolix's `Readahead(3) > High(2)` inversion is the reported streaming regression in issue #698; do not reproduce it. Assign `Now` to only the piece each head is currently blocked on (anacrolix's `now.Add(begin)`), `Readahead` to the rest of its window.
- DEADLINES OVER PURE ORDERING: give every piece in a window a deadline `now + (bytes_ahead_of_head / target_rate)` and sort the time-critical list earliest-deadline-first, as `set_piece_deadline` does. It composes correctly across multiple heads (a thumbnail head 400 MB away naturally sorts behind the play head) whereas a bare priority enum forces you to invent tiebreaks.
- PEER ASSIGNMENT: implement libtorrent's `request_time_critical_pieces` loop. Maintain per-peer `outstanding_bytes` and an estimated rate (peak rate if no payload for 30 s; swarm average if <32 KiB received and unchoked <5 s ago). Sort peers by `outstanding_bytes / rate`, drop the slowest 10 %, exclude choked/uninteresting/snubbed/over-queue peers. Walk pieces deadline-first, assign each block to the current lowest-queue-time peer, re-sort after each assignment, and stop the loop when the top peer's queue time exceeds 2 s. Run it on a 1 Hz tick and buffer the requests, flushing once per pass so they coalesce.
- WINDOW SIZING: make the window a function of measured throughput and contiguity, not a constant. Start at one piece (anacrolix's `if !reading { ra = 0 }` guard is what keeps a cold or just-seeked head from burning bandwidth), grow it as `current_pos - contiguous_read_start_pos`, and clamp it to a per-head budget of `cache_capacity / active_heads` (TorrServer's rule) with a hard ceiling around 32 MiB (librqbit's `PER_STREAM_BUF_DEFAULT`). Include a small *behind* portion (TorrServer splits the budget by a percentage) so the browser re-reading already-consumed bytes doesn't force a re-download.
- ON OPEN: (1) fetch metadata (DHT/trackers) and resolve the file; (2) immediately register two transient heads — head at offset 0 and a tail head at `len - max(piece_length, 8 MiB)` — and prioritise them concurrently, because moov may be at the end and Matroska Cues usually are; (3) return the file list only once both are in flight so the first probing Range doesn't wait on a cold picker; (4) call the equivalent of librqbit's `reconnect_all_not_needed_peers()` to un-park peers dropped as unneeded. Do NOT block the HTTP 206 on the preload completing — serve and let the reader block per-byte.
- ON PLAY: register a persistent head for the response. Serve bytes as chunks land rather than waiting for whole-piece hash verification (anacrolix `SetResponsive`) if you accept unverified data; prefer BEP 52 block-level merkle proofs where the torrent is v2/hybrid, since `piece layers` is defined precisely so one hash covers a piece and lower layers verify 16 KiB blocks. Mark the 1–2 pieces at the blocked head as duplicate-request-eligible (torrent-stream's `min(1MiB/piece_length, 2)`), which is endgame localised at the play head.
- ON PLAY, ANTI-SQUAT: port WebTorrent's two heuristics. Preventively, refuse to assign a head-adjacent piece to a peer whose rate cannot deliver the piece's `missing` bytes within `max(1, outstanding)*16KiB/rate` when a faster peer has it (`speedRanker`). Reactively, hotswap: a peer at ≥16 KiB/s may cancel and take a critical piece reserved by a peer at <48 KiB/s when `2*slow_rate <= fast_rate`. Then apply libtorrent's escalation: `timeouts = elapsed / (avg_piece_time + avg_dev/2)`, allowing one extra duplicate request per timeout, never twice to the same peer.
- ON SEEK: this is the step to get right, and it is where anacrolix leaks. Do all four, atomically: (a) move the head, reset `contiguous_start = new_pos` and collapse the window to one piece; (b) drop the abandoned range's pieces to `None` **and actively send BitTorrent `cancel` for every outstanding chunk in it** — anacrolix's `cancelRequestsForPiece` is only ever called from `onPieceCompleted`, so its peers keep their pipelines full of dead chunks and the new head can't be requested until they drain; (c) keep already-*partial* pieces in the abandoned range at low-but-nonzero priority so you don't throw away half-downloaded work (libtorrent's `prioritize_partial_pieces`, and `Partial` is the second key in anacrolix's `pieceOrderLess`); (d) snap the window start to the containing piece boundary, not the byte offset, and remember that the browser will usually seek to a keyframe *before* the requested time.
- ON ABANDON: tie window lifetime to the HTTP response body, not to a timeout. Give the head-registration a `Drop` impl that unregisters and cancels (`impl Drop for FileStream` in librqbit); in axum/hyper the body future is dropped when the client aborts, so this fires on the seek-triggered connection reset that browsers do. Add a belt-and-braces idle sweep — demote any head with no read in 60 s to zero readahead when other heads exist (TorrServer's `checkReader`/`readerOff`) — for the case where a half-open TCP connection means Drop never runs.
- SWARM HEALTH: reserve a fixed fraction of request slots for rarest-first outside every window — BiToS measured p ≈ 0.8 toward the play head / 0.2 toward rarest-first as the sweet spot. Cheaper equivalent, and what anacrolix actually does: use availability ascending as the tiebreak *inside* each priority class, and a per-torrent `rand.Perm(num_pieces)` as the final ordering for `Normal` pieces so different peers don't all pick the same piece. Also keep uploading and keep the torrent seeding after the read heads close; a streaming client that leaves at EOF is the thing the swarm-health complaint is actually about.
- PICKER SCAN DEPTH: if you copy anacrolix's global piece-order btree with an unverified-bytes cutoff, size the cutoff against `piece_length × active_heads`, not a fixed 64 MiB. With 16 MiB pieces and two heads, the 64 MiB default is four pieces of scan depth and the second head can push the play head off the end of the scan — high download rate, zero playback progress.
- RANGE SERVER: advertise `Accept-Ranges: bytes` unconditionally. Support `bytes=a-b`, open-ended `bytes=a-`, and suffix `bytes=-N` (RFC 9110 §14.1.2) — the suffix form is how demuxers grab moov/Cues. Clamp `b >= len` to `len-1` rather than returning 416; reserve 416 (with `Content-Range: bytes */len`) for `a >= len`. Answer 206 with `Content-Range: bytes a-b/len` and `Content-Length` equal to the span. Answer 206 even for a 2-byte probe or Safari will refuse to render the video. Ignore/415 multi-range (`bytes=0-99,200-299`) rather than half-implementing multipart/byteranges. Send `Content-Type` from the file extension and set the CORS headers the page already expects on `127.0.0.1:32227`.
- TESTING: build three regression tests before optimising anything — (1) seek-storm: 20 seeks in 10 s, assert time-to-first-byte after the last seek stays bounded and that outstanding requests for abandoned ranges drop to zero within one tick; (2) two-head fairness: a play head plus a thumbnail head 80 % into the file, assert the play head's throughput share does not collapse (librqbit's interleave-and-shuffle is the fix if it does); (3) thin swarm: 2 peers, both choking, assert the Fast Extension allowed-fast set is used and that a choke does not discard the whole pipeline.

OPEN_QUESTIONS:
- Is ss-bridge going to embed librqbit as a dependency, or implement its own picker? librqbit already gives you multi-head interleave, the 32 MiB window, Drop-based retraction and a working Range handler; the gaps you'd still have to add are deadline-ordered peer assignment, hotswap/busy-requests, and head+tail preload. Building from scratch means re-deriving all of it.
- Does the worker need to serve MSE/`<video>` directly, or only mediabunny? The repo today reads through mediabunny's CustomSource with closed ranges, which is far more forgiving than Safari's `<video>` (tiny 206 probe, reconnect every 4–5 MB). If direct playback is never a target, the Safari-specific Range rules can be relaxed; if it might be, they are cheap to honor now.
- What is the acceptable trust posture for responsive (pre-hash-verify) reads? Serving unverified chunks is the single biggest first-byte latency win on 8–16 MiB pieces, but a malicious peer can poison the moov and the remux will produce garbage. Options: responsive only for v2/hybrid torrents (block-level merkle), or responsive plus a re-verify-and-invalidate pass.
- Should abandoned-but-partial pieces be kept, and with what storage budget? Keeping them helps a seek-back-and-forth user enormously but needs a cache eviction policy; TorrServer solves this with a fixed-capacity piece cache and `getRemPieces()` on reader close. Unbounded retention on a user's laptop is not acceptable.
- How large are the piece sizes in practice for the torrents this serves? The whole first-byte-latency story changes between 1 MiB and 16 MiB pieces, and it determines whether the 8 MiB tail preload is one piece or eight.

SUMMARY: The seven summaries are strong on the two halves that already have prior art — the Rust engine (librqbit's play-head-driven prioritizer) and the browser demuxer (mediabunny's random-access Source) — but they share a blind spot in the middle: every one of them assumes "a 206 byte-range server in front of a torrent engine" without ever asking how a browser on https://ss.giuli.dev reaches such a server running on a stranger's home machine. That single unanswered question (TLS trust, CORS, NAT, and who pays for the bytes) determines the egress bill, the legal posture, and whether mediabunny's UrlSource can be used at all — and it forks the architecture three ways (server relay / per-worker public cert or tunnel / WebRTC-WebTransport datachannel) that nobody costed. Underneath it sit several unverified assumptions the current code makes precisely because the byte source is loopback: unauthenticated URLs handed to a Web Worker, `prefetchProfile: 'network'` justified in a comment by "the helper sits on loopback", strict-full-length blocking reads with no abort and no timeout, and a subtitle pass that walks the whole file front-to-back. Two more gaps are strategic rather than technical: nobody measured today's local ss-bridge to establish that it is the bottleneck (the rust-libs sweep in fact says the wins are in the bridge's HTTP layer), and nobody costed the sparse-timeline publishing work, which is the actual blocker on free seeking and lives entirely in the existing Go server and player, not in any worker. Finally, the security sweep designs server↔worker trust but leaves the browser — the party that will actually consume, remux and publish the bytes into the room — with no way to authenticate the worker, no way to verify the bytes match the infohash, and no credential to present.

### The browser→remote-worker byte path is never specified, and it is the load-bearing unknown
All seven summaries model the byte source as 'a plain 206 Partial Content range server' (Stremio/TorrServer/rqbit) and mediabunny needs exactly that. None says how a page on https://ss.giuli.dev issues a Range request to a worker on a volunteer's home connection. Four constraints must be satisfied simultaneously and no summary names them together: (1) mixed content — the page is a secure context, so plain http:// to a remote worker is blocked outright; the current design works ONLY because loopback is the one mixed-content exemption (web/src/localHelper.ts:19, `http://127.0.0.1:32227`). (2) TLS trust — the security sweep recommends mTLS with a *private* CA, which the browser will never trust; a worker needs a WebPKI-valid cert for a name that resolves to it. (3) CORS — preflight for the Range header plus Access-Control-Expose-Headers for Content-Range/Content-Length, per worker, per origin. (4) NAT — a residential worker has no inbound port. The three real answers (relay every byte through the VPS; give each worker a tunnel/wildcard-DNS + public cert; or drop HTTP for a fingerprint-authenticated transport) have wildly different cost and legal profiles and none was evaluated.
sources: web/src/localHelper.ts:19; web/src/pipeline/mediaInput.ts:60; web:signed-worker-security; web:stremio-torrserver

### Egress ledger is entirely absent — the worker fleet may re-create the exact wall it was built to break
No summary counts bytes. A 2h 1080p release is 4–10 GB. If bytes relay through the VPS, that file crosses the server twice (worker→server ingress, server→browser egress) per room, on top of the remuxed output the browser then PUTs to R2 and every viewer pulls back out. That is 3–4 full traversals of the media per viewing. The git sweep records the old era's ceiling as ~2–4 concurrent rooms with a 0.49 MB/s browser round trip — a bandwidth wall, not a CPU wall. Distributing the *download* to workers does nothing about that wall if the bytes still funnel through one VPS; the fleet only helps if workers serve the browser directly, which loops straight back to the TLS/CORS/NAT fork above. This ledger should be drawn before any other decision, because it is the one that decides the fork.
sources: git:server-torrent-era; web:signed-worker-security

### WebRTC / WebTransport were dismissed for the OLD architecture and never re-evaluated for the new one
The git sweep records that in-browser WebTorrent was rejected — correctly, since public swarms are TCP/uTP and a browser WebRTC peer cannot reach them. But the new architecture supplies the missing bridge: a Rust worker is a native swarm peer AND can terminate a WebRTC datachannel (webrtc-rs/str0m) or a WebTransport session (quinn, already in the recommended crate set). Either one answers all three blockers at once — ICE/STUN for NAT with TURN only as fallback, DTLS/QUIC certificate *fingerprints* instead of WebPKI certs (WebTransport `serverCertificateHashes` accepts self-signed certs under ~14-day validity), and no CORS because neither is a fetch. The cost is that you lose HTTP Range semantics and must frame request/response yourself, and mediabunny would need a CustomSource over that channel rather than a UrlSource. This may be the only design that gets direct worker→browser bytes without issuing a public certificate per volunteer, and it appears in none of the summaries.
sources: git:server-torrent-era; web:signed-worker-security

### The browser has no credential to present to a worker, and the current job shape cannot carry one
The security sweep designs job authorization (server→worker, signed envelope) but says nothing about read authorization (browser→worker). A reachable worker's /stream URL would be an unauthenticated public read of a copyrighted file — an open proxy anyone can scrape. Worse, the repo cannot easily fix this: the remux runs in a Web Worker, so the job must be structured-cloneable, which is why a bare URL string is passed (web/src/upload.ts:281-282, `{ kind: 'stream', url: file.streamUrl, ... }`) and turned into a headerless `fetch(url, { headers: { Range } })` (web/src/pipeline/remuxJob.ts around 90-118, web/src/pipeline/mediaInput.ts:60). mediabunny's UrlSource likewise cannot attach headers. So the only credential form that fits today is a query-string capability token (short TTL, scoped to room+file+worker) — which has its own leak-in-logs problem. Anything header-based means redesigning how the job crosses into the worker.
sources: web/src/upload.ts:281; web/src/pipeline/remuxJob.ts:116; web/src/pipeline/mediaInput.ts:60; web:signed-worker-security

### Nothing verifies the worker actually served the bytes the infohash promises
The security sweep's central insight — 'a job carries an infohash, never a URL, because infohashes are self-authenticating' — protects the WORKER from the server. It does not protect the BROWSER from the worker. A malicious or compromised volunteer worker can serve arbitrary bytes for any range; mediabunny remuxes whatever it is handed; the host's browser then presigns that output into the room's R2 bucket and every viewer plays it. The presign path bounds size only, not content (internal/httpapi/clientmedia.go:44, budgetSlack), and the claim model (clientmedia.go:84-116) authenticates the producing browser, not its source. Options — ship the piece hashes to the browser so it can verify each range, or accept worker attestation and treat the fleet as trusted — have very different implications and neither was considered.
sources: internal/httpapi/clientmedia.go:44; internal/httpapi/clientmedia.go:84; web:signed-worker-security

### Read amplification: the code's own justification for its prefetch profile stops being true off loopback
Both CustomSource constructions use `prefetchProfile: 'network'` with the comment 'The helper sits on loopback' (web/src/pipeline/mediaInput.ts:50 and the duplicated streamInput at web/src/pipeline/remuxJob.ts:116). The mediabunny sweep separately records that UrlSource issues OPEN-ENDED ranges (`bytes=N-`) and aborts them. Over loopback an over-fetch-then-abort costs nothing; over a metered relay or a volunteer's uplink it is real, billable, wasted bytes, and an aborted open-ended range on a worker also strands the piece window it armed. Nobody measured what 'network' prefetch actually pulls per seek. Compounding it: the reads are strict-full-length and unabortable — `helper short read` throws if fewer bytes arrive (localHelper.ts:223, remuxJob.ts:103) — with no timeout on the fetch at all, so a stalled remote swarm becomes a permanently hung promise rather than a retryable error.
sources: web/src/pipeline/mediaInput.ts:50; web/src/pipeline/remuxJob.ts:103; web/src/pipeline/remuxJob.ts:116; web/src/localHelper.ts:223; web:mediabunny-seek

### The subtitle pass is a full-file transfer, and remotely that is a second full copy of the movie
current:seek-pipeline flags 'sequential assumption #1 (worst): the subtitle pass reads the whole file front to back in 8 MiB slices, concurrently with the remux.' Locally this is a nuisance that fights the remux for the swarm. Remotely it is a second complete download of a 4–10 GB file over the relay or the volunteer's uplink, running in parallel with the seek-driven reads it is competing against, and it defeats the entire premise of requirement 3 (streaming starts without the whole file). No summary treats this as a blocker for the remote design specifically — it is one. It also interacts with librqbit's 8-simultaneous-stream ceiling and with the browser's per-origin connection limit (6 on HTTP/1.1), a concurrency budget nobody drew.
sources: current:seek-pipeline; web:rust-torrent-libs; web:piece-scheduling-theory

### Free seeking is blocked by the publishing model, not by the torrent engine — and that work is uncosted
current:seek-pipeline is explicit that the demux/remux half already works (random-access Source, MKV cues, the local patch making trimmed regions copy instead of re-encode) and that the blockers are the one-region-at-a-time model: `playlists.clear()` (web/src/pipeline/clientMedia.ts:462), a single scalar `mediaOffsetMs` threaded through the whole player (web/src/types.ts:123, web/src/player/Player.tsx:125-126,432,554-556), and a server renderer that truncates a playlist at its first unconfirmed segment. 0:00→20:00→40:00 needs three regions simultaneously playable. No summary evaluates the two candidate designs (one playlist with EXT-X-GAP/DISCONTINUITY placeholders vs N playlists with client-side switching), nor verifies that hls.js tolerates GAP tags mid-playlist without stalling, nor how varying EXT-X-MAP across discontinuities behaves. This is the highest-unknown work item, it sits entirely in the existing Go server and React player, and building the whole worker fleet without it delivers zero free seeking.
sources: web/src/pipeline/clientMedia.ts:462; web/src/types.ts:123; web/src/player/Player.tsx:125; current:seek-pipeline

### No baseline for the status quo, and 'fix ss-bridge in place' was never scored as the competing option
The git sweep quotes the OLD server era's numbers (0.49 MB/s browser round trip, 0 B/s with 35 peers between range reads, 2–4 concurrent rooms) but there is no equivalent measurement of today's local ss-bridge, which is the actual thing being replaced and is by construction faster than any remote design (no relay, no TLS, no WAN RTT). Meanwhile the rust-libs sweep says the real wins now are in the bridge's HTTP layer and names three concrete defects: the Range handler buffers the whole window in RAM (defeating progressive delivery), suffix ranges `bytes=-500` are mis-served as `bytes=0-500`, and the blocking-permit ceiling is never raised. Those are days of work in a component that already exists, and combined with a playhead-priority endpoint they would deliver requirement 3 with no fleet, no certificates and no legal exposure. The decision memo should carry that option with its own scorecard.
sources: git:server-torrent-era; web:rust-torrent-libs

### Legal exposure lands on volunteers' residential ISPs, and signing a job is evidence of direction
The security sweep correctly identifies legal risk as the dominant residual risk and notes every worker's IP is publicly visible in the swarm — but stops there. Unworked: workers are volunteers' home connections, so a notice goes to a residential ISP that terminates accounts, not to a VPS operator who can absorb it; there is no designed consent/disclosure surface for a worker operator; and cryptographically signing an envelope that names a specific infohash is affirmative, auditable evidence that the service *directed* the download, which is a worse posture than being a passive relay. Also unstated as a requirement: seeding. librqbit will upload by default, and a seeding worker is a distributor — 'download only, never seed, no DHT announce, no PEX' needs to be an explicit, verified config, not an assumption.
sources: web:signed-worker-security; web:rust-torrent-libs

### 'Video torrents only' is weaker enforcement than the summary implies
The security sweep's chain (verified metainfo → size caps, file-count caps, extension allowlist, single-file selection, path sanitization, url-list stripping) is sound as far as it goes, but an extension allowlist over metainfo is trivially defeated: name a RAR archive .mkv, or ship one real video among 700 files and select only it while the rest never downloads (which the allowlist happily permits). The sweep mentions content sniffing without saying at what granularity it runs, what happens to bytes already written when a sniff fails mid-download, or how sniffing survives the fact that the worker downloads pieces out of order for streaming — the first bytes of a file may not be the first bytes to arrive.
sources: web:signed-worker-security

### Server-side torrenting does not free the room from the host's tab, so the stability gain is smaller than assumed
The stated motivation is that the pre-8abe402 server era was 'more stable'. But in that era the server also did the ffmpeg remux, so the download AND the conversion survived the browser. The new direction keeps all media processing in the browser (requirement 1), which means the tab must stay open for the whole remux regardless — the room is still hostage to one person's window, one claim (internal/httpapi/clientmedia.go:84-116), and one sweeper reclaiming stale claims. Recorded pain point #2 of the old era (the idle sweeper deleting rooms out from under live ffmpeg) has an exact analogue here: worker job lifetime, client-claim idle TTL, and room TTL are three independent clocks that must be reconciled, and no summary reconciles them.
sources: internal/httpapi/clientmedia.go:84; internal/room/sweeper.go:24; git:server-torrent-era

### Backwards seeking versus bounded worker caches — the one pitfall that directly contradicts requirement 3
The Stremio/TorrServer sweep names 'a bounded cache that lies about piece completeness stalls every backwards seek' as a top pitfall, and the rust-libs sweep notes librqbit is sparse-on-disk with NO piece eviction. Free seeking makes backwards seeks normal (0:00→40:00→back to 0:00), so a worker holding volunteers' disks needs either full-file retention (a 4–10 GB disk commitment per concurrent room, with quota and GC that nobody specified) or eviction (which reintroduces the stall). Related and unaddressed: does a worker persist partial data across restarts; what happens when a worker vanishes mid-playback and the job is re-dispatched to a worker with zero pieces (a cold restart the player experiences as an unexplained permanent stall).
sources: web:stremio-torrserver; web:rust-torrent-libs

### Dispatch, placement and worker honesty are undesigned — only authorization is
Signing answers 'may this job run', never 'which worker, and what if none'. Missing: worker selection (geographic proximity to the *viewer* matters enormously if bytes go direct); deduplication and affinity when two rooms want the same infohash, or the same room re-dispatches (the second job should go to the worker that already holds the pieces); behaviour with zero available workers (fall back to the local bridge, or refuse?); capacity/bandwidth advertisement; and the fact that a worker can lie about piece availability, turning a browser Range read into an unbounded hang (see the no-timeout finding above). There is also a latent contradiction in the crate recommendation: tokio-tungstenite WSS 'outbound-only' is right for the control plane but is flatly incompatible with any design where the browser opens an inbound connection to the worker.
sources: web:signed-worker-security; web:rust-torrent-libs

### Local Network Access is carefully solved today, and the local/remote hybrid is unspecified
web/src/localHelper.ts is deliberate engineering around Chrome's LNA gate: `permissions.query({ name: 'local-network-access' })` at line 122, a single sanctioned prompt-raising probe in requestHelperAccess, a 4s availability cache, and a `pageIsLocal()` exemption at line 130. The host's own machine remains the strictly best byte source — zero relay, zero egress bill, zero legal exposure — so the sane design is local-first with remote workers as fallback, but no summary discusses the hybrid: which source a *viewer* (not the host) gets, how the room decides, or what happens on failover mid-remux. Also unverified: `pageIsLocal()` exempts the PAGE being on a private address, not the TARGET — so a worker on the user's own LAN (a NAS, a home server) still trips LNA, and whether Chrome's gate treats a private-IP target the same as loopback is not established anywhere in the sweep.
sources: web/src/localHelper.ts:118; web/src/localHelper.ts:122; web/src/localHelper.ts:130

### No user identity exists to attribute or rate-limit worker jobs against
There is no authentication anywhere in the Go server — grep for an Authorization header across internal/ returns nothing, and the trust model is stated in the source itself: 'possession of the room id plus being first is what authorizes an upload today' (internal/httpapi/clientmedia.go:29-31). So anyone who can create a room can cause a signed job to be dispatched onto a volunteer's home connection. The signing design gives cryptographic accountability between server and worker while the party actually choosing the infohash remains completely anonymous — which is the wrong end to secure if the goal is limiting abuse, and it means per-user quotas, bans and abuse attribution have no anchor to attach to.
sources: internal/httpapi/clientmedia.go:29; web:signed-worker-security

RECOMMENDATIONS:
- Decide the byte-transport fork FIRST, before any worker code: (a) relay all bytes through the VPS, (b) give each worker a WebPKI-valid name via a tunnel or wildcard DNS + ACME, or (c) go non-HTTP with WebRTC datachannel or WebTransport serverCertificateHashes. Everything else in the architecture — egress cost, CORS, the credential design, the legal posture, whether UrlSource or CustomSource is used — is downstream of this one choice.
- Draw the byte ledger for a concrete case (2h 1080p, 4 viewers, one seek to 20:00 and one back to 0:00) under each fork, counting peer→worker, worker→browser, browser→R2 and R2→viewer separately. If option (a) is chosen, verify the number against the VPS's actual bandwidth allowance before writing any Rust.
- Score 'fix ss-bridge in place' as a first-class competing option: fix the whole-window RAM buffering, the suffix-range bug and the blocking-permit ceiling, and add a playhead-priority endpoint (`POST /playhead {id, fileIndex, offset}` mapping onto librqbit's stream cursor). Free seeking is achievable with this alone and zero fleet, certificates or legal exposure.
- Prototype the sparse HLS timeline before the fleet — it is the real blocker on requirement 3 and the highest-unknown item. Specifically verify that hls.js plays a single playlist containing EXT-X-GAP placeholders with EXT-X-DISCONTINUITY and varying EXT-X-MAP across three disjoint regions, and that seeking into a GAP degrades gracefully. If it does not, the N-playlists design must be chosen instead, which changes mediaOffsetMs (web/src/types.ts:123) from a scalar to a region map across the player, server and pipeline.
- Fix the subtitle pass before anything remote: make the embedded-subtitle extraction lazy, range-bounded and driven by the same cues/clusters the remux already seeks with, or defer it entirely until the file is complete. As written it is a full second copy of the movie over whatever link is chosen.
- Make every read abortable and time-bounded before the byte source moves off loopback. Today `helper short read` (web/src/pipeline/remuxJob.ts:103, web/src/localHelper.ts:223) throws on a partial response and the fetches carry no signal and no timeout — over a WAN with a stalled or lying worker this is an unrecoverable hang, not an error.
- Re-measure `prefetchProfile: 'network'` against a WAN-latency source and record the actual read amplification per seek, rather than carrying forward a value whose in-code justification is 'the helper sits on loopback' (web/src/pipeline/mediaInput.ts:50).
- If remote workers proceed, design browser-side byte verification explicitly: ship the infohash's piece hashes to the browser and verify each range before it reaches mediabunny, or accept that the fleet is fully trusted and write that down as a stated assumption with its blast radius (arbitrary video injected into any room via the host's own presigned PUTs).
- Write the worker-operator posture down before recruiting anyone: no seeding, no DHT announce, no PEX, an explicit consent screen naming residential-ISP risk and public IP visibility, and a per-worker kill switch. Also reconsider whether the server should sign infohash-naming envelopes at all, given that the signature is durable evidence of direction.
- Add a user identity anchor (even a lightweight one) before dispatching jobs onto third-party machines. With the current 'possession of the room id plus being first' model (internal/httpapi/clientmedia.go:29) there is nothing to rate-limit, attribute or ban.
- Keep the local helper as the preferred path in whatever design wins, and specify the local-vs-remote decision explicitly — including the viewer-is-not-the-host case and failover mid-remux. The host's own machine remains free, fast and legally neutral; remote workers should be the fallback, not the default.

OPEN_QUESTIONS:
- Which transport actually carries bytes from a remote worker to the browser, and has anyone verified it end-to-end — including CORS preflight for the Range header and Access-Control-Expose-Headers for Content-Range?
- What is the VPS's bandwidth allowance and price per TB, and how many concurrent rooms does that permit under a full-relay design?
- Can mediabunny drive a CustomSource over a WebRTC datachannel or WebTransport stream (request/response framing, backpressure, abort) with acceptable latency, or does dropping HTTP Range cost more than it saves?
- Does hls.js play a single playlist with EXT-X-GAP placeholders plus EXT-X-DISCONTINUITY and per-region EXT-X-MAP without stalling, and what does seeking into a gap do?
- What is today's local ss-bridge actually capable of — throughput, time-to-first-frame, seek latency — so the claim that it is the bottleneck can be tested?
- Does librqbit hold the full file on disk for the room's lifetime, and what disk/quota commitment is being asked of a volunteer for one 4–10 GB concurrent room?
- How does a worker survive a restart, and what does the player experience when a job is re-dispatched to a worker holding zero pieces?
- Does Chrome's Local Network Access gate treat a private-IP (LAN, non-loopback) worker the same as 127.0.0.1, and does the current pageIsLocal() logic (web/src/localHelper.ts:130) still hold in that case?
- If the host's tab must stay open anyway for the browser-side remux, what concrete stability property does server-side torrenting actually buy over the current local bridge?
- Who chooses the worker for a given room, and what happens when there are none available?
- Should the server sign envelopes naming infohashes at all, given the evidentiary posture — or is a content-agnostic capability grant, with the infohash supplied by the client directly to the worker, a better legal shape?
